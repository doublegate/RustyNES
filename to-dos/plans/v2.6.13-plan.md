# v2.6.13 — the cartridge outgrows the die

## The problem, as arithmetic

v2.6.12 connected three wires and the fitted cartridge became the size it
declares: 256 KiB PRG, 128 KiB CHR, **468 of 553 M10K blocks**.

That is close to the ceiling, and the ceiling is below the scope:

| | |
|---|---|
| approved mapper scope | NROM, MMC1, UxROM, CNROM, MMC3, AxROM |
| worst case in that scope | **512 KiB PRG + 256 KiB CHR = 768 KiB** |
| total block memory on a 5CSEBA6U23I7 | **553 M10K ≈ 692 KiB** |

**The cartridge alone exceeds the whole device's block RAM**, before work RAM,
the PPU, or the framework. No tuning closes that gap. The official
`Hardware_MiSTer` documentation names the same threshold from the other side —
the SDRAM board exists "for cores requiring a large (>512KB) memory" — and says
the DE10-Nano's DDR3 "cannot fit into timings", which is why the answer is SDR
SDRAM rather than the memory already on the board.

So the SDRAM controller is not a preference or a nice-to-have. It is the thing
standing between a five-mapper core and a five-mapper core that can hold the
cartridges those mappers are for.

## What the research established

Full account: `ref-docs/2026-09-02-mister-sdram-hardware-reference.md`.

The four findings that shape this release:

1. **The framework gives us pins and nothing else.** `sys/sys_top.v` exposes raw
   SDR SDRAM signals; there is no controller in `sys/`. Writing one is entirely
   on this project — and it must be written from the datasheet, because the
   approved plan says so and ADR 0037 puts other cores' RTL out of reach.

2. **`sdram_sz` carries a validity bit.** `[15]` is 0 until the HPS says
   otherwise; `[1:0]` is the size. `T-MISTER-SDRAM-SZ` is therefore not "report
   the size" but "**do not read *not yet told* as *none present***" — this
   project's most-repeated defect shape, arriving in a new place.

3. **v2.9 and v3.0 are the same board electrically** — v3.0 moved the ICs to one
   side for assembly. There is nothing for the RTL to distinguish. And the
   SuperStation One has 128 MB integrated, so on that machine there is nothing
   to fit at all.

4. **`T-MISTER-SAVE`'s recorded blocker is REFUTED**, and this is a correction
   rather than a discovery. v2.6.12 concluded there was "no OSD-close signal to
   flush on". The MiSTer developer documentation states the contract directly:
   `ioctl_upload_req` — "for autosave, **HPS only reads this when the OSD is
   open**". The core never detects the OSD closing. The same page puts our case
   explicitly on that path: "Use ioctl upload for: smaller NVRAM/save files".

## The gate

Acceptance criteria, each measurable before the work starts:

| # | criterion | how it is measured |
|---|---|---|
| 1 | the controller obeys the part | **MET** -- `make -C tb sdram-gate`, green at THREE clock periods: 11640 ps (what ships), 10000 ps (different `ceil` boundaries, and exactly Table 16's tCK at CL2) and 8000 ps (below it, so the controller derives CL3 and both latencies are covered). Timings transcribed from Table 16, which **corrected three guesses, two of them unsafe**. CAS latency is now DERIVED from the clock period rather than parameterised -- both testbenches had pinned their own value and **neither pinned the shipped one**, which misses the fetch deadline at 17 cycles against 16 |
| 2 | **the existing ladder is the controller's test bench** | **MET as a mechanism, 141 of 142 as a result.** The harness builds `USE_SDRAM=1` -- bridge, arbiter, controller and behavioural part in the loop, the SDRAM domain clocked at 4x by the C++ driver -- and the same gates run against a cartridge answering from the part. Three framebuffers byte-identical over 61,440 pixels each, and a 200,000-cycle nestest bus trace **byte-identical to the on-die build's**. The one failure is `ppu-misc-2007-stress`, and it is a budget, not a defect: see the section below |
| 2b | **the open row buys the margin it was meant to** | **MET** -- auto-precharge dropped, a hit costs **6 cycles against 10** for a miss. Five mutations CAUGHT and five inert-and-documented with the arithmetic that makes them redundant |
| 3 | the model can fail | **MET** -- five mutations on the controller gate, five different checks, all CAUGHT, and **eight on the arbiter gate, all CAUGHT**. **Four checks across the two exist because a mutation first came back NOT CAUGHT**: tRP was checked on `ACTIVE` and neither of the two other commands it governs; the refresh check was both unreachable and the wrong SHAPE (a single gap, where the obligation is a rate); a DQM mutation was inert because the grant expression existed TWICE and the copy the controller consumes is the registered one; and a concurrent-grant mutation was inert because no stimulus had ever put two requesters in flight together |
| 3b | the arbiter meets the PPU's deadline | **MET** -- worst CHR latency **16 cycles against a budget of 16**, under CHR-every-32 and PRG-every-48 traffic over 96,000 cycles, with a `worst == 0` vacuity guard. No margin, which is what makes the derived CAS latency load-bearing rather than a detail |
| 4 | the mapper ceiling actually rises | **DEMONSTRATED, NOT SHIPPED.** Configured off-die at PRG **512 KiB** and CHR **256 KiB** the design compiles with 0 errors, block memory falls **3,680,717 bits to 534,989**, RAM blocks **468 to 84**, and timing closes with BETTER margin than on-die (**+0.471 ns setup** against +0.081) because 384 M10K blocks leave the design. It is not the shipped configuration because of criterion 2's single failure |
| 5 | it still fits and still closes | **MET** -- 0 errors, warning set matching the manifest **exactly**, `check_pins` and `check_qip` clean. The shipped on-die configuration closes at setup **+0.081 ns** / hold **+0.074 ns**; the off-die one at **+0.471 / +0.119**, and the difference between them is 384 M10K blocks |
| 6 | `sdram_sz` is read fail-closed | **MET** -- `rtl/sdram_presence.sv`, gated **exhaustively** over all 65,536 values against an independent model. Six mutations, all CAUGHT, including the ticket's own: `absent` ignoring bit `[15]` fails at `sz=0x0000`. `absent` is deliberately **not** `!present` -- 32,768 values are neither, and the gate asserts that count so the two cannot collapse into one wire unnoticed |
| 7 | the save path matches the documented contract | our half gated in simulation: request raised, `ioctl_din` presents the byte at `ioctl_addr`, download at the save index restores it, and PRG-RAM round-trips byte-identically |
| 8 | the oracle is untouched | no chip crate changes; AccuracyCoin 141/141 and nestest 0-diff by construction, verified structurally |
| 9 | the menumask is gated on its VALUE | **MET** -- `rtl/osd_menumask.sv` greys the Reset entry whenever the console is already held in reset. Four mutations CAUGHT, including the inverted polarity. The `D`-prefix polarity was **looked up, not guessed**: `D{n}` disables when the bit is SET, lowercase `d` when it is CLEAR, and getting that backwards greys exactly the wrong entries while looking like a working feature |

### Item G shrank when it was measured

Two of its three parts turned out to be wrong to do, which is worth stating
because both would have LOOKED like features:

- **`AUDIO_MIX` is declined.** The framework's `mix` blends left into right and
  right into left; this core assigns `AUDIO_L` and `AUDIO_R` from the same wire,
  so it is mono by construction and every setting is an identity. Adding the
  option would have put an OSD entry on screen that does nothing when selected
  -- the `VGA_SL` defect v2.6.6 found, added on purpose this time.
- **`LED_DISK` is already correct at zero.** `led_disk[1]` is an *override* bit;
  with it clear the framework drives the LED from the HPS's own disk activity.
  Asserting the override would have suppressed that in exchange for showing
  nothing, so the "fix" would have been a regression. It becomes ours when the
  core has disk activity of its own, which is `T-MISTER-SAVE`.

Only `jn` remains, and it is deliberately name-identical: any ergonomic remap is
a claim about how a pad feels in the hand, and no hardware here has one attached.

### The number that was wrong TWICE, and the second time was mine

The release measured against a CHR fetch budget of **16 SDRAM cycles** -- one dot,
read off the fetch structure, written down as conservative, flagged as unverified,
and then used as though it had been measured. It shaped four decisions: three
combinational shortcuts bought with real timing, and the conclusion that the
cartridge could not be served from SDRAM at all.

`nes_top`'s `CHR_LAT` parameter asks the console directly -- pipeline the byte
until a gate fails. Both framebuffer gates agreed exactly at 0 through 6 extra
clocks, breaking at 7, so **the budget was declared 28**, the cartridge was moved
off the die, and it was committed.

**That was wrong too, and in the same shape.** The framebuffer's tolerance is not
every CHR consumer's. The `$2007` data port tolerates ONE extra clock, not six --
eight cycles against 28 -- and the full off-die ladder said so: 141 of 142, with
`ppu-misc-2007-stress` returning Fail(test 2). Re-running the sweep against that
gate reproduces it precisely, passing at 0 and 1 and failing at 2.

So the first error was reading a structure and calling it a measurement, and the
second was taking a real measurement of one consumer and generalising it to all of
them. The second was made while correcting the first, and it survived a compile,
three framebuffer comparisons and a byte-identical 200,000-cycle bus trace before
the widest gate in the suite caught it.

**Four of the `$2007` port's eight cycles go to the console-domain crossing, which
is not optional, and the fastest possible SDRAM hit is six.** It does not fit, and
no arrangement of this memory system makes it fit. Serving the cartridge off the
die needs the `$2007` machine given more lead, the way the background fetch
already has it -- a change to the pipeline rungs 3 and 5 verify.

## Risks, and what each is mitigated by

1. **Latency.** The NES reads cartridge ROM on a fixed schedule; an SDRAM read is
   not single-cycle. *Mitigation:* the CPU access lands at a known point in a
   12-master-clock cycle and the PPU fetch cadence is fixed and already
   characterised — the budget is knowable before any RTL. If it does not fit, a
   small on-die cache in front of SDRAM is the fallback, and **the fallback is
   named here so that reaching for it is a decision rather than a scramble.**

2. **The controller is written from a datasheet and nothing else.** That is the
   firewall, and it is the highest-risk moment in the whole programme, because a
   working reference implementation is one search away and the temptation is
   strongest exactly when the model disagrees. *Mitigation:* the behavioural
   model is written first and from the same datasheet, so disagreements are
   adjudicated against the part rather than against somebody's code. Anything
   genuinely unimplementable escalates to an ADR **before** any source is opened.

3. **Simulation cannot prove the electrical half.** A behavioural model has no
   signal integrity, no clock phase, no board. *Mitigation:* say so. The phase
   shift and the board's marginality are rung 6 by construction, and the HPS can
   retune phase at runtime (`sdram_sz[14:8]`), which is a mitigation that exists
   on hardware and not in a testbench.

4. **Scope.** The controller is the largest single item since the PPU.
   *Mitigation:* D and E do not depend on A-C. If the controller runs past this
   release, **`T-MISTER-SDRAM-SZ` and `T-MISTER-SAVE` still land**, and the
   controller carries forward with its model and its gate already built.

## The framework audit — what we got wrong, missed, or left on the table

Requested mid-cycle: a sweep of what MiSTer and the SuperStation One offer that
this core has got wrong, not implemented, or not taken advantage of. Method: the
**90 ports `sys_top.v` hands `emu`**, diffed against what `rtl/emu.sv` actually
uses; the **CONF_STR option letters** the developer documentation defines, diffed
against our config string; and the modules in `sys/` we do and do not
instantiate. Facts from our own vendored source where possible, documentation
where not.

### Got WRONG — a second v2.6.12 error, and this one was in our own file

v2.6.12 said "this `sys/` vintage exposes **no** `OSD_STATUS` output". It is one
of the 90 ports, `rtl/emu.sv` **declares it**, and line 590 lists it in
`unused_misc` — a signal we explicitly marked unused while asserting it did not
exist. `sys_top.v:1859` wires it from the OSD module, so it is exactly the
"OSD is open" signal the SAVE ticket was said to lack.

Two independent errors in one investigation, and the difference between them is
the lesson. The first (the autosave contract) needed a document we had not read.
**The second needed one `grep` of a file we wrote.** Both were published.

### SuperStation One

Its additions are **host-side, not core-side**, and that is the finding rather
than a disappointment: PS1 controllers arrive as ordinary `joystick_*`, Zaparoo
NFC launches cores from the HPS, the M.2 slot and Wi-Fi/Bluetooth are Linux-side.
**One is core-visible** — the 24-bit ADV7125 analog DAC and DIN10 output make
`T-MISTER-DIRECTVIDEO` matter more on this machine than on a bare DE10-Nano,
because a much larger share of its users are on analog output.

Its 128 MB integrated SDRAM means the SDRAM work in this release needs no add-on
there at all.

### Triage — what this release takes, and what it does not

**Into v2.6.13**, because each is small and unblocked by the research:

| | why now |
|---|---|
| `T-MISTER-SAVE` (item E) | mechanism documented; and `OSD_STATUS` exists, giving a second valid trigger |
| `T-MISTER-SDRAM-SZ` (item D) | semantics now known, validity bit and all |
| `T-MISTER-MENUMASK` | **promoted from rung 6.** It was filed as "verified by looking at an OSD", but the mask is a *value this core computes* -- `mapper_ok` already exists -- and a gate can assert the computed mask without a display. Only the *appearance* needs eyes |
| `AUDIO_MIX`, `LED_DISK`, `jn` | one line each, and `LED_DISK` becomes meaningful the moment saves exist |

**Deferred, with the reason recorded:**

- **Save states + DDR3** — the largest item on the list and it deserves its own
  release, not a corner of the SDRAM one. Filed as **`T-MISTER-SAVESTATE`**.
  Note the ordering constraint: it wants DDR3, this release wants SDRAM, and
  doing both at once would make a timing regression impossible to attribute.
- **Cheats** — filed as **`T-MISTER-CHEATS`**. Wants the Game Genie decode the
  oracle already has, which makes it a good candidate for an oracle-gated rung.
- **`video_freak`, `video_freezer`, the 123 status bits, `P` pages** — filed as
  **`T-MISTER-OSD`**. These are one coherent piece of work (an options surface),
  and doing them piecemeal produces a menu nobody designed.
- **`FB_*`, `SDRAM2_*`, RTC, UART, user port** — declined, with reasons above.

## Explicitly out of scope

- **`T-MISTER-4PLAYER`, `ZAPPER`, `PADDLE`, `KEYBOARD`** — deferred to v2.8+ by
  the approved v2.7.0 plan, which names Four Score and Zapper in its
  out-of-scope list. Research does not re-scope an approved plan, and the
  maintainer asking for "as many tickets as possible" is not the same as asking
  for the plan to be reopened. Raised here so the decision is visible.
- **`T-MISTER-DIRECTVIDEO`, `T-MISTER-MENUMASK`** — verified by looking at a
  display. Rung 6.
- **`T-MISTER-VMODE`** — needs PAL timing, which this core does not implement.
- **Mappers beyond the top six**, and the 128 MB board's upper 64 MiB (reached by
  driving `nCS` as an address bit; this project needs under 1 MiB and will not
  go there).
- **Hardware bring-up.** No board is attached. Rung 6 stays open.


## Progress, and what the synthesiser found that nothing else could

Items A and B are complete and gated; the clock architecture (item C's
precondition) is settled by ADR 0039 and compiled. The arbiter -- PRG, CHR and
refresh sharing one controller -- is the remaining work.

**Three defects reached a green gate stack and were caught only by Quartus.**
That is the finding of this half of the release, and it is the third release
running with the same shape (v2.6.10's M10K inference, v2.6.12's unconnected
pins):

1. **`$ceil`/`$floor` are not synthesisable.** The controller linted clean at
   bare `-Wall`, passed its gate at two clock periods, agreed with a model
   written from the same datasheet -- and could not be built. Now forbidden in
   `docs/rtl-subset-policy.md` and enforced by `tb/check_rtl_subset.py`,
   demonstrated to catch a reintroduction. The conversion to integer
   picoseconds then immediately exposed a **32-bit overflow** the real-valued
   form had hidden, so the integer form is not merely portable but checkable.
2. **A latch on `sdram_cke`**, and underneath it a protocol error: the datasheet
   requires CKE LOW through the 200 us power-up and the controller asserted it
   from reset. **The gate passed identically before and after the fix**, which
   is the definition of a check that was not there; the model now catches the
   old behaviour at cycle 1. Removing the latch also bought **+0.339 ns of
   setup**, so it was the binding cost rather than an untidiness.
3. **`rtl/sdram.sv` was not in `files.qip`** -- v2.6.12's defect one layer over,
   a file missing from the SYNTHESIS list rather than the TESTBENCH list. Now
   gated by `tb/check_qip.py`, both directions, mutated.

And **`scripts/check_timing.py` read a stale report and reported eight healthy
corners** on a tree whose compile had just failed. It now refuses a report older
than any source.

## The clock architecture, and the hot paths

Both were asked for explicitly and both are measurements rather than opinions.

The seed was re-swept for this RTL (`scripts/seed-sweep.sh`, new): **all five
close**, hold binds on every one, and seed 3's +0.092 ns is 21% more binding
margin than the inherited seed 1. Seed 5 closes at +0.074/+0.067 -- the argument
for sweeping rather than trusting, since landing there would still have read as
"timing closes".

**There are no hot paths in this project's RTL.** The binding path in the whole
design is `pll_hdmi`, inside vendored `sys/`. The console has 13.075 ns of setup
slack on a 46.6 ns period, and the SDRAM controller has 1.68x Fmax headroom on a
brand-new interface. Adding a memory controller and a second clock domain to a
design whose worst slack was a fifth of a nanosecond sounds like it should have
cost something; it cost nothing that binds.
