# v2.6.13 — the cartridge outgrows the die

## The problem, as arithmetic

v2.6.12 connected three wires and the fitted cartridge became the size it
declares: 256 KiB PRG, 128 KiB CHR, **468 of 553 M10K blocks**.

That is close to the ceiling, and the ceiling is below the scope:

| | |
|---|---|
| approved mapper scope | NROM, MMC1, UxROM, CNROM, MMC3, AxROM |
| worst case in that scope | **512 KiB PRG + 256 KiB CHR = 768 KiB** |
| total block memory on a 5CSEBA6U23I7 | **553 M10K ≈ 692 KiB** |

**The cartridge alone exceeds the whole device's block RAM**, before work RAM,
the PPU, or the framework. No tuning closes that gap. The official
`Hardware_MiSTer` documentation names the same threshold from the other side —
the SDRAM board exists "for cores requiring a large (>512KB) memory" — and says
the DE10-Nano's DDR3 "cannot fit into timings", which is why the answer is SDR
SDRAM rather than the memory already on the board.

So the SDRAM controller is not a preference or a nice-to-have. It is the thing
standing between a five-mapper core and a five-mapper core that can hold the
cartridges those mappers are for.

## What the research established

Full account: `ref-docs/2026-09-02-mister-sdram-hardware-reference.md`.

The four findings that shape this release:

1. **The framework gives us pins and nothing else.** `sys/sys_top.v` exposes raw
   SDR SDRAM signals; there is no controller in `sys/`. Writing one is entirely
   on this project — and it must be written from the datasheet, because the
   approved plan says so and ADR 0037 puts other cores' RTL out of reach.

2. **`sdram_sz` carries a validity bit.** `[15]` is 0 until the HPS says
   otherwise; `[1:0]` is the size. `T-MISTER-SDRAM-SZ` is therefore not "report
   the size" but "**do not read *not yet told* as *none present***" — this
   project's most-repeated defect shape, arriving in a new place.

3. **v2.9 and v3.0 are the same board electrically** — v3.0 moved the ICs to one
   side for assembly. There is nothing for the RTL to distinguish. And the
   SuperStation One has 128 MB integrated, so on that machine there is nothing
   to fit at all.

4. **`T-MISTER-SAVE`'s recorded blocker is REFUTED**, and this is a correction
   rather than a discovery. v2.6.12 concluded there was "no OSD-close signal to
   flush on". The MiSTer developer documentation states the contract directly:
   `ioctl_upload_req` — "for autosave, **HPS only reads this when the OSD is
   open**". The core never detects the OSD closing. The same page puts our case
   explicitly on that path: "Use ioctl upload for: smaller NVRAM/save files".

## The gate

Acceptance criteria, each measurable before the work starts:

| # | criterion | how it is measured |
|---|---|---|
| 1 | the controller obeys the part | against `tb/sdram_model.sv`: initialisation sequence, `tRCD`/`tRP`/`tRC`/`tRFC` honoured, CAS latency respected, refresh issued inside `tREF` |
| 2 | **the existing ladder is the controller's test bench** | **all 142 co-simulation gates pass with the cartridge served through SDRAM.** This is the criterion that matters: it re-runs every mapper, every framebuffer comparison and AccuracyCoin against a cartridge that now answers from a controller instead of a block RAM |
| 3 | the model can fail | mutate the controller (drop a refresh, violate `tRCD`, take CAS latency to the wrong cycle) → each **CAUGHT** by the model, not merely by the gates |
| 4 | the mapper ceiling actually rises | PRG **256 → 512 KiB**, CHR **128 → 256 KiB**, and M10K usage **falls** because the cartridge left the die |
| 5 | it still fits and still closes | Quartus 0 errors, timing positive at **all four corners**, warning set unchanged, `check_pins` clean |
| 6 | `sdram_sz` is read fail-closed | a mutation that ignores bit `[15]` is **CAUGHT** — power-on "unset" must not read as "no board" |
| 7 | the save path matches the documented contract | our half gated in simulation: request raised, `ioctl_din` presents the byte at `ioctl_addr`, download at the save index restores it, and PRG-RAM round-trips byte-identically |
| 8 | the oracle is untouched | no chip crate changes; AccuracyCoin 141/141 and nestest 0-diff by construction, verified structurally |

## Risks, and what each is mitigated by

1. **Latency.** The NES reads cartridge ROM on a fixed schedule; an SDRAM read is
   not single-cycle. *Mitigation:* the CPU access lands at a known point in a
   12-master-clock cycle and the PPU fetch cadence is fixed and already
   characterised — the budget is knowable before any RTL. If it does not fit, a
   small on-die cache in front of SDRAM is the fallback, and **the fallback is
   named here so that reaching for it is a decision rather than a scramble.**

2. **The controller is written from a datasheet and nothing else.** That is the
   firewall, and it is the highest-risk moment in the whole programme, because a
   working reference implementation is one search away and the temptation is
   strongest exactly when the model disagrees. *Mitigation:* the behavioural
   model is written first and from the same datasheet, so disagreements are
   adjudicated against the part rather than against somebody's code. Anything
   genuinely unimplementable escalates to an ADR **before** any source is opened.

3. **Simulation cannot prove the electrical half.** A behavioural model has no
   signal integrity, no clock phase, no board. *Mitigation:* say so. The phase
   shift and the board's marginality are rung 6 by construction, and the HPS can
   retune phase at runtime (`sdram_sz[14:8]`), which is a mitigation that exists
   on hardware and not in a testbench.

4. **Scope.** The controller is the largest single item since the PPU.
   *Mitigation:* D and E do not depend on A-C. If the controller runs past this
   release, **`T-MISTER-SDRAM-SZ` and `T-MISTER-SAVE` still land**, and the
   controller carries forward with its model and its gate already built.

## Explicitly out of scope

- **`T-MISTER-4PLAYER`, `ZAPPER`, `PADDLE`, `KEYBOARD`** — deferred to v2.8+ by
  the approved v2.7.0 plan, which names Four Score and Zapper in its
  out-of-scope list. Research does not re-scope an approved plan, and the
  maintainer asking for "as many tickets as possible" is not the same as asking
  for the plan to be reopened. Raised here so the decision is visible.
- **`T-MISTER-DIRECTVIDEO`, `T-MISTER-MENUMASK`** — verified by looking at a
  display. Rung 6.
- **`T-MISTER-VMODE`** — needs PAL timing, which this core does not implement.
- **Mappers beyond the top six**, and the 128 MB board's upper 64 MiB (reached by
  driving `nCS` as an address bit; this project needs under 1 MiB and will not
  go there).
- **Hardware bring-up.** No board is attached. Rung 6 stays open.
