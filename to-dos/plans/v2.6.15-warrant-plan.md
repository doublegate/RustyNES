# v2.6.15 "Warrant" — the claims v2.7.0 will make become checkable, and the instrument pays the oracle back

## The problem, as a measurement

v2.7.0 is the submission. The contributing page's step 1 states the bar for
AI-assisted code verbatim:

> "Fully AI generated code should meet a minimum reasonable bar for readability
> and **include some evidence of quality and accuracy testing**."

This project's evidence is real -- 142 co-simulation gates, a mutation record
for each, seven rung documents that each state what the rung **cannot** verify.
And `tb/regress.sh` says in its own header that it *"is NOT a CI gate and cannot
be"*, so today that evidence is a set of documents describing gates a reviewer
cannot run from a clean checkout.

v2.6.14 audited the checklist and found five boxes already true, two ticked on
evidence that had expired, and one that could never have been ticked honestly.
It stopped at the checklist. The same defect -- **a claim measured once, that
nothing re-checks** -- sits in nine further places, two of which a reviewer
would care about most: `sys/` is asserted byte-identical to
`Template_MiSTer@3ea1134c` on a v2.6.6 measurement with no gate behind it, and
the accuracy ladder cannot be executed outside this machine at all.

## What opens the version: a name that would ship nothing

The `.rbf` naming divergence has been carried since v2.6.7 as a style item
awaiting a maintainer decision. Research for this plan measured it, and it is
not a style item.

`Distribution_MiSTer`'s builder (`.github/download_distribution.py`) requires a
stem whose **last nine characters are `_` followed by exactly eight digits**,
and `continue`s -- skips entirely -- any file that does not match:

```python
def remove_date(path: str) -> str:
    if len(path) < 10:
        return path
    last_part = Path(path).stem[-9:]
    if last_part[0] == '_' and last_part[1:].isnumeric():
        return path.replace(last_part, '')
    return path
```

`RustyNES_MiSTer-v2.6.13.rbf` yields no date, so it would never be copied into
the distribution and never reach a user through `update_all`. **The failure mode
is an accepted core that ships nothing, with no error anywhere.**

A second, independent parser in the firmware (`Main_MiSTer/file_io.cpp`'s
`get_display_name`) has a *different* rule -- the first literal `_20` with at
least six characters after it. `_YYYYMMDD` is the only form satisfying both.

Two parsers with different rules, one correct answer, and the current name
satisfies neither. That is what opens this version.

## The second finding: "needs no SDRAM" is the differentiator

The MiSTer wiki maintains a *Cores that use SDRAM* table -- which is not
documentation but the live registration database the distribution builder parses
on a 20-minute cron -- where the NES row reads `SDRAM Required? = Yes` at
86 MHz. The official FAQ gives the reason in the NES's own words:

> "The original NES for instance needs to access the ROM directly, so the
> timings are much tighter so SDRAM is required."

**This core's on-die build does not have that problem**, because PRG and CHR
live in M10K. `SDRAM Required? = No` is a table-visible property `NES_MiSTer`
cannot claim, arrived at by the mechanism the FAQ itself names as the reason the
requirement exists.

Against the duplicate-core risk that is stronger than any accuracy figure,
because it changes what hardware a user must buy. **Consequence:** the on-die
build is the default and the submission artifact, not a fallback -- which
demotes the slot-scheduled arbiter from "the largest item between here and
v2.7.0" to v2.8.0 capability groundwork.

## Decisions taken with the maintainer

| Question | Decision |
|---|---|
| `.rbf` naming | **Ship both.** `releases/RustyNES_YYYYMMDD.rbf` -- the only form both parsers accept -- plus the GitHub release asset `RustyNES_MiSTer-vX.Y.Z.rbf` for traceability. Byte-identical. GitHub release assets are parsed by nothing upstream, so the two coexist. |
| v2.7.0 and hardware | **Hold v2.7.0 until a board exists.** v2.6.15 prepares the bring-up so rung 6 costs a session, not a release. |
| v2.8.0 groundwork | **All four tracks** -- savestates + battery saves, expansion audio, cheats + OSD, more mappers. Groundwork, not implementation. |

## Risks

1. **A changes the oracle, and the oracle is the reference for every golden.**
   Regenerate and re-run the whole co-simulation suite, not just the MMC3 gates.
   Keep the pre-change run as a control: the first difference must be the cycle
   aimed at, or the experiment changed rather than the DUT.
2. **A's diagnosis may be wrong.** If driving the pre-render rise moves
   `4-scanline_timing` to sub-test **2** rather than past 3, the clock is not
   the missing piece. That is how the DUT's first two candidate fixes died.
   Test against the ROM, not against the other console.
3. **Scope.** Eight workstreams. Anything that does not fit is named at the cut.
4. **F1 may not simulate.** Measure whether `hps_io.sv` elaborates under
   Verilator before designing around it.
5. **C1 may not fit a runner.** Measure the export and gate time for a candidate
   subset before building the job.
6. **C4 is prose, and prose cannot be audited.** Where a fact has a
   machine-readable referent, gate it; where it does not, delete the duplicate
   so the fact has exactly one home.
