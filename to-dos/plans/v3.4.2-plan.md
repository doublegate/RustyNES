# v3.4.2 "Keystone": the RetroArch core on Apple Silicon Macs

A one-fix patch release on the v3.4.1 "Beacon" line, written on 2026-10-20.

## The report

The maintainer (2026-10-20): RetroArch on their Mac had not loaded the
RustyNES core for at least a couple of releases, v3.4.0 and v3.4.1 included.
RetroArch "locks and drops to CLI terminal" on loading it; the desktop app's
macOS binaries work.

## What was found

- The buildbot serves both macOS cores, rebuilt nightly
  (`apple/osx/{arm64,x86_64}/latest`, 2026-10-20 05:13-05:14). Both are valid
  Mach-O libraries exporting all 50 `retro_*` symbols, linking only
  `libSystem` and `libiconv`.
- **The arm64 core's code signature does not match its contents**: 101 of 538
  CodeDirectory page hashes mismatch, and the signed range ends 32 bytes before
  the signature. macOS on Apple Silicon kills (SIGKILL) a process that loads
  arm64 code with a broken signature, which is the reported freeze-and-exit.
- Controls from the same server, gambatte and snes9x (C cores built natively
  on libretro's Mac runner), verify with 0 mismatches, so the checking script
  is right and the defect is in how our core is built.
- Cause: libretro's `rust-apple.yml` template runs `$STRIP -S` after the
  link. On arm64 the linker has already ad-hoc signed the dylib, and the
  image's strip (osxcross, on Linux) rewrites it without re-signing.
  `rust-osx.yml` has the same step.
- The x86_64 core carries no signature, so Intel Macs are not affected.

## The deliverable

- `.gitlab-ci.yml`: `libretro-build-osx-arm64` sets `STRIP_CORE_LIB: "0"`.
- `libretro_buildbot_audit`: pins that setting in the job's own `variables`.
- The finding in `docs/agents/libretro.md`; an upstream report to
  `libretro-infrastructure/ci-templates`, drafted for the maintainer to review
  (maintainer, 2026-10-20), not filed by the agent.

## Gate

- **The branch's own buildbot pipeline produces an arm64 dylib whose signature
  verifies: 0 of N pages mismatched, and the signed range reaching the
  signature.** libretro's mirror builds every pushed branch, so this is
  measured on the same builder that serves RetroArch, before merge.
- The audit test passes, and fails when the setting is deleted (mutation).
- The release anchors, notes, CHANGELOG and lockfiles agree on 3.4.2 (the
  harness's release audits).

## Out of scope

- No new MiSTer bitstreams, ladders or seed sweep (maintainer, 2026-10-20: none
  should be needed, and none is: no RTL changes). The release attaches v3.4.1's
  two bitstreams byte for byte under v3.4.2 names, as v2.9.3-v2.9.7 did.
- No emulation, app or format change: epoch 5, protocol 9, and v3.4.1's save
  states, movies and netplay sessions carry over.
- Confirming the load on a real Mac is the maintainer's: RetroArch's Online
  Updater serves the nightly build of `main`, so the fixed core reaches it about
  a day after the merge, and the copy already downloaded must be replaced.
