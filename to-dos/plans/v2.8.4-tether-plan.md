# v2.8.4 "Tether" — the off-die SDRAM build, made trustworthy

The fifth and last release of the v2.8.x line
([ADR 0041](../../docs/adr/0041-hardware-release-is-v3.0.0.md);
[line plan](v2.8.x-libretro-rtl-audit-plan.md)). v3.0.0 ships the off-die
(SDRAM) bitstream as its secondary build, so the SDRAM path has to be as
defensible as the on-die one. It works from
[`rtl-audit-report.md`](../../docs/audits/rtl-audit-report.md) §3.4, §4.6 and
§5.2, and the [RTL ledger](../../docs/audits/rtl-disposition.md) rows targeted
at v2.8.4. The work is in the sibling.

## What v2.8.3 closed and did not

v2.8.3 "Rivet" closed the robustness rows for the on-die path. The off-die
path's rows (R-3.4a, R-3.4c, R-3.4d, R-4.6, R-5.2) were held for this release,
because the on-die bitstream does not instantiate `cart_sdram` and a change
there is invisible to its compile.

## What planning found before any code

| Row | Claim | Finding |
| --- | --- | --- |
| R-3.4a | CKE rises on the same edge as the first PRECHARGE | CONFIRMED (`sdram.sv:481-482`). The model cannot see it: it checks CKE on the command's own edge, while the part registers CKE a cycle earlier, so a command on the edge CKE rises is ignored by silicon and accepted by the model |
| R-3.4b | DQM high through the read wait masks the data beat | The ledger's REFUTED holds only at the shipped CL2. The controller selects CL3 below 10 ns, and `SDRAM_PERIODS` already runs the gate at 8,000 ps (CL3); the model masks writes only, so it cannot see the read side at all |
| R-3.4c | arbiter slices the served word with the pending request's byte bit | CONFIRMED (`sdram_arbiter.sv:353`): a strobe that arrives while the same source is served overwrites `*_hold` before the ack |
| R-3.4d | `wr_busy` omits `wr_stb` | CONFIRMED as a race; appears unreachable today (writes reach `cart_sdram` at most once per `clk_sys` cycle, four SDRAM cycles apart), so fixed as latent |
| R-4.6 | no SDRAM I/O constraints | CONFIRMED (v2.8.2 ledger) |
| R-5.2 | multi-bit address sampling across `clk_sys` -> `clk_sdram` | to measure: the clocks come from one PLL at exactly 4:1, so the crossing is synchronous and STA times it; the off-die compile is the evidence |

## The deliverable

1. **The model first.** `tb/sdram_model.sv` registers CKE (a command is
   honoured only if CKE was high at the previous edge) and masks read data by
   DQM with the datasheet's two-cycle read latency.
2. **The controller:** CKE raised with a NOP before the first PRECHARGE; DQM
   held low through a read's latency, so CL3 is correct too.
3. **The arbiter:** the byte select latched at grant; `wr_busy` covers the strobe
   cycle.
4. **The constraints:** `set_input_delay` / `set_output_delay` on the SDRAM
   pins, written for the documented AS4C32M16SB and marked provisional until the
   SuperStation One's part is read at v2.9.2; the false `RustyNES.sdc` header
   corrected.
5. **The off-die bitstream, buildable without editing source:** a Verilog macro
   selects it, and a script builds it.
6. **Bring-up:** a MemTest step and the "SDRAM absent" behaviour of an off-die
   bitstream, in `docs/bringup.md` / `docs/HARDWARE_TESTING.md`.

## The gate

- Each model change turns red against today's controller (the CKE check on the
  init sequence; the DQM check at 8,000 ps), and green after the controller fix.
  Reverting each fix fails again.
- The arbiter gate gains a re-strobe-during-service case and a back-to-back
  write case, each red before its fix.
- `tb/regress.sh` green on-die (165) and off-die (`USE_SDRAM=1`), `make -C tb
  lint` clean.
- Quartus at seed 4 closes timing for BOTH builds; the off-die report shows the
  SDRAM I/O paths constrained (no longer in "Unconstrained Paths") and the
  `clk_sys` -> `clk_sdram` transfers met (R-5.2's evidence).

## What was found and done

| Row | Verdict | How it was shown |
| --- | --- | --- |
| R-3.4a CKE with the first PRECHARGE | FIXED | the registered-CKE model flags cycle 17,192 of `sdram-gate`; `S_INIT_CKE` issues a NOP first |
| R-3.4b read DQM | FIXED (was REFUTED) | with read DQM modelled, every CL3 read (8,000 ps) returned `0x0000`; DQM now low for reads |
| read capture edge (found by R-4.6) | FIXED | the model presented read data one edge later than the datasheet (Figure 20) and the controller sampled to match; the off-die STA failed the DQ capture by 11.185 ns. Model and `S_RW`'s CAS wait corrected; the corrected model read `0x0000` everywhere against the old controller |
| R-3.4c arbiter byte lane | FIXED | `sdram-arb-gate` section 6 (re-strobe during service) read `0xa1` for `0xb2`; the lane is latched at grant |
| R-3.4d `wr_busy` | FIXED, latent | section 7 (back-to-back writes) lost the second write; unreachable from `cart_sdram` today |
| R-4.6 SDRAM I/O constraints | FIXED, provisional | on-die compile: 50 unconstrained output ports (59 before), only `SDRAM_CLK` among the SDRAM pins; `sdram_clk_pin` +4.531 ns setup / +1.337 ns hold |
| R-5.2 address crossing | NOT A DEFECT | the two clocks share one PLL at 4:1 and sit in one `-exclusive` group, so the crossing is synchronous and analysed; off-die at the shipping seed 5, `clk_sys` -> `clk_sdram` meets +2.022 ns setup / +0.158 ns hold at the worst corner |

Found along the way: `project_close -dont_export_assignments` did not stop
Quartus writing the off-die macro into `RustyNES.qsf` (`execute_flow`
writes the assignments first). The build script now writes the macro to
disk and restores the file from a snapshot, as the seed sweep does for
`SEED`, and checks the restore against git.

## Line close

The line plan asks for one full Quartus seed sweep per build once the last RTL
change of the line has landed. That is this release; it runs last, and the
pinned seed changes only by the criterion recorded in `RustyNES.qsf`.

Done on the final RTL, seeds 1-5, worst of all four corners, each from a clean
database at one build date (260926). Every seed closes in both builds.

| Seed | On-die setup / hold (ns) | Off-die setup / hold (ns) |
| --- | --- | --- |
| 1 | +0.407 / +0.058 | +0.348 / +0.078 |
| 2 | +0.105 / +0.051 | +0.357 / +0.103 |
| 3 | +0.411 / +0.078 | +0.131 / +0.097 |
| 4 (was pinned) | +0.414 / +0.067 | +0.389 / +0.083 |
| **5 (pinned)** | **+0.414 / +0.078** | +0.270 / +0.081 |

The pin moves 4 -> 5 (sibling `0f53373`). Both of the `.qsf`'s criteria pick 5
on-die; this is the first sweep where one seed serves two builds, so the rule
is now written there: the on-die criterion chooses, and the off-die build must
close at that seed. It does, at +0.270 ns of setup against +0.389 at seed 4.
The release compiles reproduce the sweep rows exactly (on-die `.rbf` md5
`53fd0548de0d7d6773922fc56c06f806`, off-die
`120117e21d2991b363c6dc4c482723f3`, the latter byte-identical to the sweep's own
seed-5 output).
