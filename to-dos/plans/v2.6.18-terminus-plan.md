# v2.6.18 "Terminus" — a CPU write lands where the cycle ENDS, and this core applies it where the cycle begins

> Covers exactly one release. Opened by a measurement taken during v2.6.17,
> recorded in that release's CHANGELOG under *Measured and rejected*.

## What opens the version: two dots, measured twice, on a ROM that names the dots

AccuracyCoin `Frozen OAM2 Increment` states the dots it writes on, which makes
the alignment directly checkable rather than inferable. Probing both `$2001`
writes the test performs, armed to the single frame the behaviour occurs in:

| write | the ROM names | this core applies |
|---|---|---|
| disable `$00` | scanline 194, dot 242 | scanline 194, dot **240** |
| enable `$1E` | dot 256 | dot **254** |

Both exactly **two dots early**, on two independent writes in one run.

The mechanism is not in dispute and is not a tuning constant. `Cpu::start_cycle`
catches the PPU up **before** the bus access, so a PPU register write is
applied at **M2-low** — the first of the CPU cycle's three PPU dots. A 6502
commits a write at **phi2**, the third. Everything downstream of a `$2001`,
`$2000`, `$2005`, `$2006` or `$4014` write therefore observes it two dots
earlier than hardware does.

**This is v2.5.4's finding one layer out.** That release found the
co-simulation TESTBENCH presenting every CPU access on the second of a cycle's
three dots and moved it to phi2; the EMULATOR applies them on the first, and
nothing has re-measured that since the v2.0.0 scheduler rewrite.

## Why this is a version and not a patch

The tempting fix was tried in v2.6.17 and is **refuted, with numbers**. Delaying
the rendering-enable gate (`rendering_enabled_delayed`, shipped lag 1) was swept
1..4 against the full battery with the mask-timing-sensitive tests as controls:

| lag | passed | Frozen OAM2 | Stale Sprite Shift Regs | Misaligned OAM2 |
|---|---|---|---|---|
| **1 (shipped)** | **143/144** | FAIL | pass | pass |
| 2 | 141/144 | FAIL | FAIL | FAIL |
| 3 | 141/144 | FAIL | FAIL | FAIL |
| 4 | 140/144 | FAIL | FAIL | FAIL |

No value closes the test and every value above the shipped one regresses two
tests that pass today. **The gate is not the lever; the write placement is.**

Moving it shifts every PPU register write in every game. That reaches the
60-ROM commercial oracle, the visual baseline corpus, every committed golden
whose run contains a PPU register write, and the co-simulation suite in the
sibling. It is ADR 0029 territory and needs its own re-baselining, which is
precisely why it is scoped here instead of appended to v2.6.17.

## Deliverable

- **A. Establish the control BEFORE changing anything.** Capture the current
  per-cycle bus stream and the framebuffer/audio hashes for the corpus that
  will be re-baselined. The first difference after the change must be a PPU
  register write's effect dot and nothing else; anything earlier means the
  experiment changed rather than the write placement.

- **B. Move the write to phi2**, behind a default-off feature so the shipped
  build is byte-identical until the evidence says otherwise. The change is in
  the `start_cycle` / `end_cycle` ordering in `rustynes-core`, not in the PPU.

- **C. Measure, per test, with controls named.** AccuracyCoin by test name (not
  the headline count — v2.6.17 showed the count hides which tests moved),
  nestest 0-diff, blargg batteries, `cpu_interrupts_v2`, the commercial oracle,
  the visual corpus.

- **D. Decide on the evidence, and accept a refutation.** If phi2 placement is
  a net regression, that is a result: revert, keep the numbers, and record why
  the M2-low placement is load-bearing. This project has shipped rejected
  changes with their measurements before and this plan authorises it again.

- **E. If it lands: the ADR.** ADR 0029 states the scheduler's access model;
  moving the commit point amends it, and the amendment names what was
  re-baselined and why.

## The gate

- **`Frozen OAM2 Increment` is NOT the acceptance criterion.** It is one
  observation. Closing it while regressing anything else is a failure, and the
  v2.6.17 sweep is the worked example of why a single-test target misleads.
- Per-test AccuracyCoin comparison before and after, **by name**. Net
  improvement with zero named regressions, or the change does not land.
- nestest 0-diff, blargg 11/11, `cpu_interrupts_v2` 5/5 — all VERIFIED.
- Every re-baselined golden accompanied by the reason its bytes moved. A
  re-baseline with no stated cause is how a real regression gets blessed.
- The default build byte-identical while the feature is off, measured.

## Progress: the diagnosis is CONFIRMED, and the cost is three tests

Deliverable B is built (`phi2-write-sweep`, default off) and C's first sweep is
done. `write_split`'s `pre` is the lever, and the result is unambiguous:

| offset | commit lands at | passed | gained | lost |
|---|---|---|---|---|
| **0 (shipped)** | 1.5 dots in | **143/144** | — | — |
| 1 | 1.75 dots in | 143/144 | — | — |
| **2** | **2.0 dots = phi2** | 141/144 | **Frozen OAM2 Increment** | Arbitrary Sprite zero, Stale Sprite Shift Regs, Misaligned OAM2 Address |
| 3 | past phi2 | 141/144 | Frozen OAM2 Increment | the same three |
| 4 | past phi2 | 141/144 | Frozen OAM2 Increment | the same three |

Two things fall out, and the second is the version's real subject.

**The root cause is confirmed.** Offset 2 is exactly where the commit crosses
into the cycle's third dot — phi2 — and that is the offset at which
`Frozen OAM2 Increment` starts passing. Offset 1 changes nothing at all,
because it does not cross the dot boundary. So the test is not sensitive to
"a bit later"; it is sensitive to *which dot the write commits on*, which is
the hypothesis, stated in advance, behaving as predicted.

**Three tests currently depend on the WRONG placement.** `Arbitrary Sprite
zero`, `Stale Sprite Shift Regs` and `Misaligned OAM2 Address` pass today and
fail at phi2. That is the v2.5.7 shape exactly — a wrong phase with windows
downstream compensating for it — and it means the version cannot be "move the
write and re-baseline". Each of the three has to be examined on its own terms
to establish whether it is a compensation that must move with the phase, or a
genuine behaviour the phi2 model gets wrong.

Note `Misaligned OAM2 Address` among them: v2.6.17 closed it by modelling
OAM2Address as a live counter, and that model was calibrated against the
M2-low write placement. It is the clearest candidate for a compensation.

**Nothing is adopted.** The shipped default stays offset 0 and the build is
byte-identical with the feature off (the `const` path is retained under
`cfg(not(feature))`, so the hot `write_split` pays no atomic load). 141 < 143,
so adopting now would be a net regression blessed by a single-test target —
precisely what this plan's gate forbids.

## Risks

1. **The corpus re-baseline can bless a regression.** The whole risk of this
   version. Mitigation: the first-difference control in A, and per-test naming
   in C. Never re-baseline on a diff nobody read.
2. **Two dots may not be one number.** The offset was measured on `$2001`
   writes; reads and other registers may not share it. Measure per access
   kind before assuming a single constant.
3. **It may be refuted.** Named as an acceptable outcome in D so a null result
   is reportable rather than something to push past.
4. **The sibling co-simulation suite compares against this oracle.** A change
   in oracle behaviour re-opens those gates; budget for re-exporting goldens
   from a pinned commit.

## Out of scope

- **Rung 6 / hardware and the v2.7.0 submission.** Unchanged, still awaiting a
  board.
- **Any further OAM2 work.** `Frozen OAM2 Increment` stays pinned in
  `KNOWN_FAILING` until this version decides the alignment question.
- **Re-litigating the v2.6.17 save-state epoch.** `PPU_SNAPSHOT_VERSION` 9 is
