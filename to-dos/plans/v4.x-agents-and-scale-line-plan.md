# v4.x: the agents-and-scale line (D34)

Drafted 2026-10-17 from the maintainer's D34 request: language models play the games (Claude,
Gemini, Codex, and local models served by LM Studio or any other OpenAI-compatible server), the
core runs massively in parallel on a GPU to fuzz and test games at scale, and a search finds the
optimum run to a game's completion. It follows the power-user line
([`v4.x-power-user-line-plan.md`](v4.x-power-user-line-plan.md), v4.1.0-v4.5.0). The slots are
proposals: each release is planned in full when its predecessor ships, and the two GPU releases
wait on a measured go/no-go (`T-GPU-SPIKE`).

| Slot | Ticket (size) | Item | Gate |
| --- | --- | --- | --- |

## Order and dependencies

- `T-AI-PLAY` builds on `T-MCP-SERVER` (v3.5.0): its tool set must include the observation
  layers and pause, not only RAM and stepping.
- `T-AI-PLAY`, `T-TAS-SEARCH` and `T-A11Y-NARRATION` (v4.3.0) share the per-game RAM schemas that
  `T-GHOST-RACE` and `T-SPEEDRUN-MEMIF` start. One schema format, one directory.
- `T-RL-ENV` (v4.5.0) consumes `T-CORE-FORK` rather than building its own fork path. If
  `T-RL-ENV` ships first, `T-CORE-FORK` moves to v4.5.0 with it.
- `T-LANE-CORE` needs `T-CORE-FORK`'s audio-off mode and state hashes; `T-GPU-BATCH` and
  `T-GPU-SEARCH` wait on `T-GPU-SPIKE`'s ADR. A no-go leaves the CPU batch as the scale path and
  closes both tickets with the measurement.

## Rules for this line

- **The CPU core is the oracle.** A lane or GPU result is a candidate until the full core replays
  it from power-on.
- **What the research says, labelled as such.** Published GPU emulators set the expectations, not
  RustyNES: NeSLE (NES on CUDA, mapper 0 only, not cycle-accurate) reports about 13M frames/s on
  an A100; CuLE (Atari 2600) reports 3-4x over a 12-core CPU, and up to about 97% of peak lost
  under fully divergent execution. A cycle-accurate lane core on the RTX 3090 is estimated at
  50K-500K frames/s, which is a hypothesis for `T-GPU-SPIKE` to test, not a figure to quote.
  Throughput is bounded by registers per thread and warp divergence, not memory: 24 GB holds more
  than a million instance states.
- **Integer-only on the GPU.** Floating point does not round identically across a CPU and a GPU
  (fused multiply-add contraction, relaxed precision), so the lane core keeps APU timing and drops
  synthesis. Audio, where wanted, is hashed separately and never blocks state equality.
- **Toolchain isolation.** `nvptx64-nvidia-cuda` is a nightly target, so the CUDA host crate sits
  outside the workspace with its own `rust-toolchain.toml`, as `rustynes-cosim` does. The
  workspace stays on its pinned stable toolchain, and the lane core's source must build on it.
  rust-gpu, wgpu and Vulkan compute are a later portable fallback under the same no-allocation,
  no-`dyn` shape.
- **Provenance.** The lane core is derived from RustyNES's own crates, so any region carrying a
  `// Provenance:` header takes that header and its section 1 row into the lane copy
  (`provenance_record_audit` covers the whole tree). NeSLE, CuLE, tasbot/playfun, Go-Explore and
  any other project's code are black boxes: their designs are taken from papers and READMEs only.
- **AI safety.** API keys come from environment variables only and are never logged or written to
  a transcript; a local-only mode never contacts a cloud provider; the MCP server listens on
  loopback behind a token; text read from the game is untrusted model input; per-game packs come
  from public RAM maps only; each episode carries a spend and token cap. The docs say plainly that
  a cloud adapter sends frames of the user's own ROM to that provider.
- **Determinism.** Model output is not deterministic, so the `.rnm` is the reproducible record of
  an episode; the core is not touched.
- **Honest claims.** Every throughput figure names its hardware, board list and baseline; every
  fuzzing or search claim names the boards and seeds it covers.

## Out of scope

- Reinforcement-learning training stacks (PPO on the GPU): `T-RL-ENV` is the environment, not the
  trainer.
- JAX or XLA ports of the console. Published JAX environments reimplement games, not consoles.
- Hosted GPU capacity, and shipping benchmarks built on commercial ROMs.
