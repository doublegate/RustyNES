# v2.4.0 "Concordance" — make the outside record match the code, and pay the deferrals

## Goal

A concordance is an index built so two records can be checked against each other.
This release is about the places where RustyNES's record of itself and the record
other people read have been allowed to drift apart — and about the work that was
deliberately deferred with a written reason, now that the reason has expired.

It is a **MINOR** release: additive, default-off, no breaking change. v2.0.0
remains the one designated breaking release (ADR 0003), and nothing here touches
the save-state or movie epochs.

Two things distinguish it from v2.3.9, which was about gates that reported passes
they had not earned:

- **v2.3.9 fixed checks. This one fixes the things checks cannot see.** The
  upstream `.info` is in a repository no test of ours can read; the deferred items
  below are each guarded by a reason written down at the time rather than by a
  gate.
- **Every item here already exists in writing as a deferral.** Nothing is invented
  for the release. If an item cannot be traced to a recorded decision, it does not
  belong in this plan.

## Item A — the upstream libretro sync (marquee, and the one that is owed)

### The obligation, stated precisely

`docs/libretro/UPSTREAM_SYNC.md` records the maintainer decision: upstream syncs
are **batched to MINOR releases**, so the next one is v2.4.0. The upstream
`dist/info/rustynes_libretro.info` therefore reads `display_version = "v2.3.5"`
through the whole v2.3.6–v2.3.9 line — *deliberately, and not by oversight*.

That deferral is now due. This is the release it was deferred **to**.

### What makes this more than a version bump

The v2.2.9 failure this policy exists to prevent was not a stale number. RetroArch
reads `dist/info/rustynes_libretro.info` from **`libretro/libretro-super`** — a
separate copy that nothing syncs and nothing compares — so the GPL relicense
reached this repo's `.info`, `Cargo.toml`, `NOTICE`, `deny.toml` and every SPDX
header, and did not reach the file users actually see. RetroArch advertised
MIT/Apache-2.0 for eleven days.

The distinction the policy rests on is worth restating because it is what makes
batching safe: **a stale `display_version` misreports a number; a stale `license`
misreports the terms under which the software is distributed.** Anything touching
`license`, `supported_extensions`, or the declared capabilities still syncs
immediately regardless of the release cadence.

### The surfaces, all of which move together

| Surface | Repo | Path |
| --- | --- | --- |
| Core metadata RetroArch reads | `libretro/libretro-super` | `dist/info/rustynes_libretro.info` |
| Public core docs page | `libretro/docs` | `docs/library/rustynes.md` |
| Local source of truth | this repo | `crates/rustynes-libretro/rustynes_libretro.info` |

### What has actually changed since v2.3.5, and must therefore be carried

Established by reading the local `.info`'s history rather than recalled:

- `display_version` — v2.3.5 upstream, v2.4.0 locally after this release.
- `description` — the mapper-family count moved **172 → 174** in v2.3.4
  (WAIXING-FS005 / NAMCOT-3453 / Sachen SA-020A).
- Every capability flag needs re-asserting by hand against the crate. The audit
  pins `license`, `display_version` and `supported_extensions` against two
  sources of truth, and **cannot see** `disk_control`, `savestate`, `cheats` or
  `core_options`. Those are the fields where a wrong value survives silently, so
  they are the ones to check against `rustynes-libretro` rather than against the
  previous `.info`.

### Verification

The audit cannot see upstream — no test can — so the sync itself stays a human
step. What it *can* do is make the sync a **copy** rather than a re-derivation,
and it already does. The check before opening the upstream PRs is therefore:

1. `cargo test -p rustynes-test-harness --test libretro_info_audit` (three
   assertions; note the `--test` form, since a bare filter matching nothing exits
   0).
2. A literal byte comparison of the local file against the one being pushed
   upstream, quoting the ref by name — a diff against "the local file" is not the
   same claim as a diff against a tag.

### Out of scope for this item

`libretro/docs#1180` — the licence on the libretro docs site — is a third-party
issue outside this project. It is tracked, not owned.

## Item B — the timeline generation counter (the mechanism v2.3.9 scoped and did not build)

### Where this came from

v2.3.9 item E cleared the call stack and access counters on a ROM change, and
recorded that the same telemetry is **not** cleared on a save-state load. A
two-call-site patch was declined as insufficient, with the reason measured rather
than argued:

| timeline jump | reachable from a patchable call site? |
| --- | :---: |
| native load-state | yes |
| wasm load-state | **no** — restores inside a `spawn_local` task holding only a cloned `EmuHandle` |
| rewind (`nes.rewind_step_back`) | **no** |
| netplay rollback | **no** |

One of four, presented as having fixed the class.

### The mechanism, and why it beats the heuristic

The plan originally proposed a last-seen `Nes::cycle()` in each consumer, reset on
a non-monotonic step. Review on #415 proposed better, and the difference is a case
the heuristic provably cannot cover:

| signal | rewind / rollback | restore to a LATER state |
| --- | :---: | :---: |
| last-seen `cycle()` | yes | **no** — the counter advances, so it is indistinguishable from execution |
| core-side generation counter | yes | **yes** |

`Nes` bumps a `timeline_generation` in `restore_inner`, in `rewind_step_back`, and
on a netplay rollback. A consumer holds the last value it saw and clears itself
when it changes. One `u64`, no cooperation from any call site, and it turns *"did
the timeline jump?"* from something inferred into something answered.

**It also generalises past this defect.** The provenance-stash problem — *every
same-timeline restore must carry the state that lives outside the save state* — is
the same question asked in the opposite direction: a same-timeline restore is
exactly one that must **not** bump the counter. Landing both against one signal is
the reason to build it rather than patch further call sites.

### The counter must NOT be serialized, and that is load-bearing

Review on #425 asked whether it belongs in the save state. It must not, and the
reason is the failure it would create rather than a preference.

The counter's only job is to be **different** after a discontinuity. Serialize it
and a restore puts back an *old* value — so loading a state saved earlier in the
session can hand a consumer a generation it has already seen, and the consumer
concludes nothing jumped at the exact moment something did. A session-local
monotonic counter cannot do that: it only ever increases, so any restore produces
a value no consumer has seen.

That makes it a member of the set `snapshot_schema_audit.rs` already enumerates —
fields deliberately excluded from the snapshot — and it lands with an entry there
carrying this reason. That file's known limitation applies directly: its reasons
are free text, and a keyword pass over them once mis-sorted 17 of 26. The entry
must therefore say **session-local, must not be restored**, not the vaguer
"runtime state" that a future sweep would have to interpret.

### Verification bar

Touches `rustynes-core`, so **AccuracyCoin is verified, not asserted** — 141/141
on the RAM decoder, nestest 0-diff, both with a confirmed non-zero test count.
Land it with the consumers that read it rather than ahead of them, so the counter
is never a field nothing observes.

## Item C — atomic writes for the remaining user-data paths

### The deferral

v2.3.9 made `Config::save_to` atomic and durable — sibling scratch file, `fsync`,
rename, parent-directory sync, exclusive creation, mode carried across, symlink
resolved. It explicitly did **not** extend that to the two other paths that write
user data with the same truncating `fs::write`:

- `save_state.rs::save_to_slot` — **a truncated save state is a user's game
  progress**, which is arguably worse than a truncated config.
- `cheats.rs` — the per-ROM cheat list.

The reason recorded at the time was that they want a **shared helper** rather than
a third copy of the same forty-line justification, and that a shared helper is a
wider change than the review thread which produced the first one.

### What the helper has to carry

Everything the config path learned the hard way, because each was found by review
after the "obvious" version shipped in a PR:

1. Sibling scratch file — across a filesystem boundary `rename` is not a rename.
2. `fsync` before the rename — `fs::write` returns at the page cache, so an
   atomic rename over unsynced data is not durable.
3. Parent-directory sync — on POSIX the entry `rename` creates is itself a cache
   update until the directory is synced.
4. `create_new(true)` — `File::create` follows symlinks and truncates (CWE-377).
5. Mode applied **at creation** via `OpenOptionsExt::mode`, then set exactly.
6. Symlink resolution — `fs::write` follows a link, `rename` replaces it, so a
   dotfiles-symlinked target must be resolved first.
7. A pid + per-call counter in the scratch name, which is what makes (4)
   adoptable at all: with a shared `.tmp`, exclusive creation fails every save
   after one crash.

Seven properties, of which **five came from review rather than from the first
draft.** That is the argument for one helper rather than three implementations.

### The helper is not uniform across platforms, and the plan should not pretend it is

Review on #425 is right that this needs stating rather than assuming. Three of the
seven properties are POSIX-specific, and the config implementation already gates
them:

| property | Windows |
| --- | --- |
| parent-directory `sync_all` | not applicable — opening a directory as a `File` is not portable, and `MoveFileEx` orders the metadata write |
| mode at creation, then exact mode | not applicable — the ACL is inherited from the parent directory rather than carried on the file |
| symlink resolution | applicable in principle; the dotfiles pattern that motivates it is a Unix convention |

`rename`-replaces-existing is the one that needed checking rather than assuming,
and it holds: `std::fs::rename` maps to `MoveFileEx` with
`MOVEFILE_REPLACE_EXISTING`. The helper therefore has a portable spine — scratch
sibling, write, `fsync`, exclusive creation, rename — with a `#[cfg(unix)]` tail.
That is the shape the config path already has, and the reason it is worth
extracting rather than reinventing per call site.

### Verification

Per-property tests, in both directions where a direction exists. The config path's
suite is the template: the symlink test, the occupied-scratch decoy, the
rename-failure cleanup, and the permissions assertion that failed before its own
fix. State plainly which properties are **not** covered — `fsync` is not
observable in-process, and neither is the scratch counter.

## Item D — the two remaining `skip_serializing_if` claims

`graphics.hd_packs` (v1.5.0) and `graphics.shader_presets` (v1.2.0) both document
a pre-feature config as "byte-identical". Both are byte-identical only until the
first save: `#[serde(default)]` is a **load** guarantee, and the TOML serializer
writes an empty table for an empty collection.

v2.3.9 corrected the prose and deliberately did not change the behaviour, because
altering what two shipped features write is a separate decision from fixing a
false claim. This is where that decision belongs.

The change is one attribute each plus a round-trip test per field asserting **both
directions** — the empty case is omitted, and a populated one survives. A
one-directional test passes against a field that never persists anything at all,
which is the failure mode an over-eager `skip_serializing_if` produces.

## Item E — RAM Atlas: the remaining export paths

Deferred in v2.3.9, and the condition recorded there — *"until the Watch export
has been used in anger"* — is **not evaluable**, which review on #425 correctly
flagged. Nothing can test it, so as a gate it was decoration.

Stated properly: this item is **unscheduled**, and it opens when a maintainer
schedules it. The design question is already settled (below), so what is missing
is demand rather than analysis — and demand is a judgement call rather than a
measurement. Writing it as a condition dressed a scheduling decision up as a
criterion.

When it does open, the one thing already established: **a cheat is a write**, so
unlike the watch export it needs the locked-session predicate (netplay / TAS /
RetroAchievements hardcore) that gates Observe and Verify. The watch export
correctly does without it because it only writes to another panel's list.

Per-game persistence stays out, and the reason has not changed: a restored verdict
without its evidence is a claim that cannot be checked, which is this panel's whole
argument in reverse.

## Explicitly out of scope

Named so they read as decisions rather than omissions.

- **APU workstream D2 and D4.** Unmeasured on purpose. Under fat LTO with
  `codegen-units = 1` the guarded code is already inlined and its always-not-taken
  branches perfectly predicted, so the prior for these two is a **null, not an
  unknown** — D1, D3 and D6 each measured that null. `docs/performance.md` carries
  the three conditions that would justify reopening them.
- **A per-PR CHANGELOG gate.** Measured against the last 50 first-parent merges
  and rejected at a **62% false-positive rate** — features land bare and the cut
  PR composes the section. A check keyed on the *cut* rather than the PR is the
  shape that would work.
- **Bisection in the Divergence Lens.** Not implemented as a decision: it costs
  about seventeen extra trials to produce a weaker answer than the causal-input
  comparison already gives. It remains the only route in a build without
  `debug-hooks`.
- **A store launch.** RustyNES is income-free (ADR 0035); any free listing is a
  later, unversioned step and is not tied to this release.

## Verification bar

The standing gate, plus:

- **AccuracyCoin 141/141 on the RAM decoder** — the authoritative one; the
  framebuffer decoder reports 120 and is known-buggy — and nestest 0-diff.
  **Verified rather than asserted** for any item touching a chip crate or
  `rustynes-core`, which item B does by construction.
- **A non-zero test count confirmed** on every suite quoted. A filter matching
  nothing prints `0 passed` and exits 0; the `--test <target>` form is the one
  that runs an integration suite.
- **Any new gate demonstrated to fail** for the defect it targets, by mutation.
  A gate that cannot fail is not a gate.
- **The full clippy matrix**, not one build: workspace, `debug-hooks`, `full`,
  `no_std` thumbv7em, and all four wasm32 combinations. v2.3.9 found a lint
  violation reachable only under `browser-cheevos`; a lint added on one build
  covers one build.
