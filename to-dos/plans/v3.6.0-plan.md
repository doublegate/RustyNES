## Results recorded during the release

- **Row 4, `T-LIBRETRO-CONSOLES` (2026-10-23): no-go on all three targets.**
  Switch: the Rust target has no `std`, and a `-Zbuild-std` build fails in
  `std` itself (v2.9.8's reason, now checked by a build). Vita and 3DS: the
  staticlib compiles with nightly `-Zbuild-std`, but no libretro template or
  image has Rust and the console SDK, it was not linked (no devkitARM or
  VitaSDK here), and at about 4 ms per frame on an i9-10850K the core is
  expected (not measured) to run well below full speed on a 268-444 MHz ARM
  core. No buildbot job was added. Detail and what would reopen it:
  `docs/libretro/architecture.md`, "Console targets".
- **Rows 1-3 and `T-LIBRETRO-EMU-OPTIONS`:** done on
  `feat/v3.6.0-libretro`; see CHANGELOG `[Unreleased]`. Found on the way, not
  fixed: a Vs. `DualSystem` cabinet's state does not round-trip byte for byte
  under the CPU overclock (inert OAM-decay ages; a core issue, pinned by an
  ignored probe in the libretro harness).

## Row 5 and its companion tickets: the record (2026-10-23)

Row 5 (`T-ANDROID-API37`) landed with `T-ANDROID-AUDIO-NONBLOCKING`,
`T-IOS-DURABLE-WRITE` and `T-IOS-FDS-PERIODIC` on `feat/v3.6.0-mobile`. Gates
met: the permission flow under JVM test (`LocalNetworkAccessTest`), and a LAN
session on the emulator (two headless API 37 emulators, run-sheet L1 and L2).
Skipped, each with what would unblock it:

- **Every device row** (run-sheet L1-L5, T13, T14): no Android 17 phone or
  iOS device was used. A physical Android device was attached over wireless
  adb and was deliberately not touched without the maintainer's say-so. L4,
  the audio drift check, is what the maintainer asked for before the blocking
  write went (`c04da0ca`); the emulator reading in that row is not a
  measurement.
- **Compiling the Swift**: no Swift toolchain on the Linux host. The iOS
  workflow's Simulator build compiles it on the first push; until then the
  only gate is `ios_source_audit.rs`, which proves wiring, not behaviour.
- **L3, room-code play with the permission refused**: needs a configured
  relay reachable from the emulators.

`T-DEBUG-DAP` status (2026-10-23, branch `feat/v3.6.0-dap`): the gate is met by
a scripted DAP client in `crates/rustynes-dap/tests/dap_e2e.rs` against a cc65
and an llvm-mos build of `tests/roms/dap/dapdemo.c`, rebuilt with pinned
toolchains by CI's `dap-fixtures` job (ADR 0049, `docs/dap-debugger.md`). Not
run: an actual editor (no VS Code instance was driven) and an actual GDB or
LLDB, because no released build of either has a MOS 6502 target; the GDB stub
is exercised by a protocol client in `tests/gdb_e2e.rs`. Unblocked by a GDB or
LLDB with MOS support, and by a maintainer run of the VS Code sketch in the
spec.

`T-AUDIO-STEMS` landed on `feat/v3.6.0-stems` (`docs/audio-stems.md`): both
gates met, the CLI only. **Skipped:** a desktop menu entry (both tools are
headless passes over a fresh console; from the window they would need their
own thread and progress UI); per-chip stems for a multi-chip NSF (would need a
per-chip record in the mapper's per-cycle path); ripping bank-switched boards
(needs the NSF bank layout inferred from the trace). **Found:** the NSF
player had not called a 60 Hz tune's `play` since v2.9.8 (fixed on the same
branch; whether it raises `EMULATION_EPOCH` is for the cut).

## For the maintainer (2026-10-23)

- **Provenance question, `rustynes-dap`'s cc65 reader.** Before writing
  `crates/rustynes-dap/src/debuginfo/cc65.rs` the agent had read
  `rustynes-frontend/src/debugger/source_map.rs`, which carries a Mesen2
  `Provenance:` header. It wrote the new reader from ld65's own `--dbgfile`
  output and cc65's documentation and put an origin disclosure at the top of
  the file rather than a `Provenance:` header. Whether that is a derivation
  needing a header, a section 1 row and a `NOTICE` entry is the maintainer's
  judgement, not the tooling's; it is recorded here and in the release notes,
  not certified either way.
- **libretro save states grow 16 bytes**: each state records the emulation
  options it was made under (overclock, sprite limit, Four Score, forced DIP
  switches) and a restore applies them, because RetroArch replays movies from
  a state and starts netplay from the host's state. Older states still load
  and leave the options alone. Reverting `85d8780b` keeps the two options but
  drops the record.
- **NSF output changes**: 60 Hz NSFs play again (not since v2.9.8), and MMC5
  NSFs play at all. No golden or fingerprint covers an NSF, so nothing
  recorded moved. `EMULATION_EPOCH` rises to 8 anyway (maintainer,
  2026-10-24), the strict reading of the bump rule taken at v3.5.1: NSF
  output changes from the same inputs. `last_release_epoch` becomes 8 at the
  cut.
- **Not yet verified on hardware or with real clients**: no Android or iOS
  device row ran; the Swift is uncompiled on this Linux host; no editor and no
  GDB/LLDB has driven `rustynes-dap`; no RetroArch build offers float audio.
