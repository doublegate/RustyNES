# v2.3.8 "Parallax" — the Divergence Lens

**Status:** **SHIPPED** 2026-08-20 (tag `v2.3.8`, cut from the boundary commit
`5ba66392` rather than from `main`, so the release artifacts contain exactly the
Divergence Lens). See `CHANGELOG.md` `[2.3.8]`.

## Goal

Answer **"why do these two runs differ?"** with the same causal chain the last two
releases built for a single run.

Two `Nes` instances, one anchor, identical input, differing configuration. The
Lens finds the first frame where they part company, narrows that frame to the
pixel or the sample that actually differs, and hands that pixel to Pixel
Provenance (v2.3.2) and that sample to Audio Provenance (v2.3.7) — which already
answer "which instruction caused this, and when".

This is the third of three because it is the cheap one: it *composes* the two
provenance features rather than building a third.

---

## What the substrate already provides — read this before planning any of it

`crates/rustynes-probe/src/lib.rs` (v2.3.6) is further along than the v2.3.7
carry-forward note credited, and the note is wrong on one point. Verified against
the source, not from memory:

| Capability | Status | Where |
| --- | --- | --- |
| Two configurations from one anchor | **already works** | `run` (baseline) + `run_perturbed` (variant) |
| The licence to attribute a difference to the config | **already argued** | `run_perturbed` doc: `setup` runs after restore and before any frame, so "whatever it changes is the only difference" |
| First frame where two trials differ | **already works** | `Probe::first_divergence(a, b) -> Option<u32>` |
| "They agree" vs "nothing ran" | **already distinguished** | `Probe::agree` exists precisely because `first_divergence(..).is_none()` is also true for two empty trials |
| Trial budgeting | **already enforced** | `Budget`; the uncounted path was made private on #384 after `latency::measure` used it and the budget was "computed, documented and never enforced" |
| The caller's provenance survives a trial | **v2.3.7, and it did not before** | `TrialGuard` holds both stores aside across the anchor restore, which `Nes::restore_inner` clears |
| A trial's *own* provenance | **does not exist** | the same guard leaves the emulator unarmed for the trial's duration, deliberately — see work item B |

**The carry-forward note says divergence is "located by the v2.3.6 probe engine's
bisection". There is no bisection in the probe engine, and frame-granular
divergence does not need any**: `run` materialises one `u64` per frame, so
`first_divergence` is a linear scan over an array that already exists. Bisection
would only buy something in a design that refuses to record every frame — see
work item B, where that trade-off is real.

Correcting this now matters because "we already have bisection" would have made
item B look free.

## The actual gap

`Observable` reduces an entire frame to **one `u64`**:

```rust
pub enum Observable { Framebuffer, IndexFramebuffer, Wram, AudioEnergy }
```

That is the right shape for *detecting* divergence and the wrong shape for
*localising* it. A hash says frame 412 differs; it cannot say which pixel. And
`AudioEnergy` is documented as "coarse energy … quantised, because exact float
equality across a resample would be noise, not signal" — so an audio divergence
arrives coarser still.

So the Lens is not "find the divergence" (done) but **"narrow the frame the
detector already found, then hand off"**. Everything below follows from that.

## Status — what has landed

Recorded here rather than left to be inferred from the branch, because the plan
is the thing people read to find out what is left.

| Item | State | Where |
| --- | --- | --- |
| A — localise a framebuffer divergence to pixels | **landed** | `divergence::localise`, `PixelDivergence` |
| B — sub-frame localisation | **closed, without bisection** | `Probe::run_capturing`, `localise_explained` |
| C — audio divergence | **landed**, resolves to a CPU cycle | `divergence::localise_audio` |
| D — the panel surface | **landed** | `Tools -> Divergence Lens` |
| spec | **landed** | `docs/divergence-lens.md` |

Two findings from building it, both worth carrying forward rather than leaving in
commit messages:

- **Item A needed no new engine primitive.** A trial restores the anchor on the
  way IN and not on the way out, so the diverging frame can be read straight off
  `nes`. The estimate that it would need one was wrong in the cheap direction.
- **A doc claim had to be retracted mid-item.** `differing_fields` was
  documented as possibly empty at a located pixel. It cannot be: an
  index-framebuffer entry is `(emphasis << 6) | colour`, so a differing entry
  means `color` or `color_mask` differs. Under the permissive reading an empty
  result is something to render; under the correct one it means the two records
  did not come from the two configurations. A mutation reading both from the
  same trial was caught only once the assertion was tightened to match.
- **Item A shipped a bug that its own review caught before a reviewer did.**
  `localise` ran its four trials and returned, leaving the live emulator wherever
  the last trial ended — through the panel, asking a question advanced the user's
  game by thirty frames. Both entry points now restore through one wrapper, and
  that restore is guarded so it does not clear the caller's provenance, which is
  the v2.3.7 defect one layer up.

**Item B closed, and the answer was neither option this plan offered.** It framed
the choice as bisect-the-frame versus ride-the-records, and asked for the cheap
one to be proved viable first. Proving it produced a third answer.

For audio, riding the records works directly and resolves to a CPU cycle. For
pixels, `localise_explained` returns the diverging pixel's `PixelProvenance` from
**both** configurations, so the answer is *which causal input differs* — the
winning layer, the pattern row, the nametable and attribute addresses, the
palette entry, the emphasis mask — rather than *at which cycle the two runs
parted*.

That is better than bisection rather than cheaper, which is why the plan's
framing was wrong rather than merely unresolved. A cycle index says when; a
differing `pattern_addr` says the two runs fetched different tile data, which is
a lead. Bisection would have spent ~17 extra trials to produce the weaker answer.

**Bisection is therefore not implemented, as a decision.** It remains the only
route in a build without `debug-hooks`, and it is the mechanism to reach for if a
case appears whose causal inputs match but whose timing differs.
`docs/divergence-lens.md` carries the full record so the question is not
rediscovered.

## Work items

### A — Localise a framebuffer divergence to pixels (marquee)

Given frame `N` from `first_divergence`, re-run both configurations to `N`,
retain the **full** framebuffers rather than their hashes, and diff them.

- Return the diverging pixel set, not just the first pixel: a one-pixel
  difference and a whole-scanline difference are different bugs, and the count is
  the cheapest signal that distinguishes them.
- Report the **bounding box plus the population count**. A caller that wants one
  pixel takes the first; a caller that wants to know "is this a palette change or
  a scroll bug" wants the shape.
- Hand the chosen pixel to Pixel Provenance **in the diverging instance**, armed
  for exactly frame `N`. The panel already answers dot/scanline, winning layer,
  nametable/attribute/pattern addresses, palette entry, and the CPU instruction
  and cycle behind each byte.

**Why not just diff every frame as you go:** retaining two full framebuffers per
frame across a long trial is the memory blow-up the `u64` reduction exists to
avoid. Detect cheap, localise expensive, and only once.

### B — Sub-frame localisation, and the honest cost argument

Frame `N` is where they differ *by the end of the frame*. The PPU renders it over
89,342 cycles, so "frame N" can hide a divergence that began at dot 0 or at dot
89,341 — a distinction that matters when the question is which instruction did it.

Two candidate mechanisms were listed here, with the instruction to **choose on a
measurement, not a preference**, and to establish before writing either whether
the cheap one works at all:

1. **Bisection over cycles within the frame.** Re-run to cycle `k`, compare, halve.
   `log2(89_342) ≈ 17` re-runs of a partial frame. Bounded and simple; costs
   ~17 trials against a `Budget` that exists specifically to stop this class of
   loop from being unbounded.
2. **Ride the existing per-cycle records.** v2.3.7's Audio Provenance already
   keeps a `MixRecord` per CPU cycle when armed, and Pixel Provenance keeps the
   per-pixel causal record. If both are armed for frame `N`, the divergence may be
   readable *without* re-running at all.

**Settled, before either was written. Option 2 does not work as stated, and the
reason is not the one predicted.** The anticipated failure mode was that the two
records would not be comparable across instances. The actual one is that there
are no records to compare: **a probe trial produces none.**

`Probe::run_uncounted` restores the anchor through `restore_quiet`, and
`Nes::restore_inner` clears both provenance stores. So before the v2.3.7 fix, a
trial's records were destroyed at the start of the *next* trial — and the
caller's records with them, which is the user-visible defect that fix closed.
After it, `TrialGuard` holds both stores aside for the trial's whole duration,
which leaves the emulator **unarmed** while a trial runs. That is deliberate and
correct: re-simulated frames never happened on the user's timeline, so they must
not contribute attributions to it. But it means a trial records nothing, under
either the old behaviour or the new one.

So item B does not shrink to plumbing, and it does not fall back to bisection
either. Its **first step is a new capability**, and the v2.3.7 fix is what makes
that capability cheap and safe rather than dangerous:

- **`Probe::run_capturing_provenance`** (name provisional) — same trial, but
  instead of leaving the emulator unarmed, arm a **fresh** store for the trial
  and return it to the caller alongside the samples. The caller's own store is
  already held aside by `TrialGuard`, so there is no path by which a captured
  trial can contaminate the user's timeline; that separation is the precondition,
  and it now exists.
- Two trials, each with its own captured store, are then directly comparable —
  same anchor, same instance, one perturbation between them.
- The store must be **opt-in per trial**, not per `Probe`. Arming a per-cycle mix
  trace for every trial would make the Latency Oracle pay for a feature it never
  reads: a frame is ~29,780 CPU cycles, so 21 trials is ~625k records nobody
  looks at.

Bisection is **not** dead — it is now the fallback rather than the alternative,
and it is what a build without `debug-hooks` must use, since capture cannot exist
there. Decide between them on the same basis as before: measure the capture path
first, and only write bisection if it does not answer the question.

**Still do not implement both speculatively.** The v2.3.1 campaign measured ten
candidates and rejected all ten; the value there was the measurement, not the code.

**Carry the lesson, not just the finding.** The plan asked to establish option 2's
viability before writing either mechanism, and that instruction is the only reason
this was caught at the design stage instead of surfacing as a Divergence Lens that
returned an empty explanation for every input — which is precisely how Pixel
Provenance shipped, four releases running.

### C — Audio divergence

`AudioEnergy` is deliberately coarse, so it detects and cannot localise. With
Audio Provenance armed on both instances, the diverging **sample** resolves to a
`MixRecord` — mixed value, dominant channel, that channel's live state, the
`$4000-$4017` write behind it, and the instruction and cycle that performed the
write.

Note the v2.3.7 fix that makes this complete: `$4014` and `$4016` are now
attributed, so a divergence caused by an OAM DMA or a controller strobe inside
the APU window resolves to an instruction rather than to an empty slot.

### D — The surface

One panel, `Tools → Divergence Lens`, `debug-hooks`-gated and output-only like
its two predecessors, so the shipped default build is unaffected **by
construction** — and verified anyway, per the v2.3.4 lesson that "by
construction" claims about a crate you edited are the ones that turn out false.

It must decline rather than guess, in the two v2.3.6 senses:

- **"They agree" and "nothing ran" are different answers** and must render
  differently. `Probe::agree` already encodes this distinction; the panel must
  not collapse it.
- **A budget exhausted mid-search is not "no divergence".** It is "I stopped
  looking", and the panel says so. The Latency Oracle's `None` vs `Some(0)`
  precedent applies directly.

Register it in `DebuggerOverlay::clear_rom_bound_analysis` — the single hook for
panel state that outlives the `Nes` it describes. Three panels have already been
caught by that seam; a fourth must not add a per-panel clear.

## Verification bar

The standing gate, unchanged, plus:

```bash
cargo clippy -p rustynes-probe --all-targets -- -D warnings
cargo clippy -p rustynes-probe --all-targets --features debug-hooks -- -D warnings
cargo test  -p rustynes-probe
cargo test  -p rustynes-probe --features debug-hooks
```

**Both feature states, every time.** `rustynes-probe` gained a `debug-hooks`
passthrough in v2.3.7, so it now has two configurations that compile different
code, and the Lens lives in the gated one. A single-configuration run is how the
feature-off build breaks unnoticed — `TrialGuard::enter` already needed a
configuration-scoped `#[allow]` because it is `const`-eligible only with the
feature off.

**The accuracy contract, verified and not asserted** — confirm a non-zero test
count, since a filter matching nothing prints `0 passed` and exits 0:

```bash
cargo test -p rustynes-test-harness --features test-roms --test accuracycoin  # 141/141, RAM decoder
cargo test -p rustynes-test-harness --features test-roms --test nestest       # 0-diff
cargo test -p rustynes-test-harness --features test-roms --test audio_expansion  # 25 passed
```

**Specific to this release:**

- The pixel-diff must be **mutation-checked per branch**, not once. A test that
  exercises only the "they differ" path leaves the "they agree" path vacuous, and
  a two-assertion test with one mutation is the trap recorded in
  `CLAUDE.local.md`.
- A **known-divergent pair** and a **known-identical pair** are both required
  fixtures. Without the second, a Lens that always reports divergence passes.
- If item B chooses bisection, its trial count must be **asserted against the
  budget**, not merely bounded in prose.
- If item B implements trial-scoped capture, one test must assert the **caller's**
  store is byte-identical after a capturing trial — not merely non-empty. The
  whole point of the capability is that a trial's records and the user's records
  stay separate, and "non-empty" passes on a store the trial refilled with frames
  that never happened. That is the exact assertion strength the v2.3.7 fix was
  written against.
