# v2.9.x — re-audit, optimise, and take the core to the board

The third minor line to the SuperStation One core at **v3.0.0**
([ADR 0041](../../docs/adr/0041-hardware-release-is-v3.0.0.md)). By its start the
four audits are closed in their ledgers and the last planned RTL change has
landed. This line checks that claim, spends what optimisation clears the bars,
cuts the release-candidate bitstreams, and **runs them on the board**.

> **Re-planned (maintainer, 2026-09-29).** The board session (v2.9.2's Strands
> A-F) and the mobile device runs (v2.9.3) move after v3.0.0, with the fixes
> each produces; v2.9.4+ as written below does not happen in this line. v2.9.3
> shipped its prepared run sheet and emulator pre-run without the device run.
> See [ADR 0041](../../docs/adr/0041-hardware-release-is-v3.0.0.md)'s 2026-09-29
> amendment.

([`v2.7.0-shakedown-plan.md`](v2.7.0-shakedown-plan.md), now superseded). They
were written for the board and they are still right, so they are carried here

## SDRAM and DDR3: what the SuperStation One's memory makes possible

Researched 2026-09-26 at the maintainer's request, in the project and on the
Internet (MiSTer framework documentation, the SS1's published specifications,
datasheets, nesdev). **No NES emulator or NES core source was read**, the
firewall above applying in full. Tags: **[V]** read at the source, **[S]** a
search summary only (confirm before relying on it), **[M]** measured here,
**[I]** inference.

### Four facts that decide everything below

1. **The SDRAM is private to the fabric; the ARM reaches DDR3.** The SDRAM sits
   on FPGA I/O pins (GPIO 0 plus three Arduino-header pins) [V
   <https://boogermann.github.io/Bible_MiSTer/hardware/sdram-board/>], and the
   HPS talks to a core only through `hps_io` (ioctl download and upload, the SD
   block interface, status bits) and through DDR3 [V
   <https://mister-devel.github.io/MkDocs_MiSTer/developer/hps_io/>]. So the
   SDRAM is the low-latency store for what the fabric needs at bus speed, and
   anything software on the HPS must see goes through DDR3.
2. **The framework already puts state in DDR3, not SDRAM.** Save states live in
   a DDR3 region the core declares with `SS{base}:{size}`, four slots, each with
   a change-counter header the HPS watches; the core serialises its own state
   [V <https://mister-devel.github.io/MkDocs_MiSTer/developer/savestates/>].
   Rewind exists in the Game Boy core (40 s) and the GBA core (about 0.5% speed)
   [V, their READMEs], stored in DDR3 [S]. DDR3 reads take about 20 cycles at
   100 MHz "but can be way longer" [V
   <https://mister-devel.github.io/MkDocs_MiSTer/developer/emu/>], which is why
   cartridges stay in SDRAM.
3. **The cartridge needs about 1 MB of the 128.** Of 2,682 images in the
   per-game database, 8 exceed 512 KiB PRG or 256 KiB CHR [M]. The capacity
   matters only as mapper breadth grows (MMC5 1 MB each [V nesdev]; mapper 268
   multicarts to 32 MiB [V nesdev]).
4. **But the on-die caps already exclude real games.** This core's six mapper
   families cover 2,170 database titles: **2,022 fit on the die, 141 (53 USA
   releases) fit only the off-die build** -- among them *Kirby's Adventure*
   (512 KiB / 256 KiB), *Mega Man 5* (256 KiB CHR) and *Mega Man 6* (512 KiB
   PRG) -- 6 are MMC1 SUROM, refused by both (among them *Dragon Warrior III*
   and *IV* and *Final Fantasy I, II*), and 1 fits neither (*Street Heroes*,
   an unlicensed image the database lists as mapper 0 with 512 KiB each of PRG
   and CHR) [M, `crates/rustynes-gamedb/src/game_database.txt` against
   `emu.sv`'s `PRG_MAX_KB`/`CHR_MAX_KB`; the last group was omitted until
   v2.9.1's review, which is why the groups summed to 2,169].

The bus has room: at 8 cycles an access, one PRG read and about 1.5 CHR fetches
use roughly 20 of the 48 SDRAM cycles in a CPU cycle [I, from `docs/sdram.md`'s
measured access cost]. But the CPU's deadline has little margin, so no new SDRAM
traffic is safe until more exists. **Corrected at v2.9.1:** this paragraph said
"zero margin, 24 of 24 on the console", which is v2.6.16's figure. Re-measured
on the v2.9.0 tree it is **22 of 24** on all three console workloads, a margin
of 2, and 26 of 24 in the arbiter gate's synthetic worst case [M,
`RustyNES_MiSTer/docs/sdram.md` §"v2.9.1: CHR in its own bank"].

### Candidates, and where each lands

| # | Candidate | Where it runs | Placement | Main constraint |
|---|---|---|---|---|
| S1 | **Split PRG and CHR into different SDRAM banks** (NR-08) so a PRG read never closes the row a CHR fetch has open | fabric | **v2.9.1** | measured by the arbiter gate's latency table and the off-die ladder |
| S2 | **Slot-scheduled arbiter**: give CPU and PPU fixed slots, since both access patterns are deterministic | fabric | **Decided at v2.9.1: after v3.0.0.** S1 left PRG's worst at 22 of 24 (CHR's went 20 to 18). The bound is refresh: a refresh precharges every bank, so the access after it misses wherever the rows are. No added SDRAM traffic lands before v3.0.0, so nothing needs more margin before then. Redesigning the arbiter one release before the first board session would put an untested design on the board | a redesign of `sdram_arbiter.sv` that also places refresh in known-idle slots; the prerequisite for any added SDRAM traffic (S4-S12) |
| S3 | **Which build is the headline.** Off-die runs 141 titles the on-die build refuses | -- | **input to v3.0.0** (ADR 0041 made off-die secondary; this number is new) | the off-die build needs SDRAM, which a bare DE10-Nano lacks; the SS1 always has it |
| S4 | **Mapper breadth into the space**: MMC1 SUROM (the two *Dragon Warrior* titles), MMC5, large multicarts | fabric + SDRAM | after v3.0.0 (rung 7 continued) | MMC5's split and per-tile CHR banks make its fetch pattern the hardest the arbiter would see |
| S5 | **CHR prefetch / line buffer**: pattern addresses are known dots ahead (nametable byte first; all eight sprites at dot 256) [I, nesdev PPU rendering] | fabric | after v3.0.0, with S4 | only needed once a mapper's pattern defeats S1 and S2 |
| S6 | **Save states** through the framework's DDR3 `SS` region | fabric serialiser + DDR3 + HPS | after v3.0.0 (first feature candidate) | the core must stream every register and memory, including PRG-RAM and CHR-RAM held in SDRAM |
| S7 | **Rewind**, a ring of states in DDR3: at an estimated 20-30 KiB per state, 64 MB is about 40-60 s of every-frame rewind | fabric + DDR3 | after S6 | DDR3 arbitration against the scaler framebuffer (GBA reports about 0.5% slowdown and some audio stutter) |
| S8 | **Spend the freed M10K** (468 to 84 blocks off the die): NTSC composite simulation, band-limited audio, expansion-audio tables | fabric | after v3.0.0; band-limiting informed by Strand C's measurement | DSP and ALM budget, not memory |
| S9 | **FDS**: disk image in SDRAM or DDR3, 8 KiB BIOS on the die, writes persisted through the HPS | fabric + HPS | after v3.0.0 | disk-write persistence path |
| S10 | **Cheats**: the framework's `.gg` loader (address, compare, replace) with a fabric compare-and-replace on the CPU bus [V <https://mister-devel.github.io/MkDocs_MiSTer/cores/features/cheats/>] | fabric + framework | after v3.0.0 (small) | none beyond the matcher |
| S11 | **RetroAchievements**: the core mirrors WRAM and PRG-RAM into DDR3 each VBlank; software on the HPS runs rcheevos | fabric + HPS | after v3.0.0, **only in a third-party `Main_MiSTer` fork** [S] | not in the official framework |
| S12 | **TAS record and playback**: fabric input capture, log kept by the HPS | fabric + HPS | after v3.0.0 | no framework support to build on; needs a deterministic power-on |
| S13 | **Read-only Lua** on the HPS over the DDR3 mirror | HPS | not planned | needs `Main_MiSTer` changes; no per-instruction hooks are possible |
| S14 | **Debugger**: fabric trace and breakpoints into a DDR3 buffer | fabric + DDR3 | not planned | a large RTL effort with the OSD as its only UI |
| -- | **Run-ahead, rollback netplay** | -- | **infeasible** | both re-simulate several frames inside one; fixed-speed fabric cannot, and no MiSTer core does [S] |
| -- | **HD graphics packs, HD audio track replacement** | -- | **not recommended** | no FPGA precedent; the scaler cannot composite per tile; HD audio would need a new HPS decoder path |

**Open facts, read at Strand A:** the SS1's SDRAM part number and chip topology
(only "128MB BGA SDRAM" is published [V
<https://retroremake.co/pages/superstation%e1%b5%92%e2%81%bf%e1%b5%89>]), and its
DDR3 size. The SS1 supports a single SDRAM only [V
<http://nerdlypleasures.blogspot.com/2026/07/the-superstation-one-is-this-one-fpga.html>].
Since v2.9.0 the off-die build refuses boards under 64 MB: the controller drives
ten column bits and a 32 MB board's 256 Mbit part has nine.

## Strand A — platform, before the core is touched

Executes `RustyNES_MiSTer/docs/HARDWARE_TESTING.md` §2.

- **Reflash the SD card even on a new unit.** Factory cards ship with overlapping
  partitions that corrupt silently.
- `update_all.sh`; replace the stock INIs and `yc.txt`; **record the four DIP
  switches**.
- USB-C PD at **9 V / 3 A**. A marginal supply mimics SDRAM corruption.
- **The baseline smoke rows on the stock `NES_MiSTer` core, not ours.** A platform
  fault found after our core is loaded costs a day in the wrong repository.
- ***(new)* Two reads the plan now depends on.** (1) Does a DE10-Nano-targeted
  `.rbf` load at all? Two spec sources name the SS1's FPGA as a Cyclone V SX
  5CSXFC6D6F31 against this build's 5CSEBA6U23I7; the stock core loading is the
  answer. (2) **The SDRAM part number**, photographed. v2.8.4's SDC constraints were
  written for the documented AS4C32M16SB and marked provisional pending this read.

The corpus goes in two places: `games/NES/tests/` for the stock core and
`games/RustyNES/tests/` for ours. Same bytes.

## Strand B — first boot, nine steps, stop at the first failure

`bringup.md` orders the steps so that what one *rules out* is worth more than
what it confirms. Copy the **v2.9.2 release-candidate `.rbf`** to `_Console/`
*(corrected: the Shakedown plan named `RustyNES_20260919.rbf`)*.

The headline build is **on-die** (`USE_SDRAM_CART = 1'b0`). The SDRAM controller is
still instantiated and still runs its power-up and refresh, so a wiring or phase
defect can show even though the cart path reads nothing from it.

Step 7, "a picture, and it is the right picture", needs the most care: commercial
titles already render byte-identically to the oracle over all 61,440 pixels **in
simulation**, so a wrong picture there is a palette or video-path question, not a
rendering one.

**The off-die build** repeats this strand after MemTest passes.

## Strand C — the four properties no gate can reach

| property | instrument | note |
|---|---|---|
| palette | colour-bar capture against the FBX Smooth reference | the PPU gates compare the **pre-palette** index, deliberately |
| video timing constants | H/V on a scope | **a display that syncs is not proof the numbers are right** |
| audio absolute level | DC-coupled, resting level in silence | the `FRAC` 8→15 fix for a +127 offset was never gated |
| band-limiting | listen, and capture | absent by design; expect harsher treble. **A known difference, not a defect** |

## Strand D — batteries, read back as bytes

- **blargg and `instr_test-v5`** report through `$6000-$6003`, the cartridge save
  window, so `tools/run_battery.sh` reads them back unattended.
- **AccuracyCoin reads back as bytes** *(corrected: the Shakedown plan said it
  "stays a screen")*. v2.6.22 built the `$6000` mirror ROM
  (`tests/roms/AccuracyCoin/mirror/`) and its simulation control, so
  `accuracycoin_status <golden>.ram.bin sav:<file>` diffs the 144 scored entries.
  `run_battery.sh` reports that ROM as `vector-not-verdict`, which is correct.
- **Tier 2**: A/B against stock `NES_MiSTer` on the same silicon.
- **Tier 4**: a soak of 4+ hours on passive cooling, including save and load across
  a power cycle, which is `T-MISTER-SAVE`'s hardware acceptance.

## Strand E — the two tickets a board unblocks

- **`T-MISTER-DIRECTVIDEO`**: the acceptance is a picture on a CRT. The SS1's
  integrated ADV7125 and FPGA YC encoder make it testable without an I/O board.
- **`T-MISTER-MENUMASK`**: whether the greyed OSD entry renders. Eyes on an OSD.

## Strand F — re-measure the incumbent, then decide

1. **Build the current `NES_MiSTer` and run the same AccuracyCoin build against
   it.** Never compare across catalog versions.
2. **Write the feature delta honestly.** The incumbent has save states, cheats,
   palettes, Four Score, Zapper and PAL.
3. **Then decide** whether to submit. If accuracy no longer separates the cores,
   the argument that can is the co-simulation apparatus.

What may be said about the incumbent's public release history is governed by
[ADR 0040](../../docs/adr/0040-public-release-metadata-is-outside-the-reference-firewall.md).

## Risks

- **A platform fault read as a core fault.** Mitigated by Strand A on the stock core.
- **The device question has the wrong answer.** If the SS1 does not load a
  5CSEBA6U23I7 bitstream, v3.0.0 needs a second Quartus target, a second seed sweep
  and a second set of timing reads. That is the most expensive surprise available,
  and why it is the first thing Strand A reads.
- **The four properties are measured for the first time.** A palette or timing
  correction is an RTL change, which re-opens the seed sweep and the bitstream, so
  budget for a second compile cycle.
- **Declined as a duplicate** at submission. Accepted in writing since v2.4.1;
  Retro Remake is a planned second home.
- **`misterfpga.org` returns HTTP 403 to automated fetching**; its forum threads
  need reading by hand.
