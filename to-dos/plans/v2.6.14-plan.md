# v2.6.14 "Docket" — the submission checklist becomes auditable

## The problem, as a measurement

v2.7.0 is the submission: an email to `newcores@misterfpga.org` with a link to
`RustyNES_MiSTer`. `to-dos/mister/contribution-checklist.md` is the list that
says whether the repository is ready, and it has **16 unticked boxes** of 30.

The question this version asks is not "how many can we tick". It is **which of
them are already true and merely unticked, which are false, and which are
blocked** -- and v2.6.12 is the precedent: annotating nine `T-MISTER-*` tickets
with a blocker apiece turned "none of these landed" into a measurement, and the
finding was that **not one was blocked on effort**.

A checklist whose boxes are prose cannot be audited. An ordering can, a count
can, and a per-item verdict can.

## What opens the version: a claim I shipped that is false

While answering a CodeRabbit finding on the v2.6.13 PR -- "the plan says a
five-mapper core without saying which five" -- I wrote:

> the five-family core rung 7 shipped (NROM, UxROM, CNROM, AxROM, MMC3 -- MMC1
> is the sixth approved family and is not yet implemented)

**Both halves are wrong**, and one command shows it:

- `rtl/cart/cart.sv` decodes mapper **1** at three sites (`mmc1_prg`,
  `mmc1_chr`, the PRG-RAM enable), and `tb/regress.sh` registers a
  `mapper1mmc1063` gate that has been green since rung 7 opened. **MMC1 is
  implemented.**
- The five families rung 7 landed are **UxROM, CNROM, AxROM, MMC1 and MMC3** --
  its own doc title says so -- **on top of** NROM, which landed at v2.6.3. NROM
  is not one of the five.

So the approved six-family scope is **complete**, not five-sixths done.

I asserted a fact about the code from memory rather than checking it, inside a
reply that was itself correcting somebody else's reading of the same line. It
shipped in v2.6.13's plan document and in a public review reply. It is retracted
here rather than edited away, because the correction is the finding: **the
project's own rule is to verify a reviewer's claim before writing the fix, and
the failure mode is verifying THEIR claim and then not verifying MINE.**

## Deliverable

1. **The retraction**, everywhere the claim propagated, plus a follow-up comment
   on the resolved review thread so the public record is corrected too.
2. **A per-item verdict on all 17 unticked boxes**: already true (with the
   evidence and the release that made it so), false (with what would make it
   true), or blocked (with the named blocker, in the v2.6.12 shape).
3. **The `.rbf` naming divergence resolved or deliberately deferred**, from
   `Distribution_MiSTer`'s own source rather than from the wiki prose or from
   memory. This is the one checklist item that is a genuine incompatibility
   rather than a missing tick: MiSTer's updater selects the newest bitstream by
   the **date** in the filename, and this project ships a **version**-named one.
4. **Whatever the audit finds.** On the v2.6.12 precedent, that is the part
   worth doing the work for.

## The gate

| # | criterion | how it is measured |
|---|---|---|
| 1 | the MMC1 claim is retracted where it was made | `grep` across both repositories returns **zero** sites still asserting it; the resolved review thread carries a correction |
| 2 | **every checklist item carries a verdict** | a standing audit walks `contribution-checklist.md` and fails unless each box is either ticked **with a release tag** or unticked **with a named blocker**; demonstrated to fail by mutation |
| 3 | the naming rule is stated from its own source | the selection mechanism is quoted from `Distribution_MiSTer`, with the file and line, not from the wiki page that paraphrases it |
| 4 | the oracle is untouched | no chip crate changes, so AccuracyCoin 141/141 (RAM decoder) and nestest 0-diff hold by construction -- verified anyway |
| 5 | the ladder still passes | 142 of 142 on the die; the off-die configuration re-measured if any RTL changes |

Criterion 2 is the one with teeth, and it is deliberately the same shape as the
gate v2.6.11 added for release-lead ordering: **prose cannot be audited, so make
the structure carry the claim.**

## Risks

1. **The audit finds most items already true, and the release is thin.** Named
   up front rather than discovered. Mitigations: the naming work is real
   regardless, and the v2.6.12 precedent says annotating a list of blockers is
   where the findings come from. If the audit genuinely produces nothing, that
   is a publishable result and the release says so instead of padding.
2. **A checklist item is ticked on evidence that has expired.** The whole point
   of v2.6.9's finding: an exclusion's stated reason stops being true and nobody
   re-reads it. The audit must re-measure ticked items too, not only unticked
   ones.
3. **Rung 6 stays open.** No DE10-Nano and no SuperStation One are attached to
   this machine. Four checklist items need one and cannot be closed here; they
   get blockers, not ticks.

## Out of scope

- **The slot-scheduled arbiter**, and with it the off-die flip. It is named in
  v2.6.13's documents as what makes the CPU's deadline provable, and it stays
  named: an off-die core cannot run at all without the SDRAM add-on, so the flip
  needs a fallback for a missing board before it is worth having, and that is a
  design change rather than a checklist item.
- **Hardware bring-up.** No board.
- **Any new mapper family.** The approved scope is complete, which is the first
  thing this version establishes.
