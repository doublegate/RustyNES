# v2.6.12 — the bitstream is an NROM-only console

Rung 7 landed five mapper families and 142 co-simulation gates verify them. The
integration layer that turns that RTL into a bitstream was never told.

## Measured before planning

Three `nes_top` inputs are **not connected** by `rtl/emu.sv`. Quartus says so, in
a `Port Connectivity Checks: "emu:emu|nes_top:u_nes"` table, and ties them to
ground:

```text
; cart_mapper         ; Input ; Warning ; Declared by entity but not connected by
;                     ;       ;         ; instance. ... the port will be connected to GND.
; cart_prg_16k_banks  ; Input ; Warning ; (same)
; cart_chr_8k_banks   ; Input ; Warning ; (same)
```

In the shipped v2.6.11 bitstream that means:

| tied to GND | consequence in silicon |
|---|---|
| `cart_mapper = 0` | **mapper 0 for every cartridge**, whatever its header says |
| `cart_prg_16k_banks = 0` | `prg_8k_count = 0` -> `prg_bank_sel = 0` -> an **8 KiB PRG window**, no banking |
| `cart_chr_8k_banks = 0` | `chr_is_ram = 1`, `chr_1k_count = 8` -> **8 KiB CHR** |

and the fitter's own RAM summary agrees exactly:

| memory | declared | **implemented** |
|---|---|---|
| `prg` | 262,144 x 8 = 256 KiB | **65,536 bits = 8 KiB** |
| `chr` | 131,072 x 8 = 128 KiB | **65,536 bits = 8 KiB** |
| `prg_ram` | 8,192 x 8 = 8 KiB | 65,536 bits = 8 KiB (correct) |
| work RAM | 2,048 x 8 = 2 KiB | 16,384 bits = 2 KiB (correct) |

The two arrays whose size depends on a tied-off input are the two that collapsed.
The two that do not are correct. That is the mechanism, not a coincidence.

**`emu.sv` states it in its own OSD string**, and did so honestly when it was
written at v2.6.6:

```systemverilog
"I,Cartridge loaded,Unsupported mapper - this core is NROM only;",
```

It parses the header's mapper number and PRG size, uses them to gate reset and
raise that message, and never forwards them. v2.6.9 added MMC1, UxROM, CNROM,
MMC3 and AxROM to `cart.sv`; nothing updated the layer above it.

**Two of the six titles in v2.6.11's montage are larger than the fitted
cartridge** -- *Bad Dudes* is 128 KiB CHR and *Battletoads & Double Dragon* is
256 KiB PRG. They render under Verilator, which builds the full array from the
parameters. The bitstream does not contain it.

## Why nothing caught it

- **Simulation cannot.** `tb/cpu6502_cosim.sv` drives `mapper`, `prg_16k_banks`
  and `chr_8k_banks` directly, so every one of the 142 gates exercises a
  correctly-configured cartridge. The tie-off exists only in the path
  Verilator never takes.
- **Quartus did**, three times, in plain language.
- **`tb/quartus_clean.py` did not, and was right about what it checks.** Its
  contract is to fail when a message **cites a path** under `rtl/` or `tb/`.
  These warnings live in a table that cites an INSTANCE path
  (`emu:emu|nes_top:u_nes`) and no file at all: **0 of 125 carry a file path.**

## The deliverable

1. **Connect the three ports**, so the header the loader already parses reaches
   the cartridge.
2. **A port-connectivity gate.** `quartus_clean.py` gains a second contract: no
   port of an instance under our own hierarchy may be left unconnected. Keyed on
   the instance path, because that is what the table carries.
3. **A memory-size gate.** Assert that each cartridge array's IMPLEMENTED bits
   equal its declared size. This is the check that did not exist and the one
   that states the property directly rather than by proxy.
4. **Re-qualify v2.6.11's montage claim** the way "reproducible" was qualified:
   true of the RTL, and not of the bitstream until this lands.

## Explicitly NOT in scope

- **The SDRAM controller.** Connecting the ports makes the declared 392 KiB real,
  which fits on-chip; it does not make a 512 KiB MMC3 game fit. That is the next
  item and it is a different piece of work.
- **Rung 6 / hardware.** No board is attached.
- **The v2.7.0 submission.** Gated on hardware.

## Risks

1. **The full cartridge may not fit.** 392 KiB is 3,211,264 bits against
   5,662,720 on the device, and the framework already uses some. If it does not
   fit, the finding is unchanged and the remedy moves to SDRAM sooner.
2. **Timing may move.** Three real inputs replace three constants, so the
   banking logic stops being constant-folded. Expect the fit to change and
   re-measure rather than assume; the seed sweep is the existing tool.


## Added mid-cycle, at the maintainer's request

Two items were not in this plan's deliverable and are the larger half of what
shipped. Both are recorded here with their outcomes rather than left to the
CHANGELOG, because both ended somewhere the plan would not have predicted.

### The nine `T-MISTER-*` tickets: "close them before landing this"

**Outcome: none closed, and that is a measurement rather than a refusal.**
Annotating each with a blocker and an unblock condition established that **not
one of the nine is blocked on effort** -- four are deferred to v2.8+ by the
approved v2.7.0 plan (which names Four Score and Zapper in its out-of-scope
list, and whose peripheral-input-device class covers the Vaus paddle and the
Family BASIC keyboard), three cannot be verified by anything in this
repository, and two wait on subsystems that do not exist. So the list is **the
rung-6 agenda, not a backlog**.

`T-MISTER-SAVE` is what established it, because it was attempted. Its entry
claimed the implementation was unblocked and only the verification was rung 6;
that split does not survive `sys/hps_io.sv`. There is no OSD-close signal to
flush on, `hps_io.sv:152` says `ioctl_upload_req` "must be supported on HPS
side for specific core", and both routes terminate in `hps_io`, which the
testbench does not instantiate. **A save path written now would ship with zero
evidence.** The attempt is preserved as a patch and not committed; `cart.sv`
deliberately carries no save port, because `tb/check_pins.py` would have had to
be lied to in order to accept an unconnected one.

The tickets were also filed under a heading reading "cases where the DUT is
measurably more accurate than RustyNES itself". None of them is; corrected in
place.

### The gate this release added had the defect it was written to close

Raised in review, and **worse than the report**. The claim was that
`check_pins.py` *could* pass when the lint had not run. The non-zero control
written to close that failed on its first CI run, and the **successful** run
before it reads `check_pins: 0 PINMISSING warning(s) examined` / `PASS`.

**The gate had been inert on CI since the moment it was added, in this
release, while reporting PASS on every run.** Locally the same command examines
57. Two causes, both Verilator version skew between CI's 5.020 and the local
5.050, running in **opposite** directions: the error line loses its
`-MODMISSING` suffix on 5.020 (so the allowlist refused a *healthy* run), and
the warning reads "Cell has missing pin" rather than "Instance has missing pin"
(so the regex matched nothing). CI now reports **57 examined**.

The reusable rule: **every counting gate needs a non-zero control**, and the
message *text* is not a contract -- the warning *code* is.

### The release tooling deleted a release while cutting this one

`bump_release.py`'s `PERIOD` shape assumes a period *ends* the statement. True
of `OVERVIEW.md`, false of `SECURITY.md`, where it separates the head from a
`Built on ...` chain -- so the head was swapped and **v2.6.11 left absent**.
Split into `PERIOD` / `PERIOD_CHAIN` with four selftests; collapsing it back
fails three. Two further anchors needed hand correction and **the v2.6.11 chain
gates named both**, which is that gate catching a real skip in each of its two
releases.
