# v2.6.20 "Telltale" — the counter had no reader, and the picture had no gate

> Covers exactly one release. A telltale is an instrument that makes a state
> visible which is otherwise only inferable — a ribbon on a shroud showing the
> wind. Both halves of this release are telltales: a counter that existed and
> was never read, and a rendered consequence that was never compared.

## What opens the version

v2.6.19 shipped the DUT at **148 of 149** AccuracyCoin entries, with
`Misaligned OAM2 Address` ($0495) the single divergence, and the retrospective
audit closed leaving two findings explicitly open, one of them reachable:
**no gate writes CHR-RAM while rendering is enabled.**

v2.7.0 is the submission and is blocked on hardware, so this release takes what
is reachable without a board.

## Strand A — the counter becomes observable

### The instrument came first, and it cost one byte

The entry is the **last** catalog row, so the full battery is 134 M cycles
(~35 min) per attempt. No sub-test ROM existed for it, and the corpus fixture
named `sprite-eval-misaligned-oam.nes` is a **different** test ($045A).

`build_sub_test_rom.py` injects the suite and test indices as plain immediates,
and they survive into the assembled binary. In
`advanced-sprite-eval-frozen-oam2-increment.nes` (suite 21, test 2) they sit at
file offset `0x10AA` (`A0 15` = `LDY #21`) and `0x10B4` (`A2 02` = `LDX #2`).
The catalog orders suite 21 as Sprites-On-Scanline-0 / Stale Sprite Shift Regs /
Frozen OAM2 Increment / **Misaligned OAM2 Address**, so test index **3** is the
entry — confirmed by two independent sources before the patch
(`BUILD-PROVENANCE.tsv` records the base ROM as suite 21 test 2, and the
catalog's own row order).

One byte, `0x02` → `0x03`. `validate_sub_test_rom` reports `$0495` settling at
**Pass** on frame 82. **35 minutes became 30 seconds**, which is what made two
experiments affordable instead of one.

### What was actually wrong — and the claim this retracts

v2.6.19's own RTL comment said *"making the fetch read `oam2_fetch_addr`
directly is the remaining work"*. **That is wrong**, and the four sprite-fetch
read sites must stay dot-derived:

* the oracle passes $0495 while its `fetch_sprite_tile` still indexes `slot * 4`;
* those sites feed the pixel pipeline and have no path to `oam_bus`, which is
  the only thing `$2004` can return while rendering; and
* the two indices are different **sequences** over the same 32 bytes — over
  slot 0 the counter reads `0,0,1,1,2,2,3,3` against the dot-derived
  `0,1,2,3,3,3,3,3` — so substituting would move every sprite on screen.

The defect was that `oam2_fetch_addr` was **write-only**. `$2004`'s post-fetch
rest value was a hardcoded `sec_oam[0]`.

### Two changes, and the second was found by a byte

**One-shot at documented dot 321** (`dot == 9'd320` raw), assigning
`oam_bus <= sec_oam[oam2_addr_next]`. `oam2_addr_next` is a combinational
next-value view, needed because `oam_bus` uses the documented-minus-one
convention while the counter block uses documented dots — reading the register
at that edge yields its pre-320 value (31) and would put sprite 7's X on `$2004`
for dots 321-340 of every line of every game. In the ordinary case `31 + 1 = 0`,
so every fully-rendered scanline is byte-identical.

That alone did **not** close it: the DUT read `$A3`. The oracle's own v2.6.18
study had already tabulated that byte — OAM2 index `$17`, **exactly one
increment short** of the expected `$18` — so the second change was named by the
measurement rather than searched for.

**The increment window returns to 256**, which v2.6.19 had narrowed to 258. That
narrowing was review-driven and wrong: the 33rd candidate is suppressed by
`!oam2_overflowed`, so both windows perform 32 increments in a complete pass and
differ only in **phase**. v2.6.19's comment predicted its own blind spot —
*"mostly invisible … nothing downstream can tell 318 from 320"* — and it was
invisible because nothing read the counter.

With both: **`$0495` both Pass, and `$0050` = `0x06` on both sides**, so the
gate passes on the right byte rather than by coincidence.

## Strand B — the CHR-write gate

The gap is not missing stimulus: `chr_wr` fires constantly (four of six rung-7
mapper ROMs are CHR-RAM). It is that **no CHR-RAM ROM's consequence is rendered
and compared** — all three framebuffer gates are CHR-ROM by construction, and
the rung-7 ROMs never enable rendering.

A new `mkrom.py` program writes patterns into CHR-RAM through `$2007`, then
renders them. Live control: `chr_wr assertions: N` must be non-zero.

## Strand C — the submission checklist

Untouched since v2.6.16 across three releases. `.srf` is ticked (v2.6.19 adopted
it, and the box's own plan said "the next release that rebuilds the bitstream").
Two count-bearing boxes were re-measured and are **correct** — both looked
expired under a narrower `find` than the one that wrote them, which is recorded
so a third audit does not repeat it. All nine remaining unticked boxes already
carry an explicit blocker.

## Out of scope

Rung 6 and the submission (no board) · the SDRAM CAS dispute · the remaining
~169 mappers · egui/wgpu (one upstream release away).
