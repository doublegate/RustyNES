# v2.6.8 "Arrears" — the gates v2.6.7 fixed, and never widened

Arrears are debts carried forward: obligations that were correctly deferred and
then went on being deferred after the reason expired. Every item in this release
is one. v2.6.7 fixed real defects and then left the gates narrowed *around* the
places it had fixed, because narrowing them was the right call at the time and
nothing re-opened the question afterwards.

**A deny list is an assertion about the thing under test.** Changing the thing
under test re-opens it. v2.6.7 changed both the DUT (the `$4017` interrupt-clear
split) and the harness (the `Observable` completed at end-of-cycle, `nmi_line`
wired to the effective line rather than the testbench's injection pin) — and no
exclusion was re-measured against either.

## What v2.6.7 closed, and what it left

**Closed:** the bitstream published and reproducible (`md5 378405a2…`, clean ==
incremental); the work RAM moved to block memory (30,265 -> 21,865 ALMs, timing
-0.639 -> +0.130 ns); caveat C2; caveat C6 in the oracle.

**Left, and this release's whole subject:**

- **The nestest gate compares 265,000 cycles against a 5,062,688-cycle golden.**
  The cap was correct when written — it sat just short of C6's first divergence,
  named rather than hidden. C6 is now fixed and the cap is pure arrears.
- **Six goldens on `CKPT_DENY`**, none re-measured after the fixes that were
  aimed at four of them.
- **`nestest` has no nine-field comparison at all** — it uses `nestest-gate`, so
  the `cpu-bus-gate` auto-attach cannot reach it, and it is absent from the
  explicit checkpoint loop's 35 entries.

## Measured before planning, not assumed

| question | measurement |
|---|---|
| is C6 actually closed? | **yes** — all **5,062,680** cycles match on `pc`, `bus_addr`, `bus_data`, `bus_access` |
| do the denied streams still differ? | **4 of 6 now PASS**: `irqlat048`, `ppuvbl023`, `ppuvbl024`, `ppuvbl025` |
| which still differ? | `apuconflict039` (checkpoint 8 of 88, window (32775, 36871]) and `ppuoamcorrupt052` (real hash divergence) |
| does nestest raise an NMI? | **yes** — `nmi_line` set on **3,592** cycles, `irq_line_at_low` on **62,516** |
| is a board attached? | **no** — no USB-Blaster on the USB bus, no serial device, no removable block device, no MiSTer mount |

**That fourth row retires caveat C4.** C4 states the checkpoint gate "cannot
catch an `nmi_line` defect, because not one gated golden ever raises an NMI".
The stimulus exists, its checkpoint golden exists (1,237 checkpoints), and it is
simply not wired in.

## The deliverable

1. **Raise the nestest gate to the golden's full depth** — 265,000 ->
   5,062,688, a **19x** increase on the project's deepest stimulus, and correct
   `docs/rung3-ppu.md`'s claim plus the now-stale C6 section.
2. **Give nestest a nine-field checkpoint comparison**, which closes C4.
3. **Retire the four `CKPT_DENY` entries that now pass**, and restate the reason
   for the two that remain from a current measurement rather than an old note.
4. ~~Fix a ROM-path resolution defect in `regress.sh`.~~ **REFUTED, and
   recorded rather than deleted**, because the refutation is the useful part.
   Re-measuring `ppuoamcorrupt052` died with
   `cannot open ../RustyNES_MiSTer/tb/roms/...`, which read as a latent harness
   bug: the manifest's relative path exists from the repo root but not from
   `tb/`, where `make -C tb` runs. It is not a harness bug. `regress.sh` does
   `cd "$(dirname "$0")"` on line 29 and therefore validates from **`tb/`**,
   where the relative path correctly fails and the absolute fallback correctly
   triggers. The defect was in the ad-hoc measurement script written for this
   release, which ran from the repo root and resolved the path *by coincidence*
   — `$_REPO_ROOT/../RustyNES_MiSTer/tb/roms/` and `$_REPO_ROOT/tb/roms/` are
   the same directory. Verified from both working directories before the
   "fix" was written.

## The gate

Every clause measurable, and none satisfiable by a vacuous result:

| # | criterion | how it is measured |
|---|---|---|
| 1 | nestest runs to the golden's depth | the gate compares **5,062,680** cycles with 0 divergences, and `NESTEST_CYCLES`'s default is derived from the golden rather than a literal that can drift from it |
| 2 | nestest is compared on **nine** fields | `ckpt:nestest` appears in `regress.sh` output and passes over **1,237** checkpoints |
| 3 | **C4 is closed by demonstration, not by argument** | an `nmi_line` mutation, previously NOT CAUGHT for want of a stimulus, is now **CAUGHT**. A NOT CAUGHT here is classified against the five known meanings and remediated, never reported |
| 4 | the deny list is current | it contains exactly the entries that were measured failing **in this release**, each with its divergence named; the four removed are each shown passing |
| 5 | no regression | `./tb/regress.sh` no worse than v2.6.7's **123 passed / 0 failed / 0 skipped**, and the comparison count RISES |
| 6 | the oracle is untouched, or verified | if no chip crate changes, AccuracyCoin 141/141 holds by construction and is re-run anyway; if one does, it is VERIFIED |

Clause 3 is the one that matters. Clauses 1, 2 and 4 widen coverage, and widening
coverage without demonstrating that the wider gate can FAIL is how this project
has previously shipped a check that tested nothing.

## Risks

1. **A widened gate finds a real defect.** That is the point, and it reshapes the
   release from packaging into accuracy work. Expected rather than feared: the
   last two coverage widenings each found one.
2. **The `nmi_line` mutation comes back NOT CAUGHT for a new reason.** Five
   meanings are catalogued; a sixth would itself be the finding.
3. **Suite runtime.** Adding a 5 M-cycle checkpoint comparison costs simulation
   time; it rides the same DUT invocation as the bus gate, so the marginal cost
   should be near zero — to be measured, not assumed.

## Explicitly out of scope

- **Hardware bring-up.** Rung 6 stays open; no board, confirmed by checking.
  It moves to the first release after one exists.
- **`apuconflict039` and `ppuoamcorrupt052`.** Both genuinely differ. Each needs
  its own diagnosis and neither is a gate-widening task.
- **The SDRAM controller and the mapper rung.** Unchanged from v2.6.7.
