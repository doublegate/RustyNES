# Ecosystem horizon for the v3.1 to v4.0 roadmap (2026-10-07 to about 2027-10)

Read-only research, gathered 2026-10-06. Every claim carries a source. Labels:

- **[V]**: verified against a primary source in this session.
- **[S]**: from a secondary source (press or blog) and not checked against the primary.
- **[I]**: my inference from a published pattern or cadence. It is not an announcement.
- **[U]**: could not be verified.

No source of any other NES emulator or NES HDL was read. The repo was read only for context.

---

## 0. Headline findings (the five that change plans)

1. **The libretro build image stopped passing `-C ar` on 2026-09-03.** RustyNES's whole reason for holding the buildbot on 1.96.0 may already be gone. [V]
   - Commit `841f3619` in `libretro-infrastructure/libretro-build-rust` is titled "Remove -C usage as no longer supported by rust". Commit `2956e008` followed it, and image pipeline `674682c8` was green on 2026-09-23.
   - The Apple `CARGO_TARGET_*_RUSTFLAGS` now hold only properly separated `-C link-arg=...` flags.
   - `rust-toolchain.toml`, AGENTS.md and `docs/agents/libretro.md` (dated 2026-10-06) still describe the image as injecting `-Car=...`.
   - Confirm it by reading one Apple job log from the next RustyNES buildbot pipeline before unpinning.
2. **Android developer verification takes effect in 2027.** GitHub-sideload distribution is affected directly. [V]
   - Enforcement started on 2026-09-30 in Brazil, Indonesia, Singapore and Thailand, on certified devices running Android 7+.
   - The global rollout is "2027 and beyond".
   - The free "limited distribution" account covers only 20 devices. Wider distribution needs Android Developer Console registration with government ID.
   - Users can still install unverified apps through an "advanced flow".
3. **UniFFI main has merged zero-copy `&mut [u8]` (PR #2940), but it is not released yet.** [V] It unblocks MOB-06 at UniFFI 0.33, probably around Q4 2026 or Q1 2027 [I].
4. **AccuracyCoin upstream added 2 new tests on 2026-10-05** (commit `9fc47e06`). There are also 6 other commits since RustyNES's last re-sync on 2026-09-19 (#528). [V] Those include the fix "Fixed an issue with Misaligned OAM Behavior". So "144/144" is now 144 out of a larger catalog.
5. **Android 17 (API 37) adds a mandatory `ACCESS_LOCAL_NETWORK` runtime permission** for apps that target it. [V] Android LAN netplay breaks silently unless the app requests it. No Play deadline for API 37 has been announced yet [V]. By the annual pattern it will be about 2027-08-31 [I].

### Stabilisations since 1.96 that are relevant here [V]

- **1.97:** `isolate_highest_one`, `isolate_lowest_one`, `highest_one`, `lowest_one` and `bit_width` on integers and `NonZero`; const `char::is_control`.
- **1.98:**
  - Algebraic float ops (`f32::algebraic_add`, `algebraic_mul` and the rest). These *permit* reassociation, so results can vary with optimisation. **Never use them in the deterministic core or BLEP synthesis.**
  - `format_into` / `NumBuffer`; `Atomic::from_mut`.
  - `std::range::legacy`, groundwork for the range-type edition change.
- **1.99:**
  - C-variadic function definitions (`extern "C" fn(..., args: ...)` with `core::ffi::VaList`).
  - `Vec::into_parts` / `from_parts`; `Box::into_non_null` / `from_non_null`; `size_of_val_raw` / `align_of_val_raw`.
  - `String::from_utf8_lossy_owned`; `std::fs::set_times`.
  - C-variadic definitions matter only if the RA or libretro log callbacks are ever implemented on the Rust side. They take a C `va_list`.

### Portable SIMD (`core::simd`)

Still **nightly-only** as of 2026 [S]. It is not in the 2026 Project Goals list [V].

- Do not plan around it in the v3.x to v4.0 window.
- Per-target `core::arch` intrinsics remain the only stable route. The repo has already measured and rejected the SIMD blitter.

### Target-tier changes that touch RustyNES

- **`i686-pc-windows-msvc` loses host tools** (RFC 3999, written 2026-07-02 [S]). The blog post "Demoting i686 Windows targets to std-only" appeared on 2026-10-02 [V, title only; the post URL 404'd].
  - It is std-only from here on, so cross-compiling *to* it still works.
  - `i686-pc-windows-gnu` was already Tier 2 from 1.88 [V].
  - Relevance: the libretro buildbot's Windows i686 job (added in #554) and any 32-bit Windows desktop binary.
- **`x86_64-apple-darwin` was demoted to Tier 2** (RFC 3841) [S]. Intel-Mac binaries still build but get less testing.

### Next edition (Rust 2027)

Nothing official has been announced. [V]

- rustc `main` (`compiler/rustc_span/src/edition.rs`, fetched 2026-10-06) has `Edition2015/2018/2021/2024/EditionFuture` and **no `Edition2027` variant**. `LATEST_STABLE_EDITION = Edition2024`.
- The 2026 Project Goals have no "Rust 2027 edition" goal. The closest is "Evolving the standard library API across editions" [V].
- Community discussion (internals, 2025) says 2027 happens only if enough breaking work, such as the RFC-accepted range-type fix, is ready. Otherwise the edition slips to 2028 or later [S].
- The 2024 edition existed as an unstable nightly edition for well over a year before it shipped in 1.85 [I]. By that precedent, **a 2027 edition shipping before late 2027 is unlikely**, and certainly not inside a v4.0 window that ends around Q3 2027 [I].

### Other 2026 project goals worth watching [V for names]

`build-std`, "Stabilize cargo-script", "Const Traits", "Stabilize never type (`!`)", "Stabilize the next-generation trait solver", "Wasm Components" (a `wasm32-wasip3` target), and "Stabilize MemorySanitizer and ThreadSanitizer Support".

- MSan and TSan would strengthen the fuzz and `emu-thread` gates if they stabilise.
- `build-std` would matter to the tvOS and `thumbv7em` jobs.

### MSRV move?

Nothing in 1.97 to 1.99 is needed by the core. Library MSRVs are the real driver:

- egui 0.36.2 and wgpu 30 both declare `rust-version = "1.95"` [V, upstream `Cargo.toml`].
- winit 0.31 beta declares 1.86 [S, lib.rs].

The binding constraint is the libretro buildbot pin. See section 3.

**Implication for RustyNES:**
- Keep the workspace pin tracking stable on a cadence, for example every second stable, in a MINOR release.
- Add an explicit "no algebraic float ops in chip crates" lint or review rule.
- Do not schedule a Rust 2027 edition migration before v4.0. Re-check rustc for an `Edition2027` variant in about Q2 2027, and if one lands, plan the migration as a post-v4.0 MINOR.

## 3. libretro / RetroArch

### The build image and `-C ar` [V]

- The image repository is `git.libretro.com/libretro-infrastructure/libretro-build-rust` (files: `Dockerfile`, `Dockerfile.apple`, `Dockerfile.android`, `.gitlab-ci.yml`). The master pipeline builds `Dockerfile` and pushes it to `$CI_REGISTRY_IMAGE`.
- **2026-09-03, `841f3619` "Remove -C usage as no longer supported by rust":** replaced the `-Car=<path>,Clink-arg=...` values with `CARGO_TARGET_*_AR`.
- **Then `2956e008` "Attempt #3 to fix rust":** removed the `_AR` variables and set clean values:
  - macOS: `CARGO_TARGET_{X86_64,AARCH64}_APPLE_DARWIN_RUSTFLAGS="-C link-arg=-undefined -C link-arg=dynamic_lookup"`
  - iOS and tvOS: the same, plus `-C link-arg=-rpath -C link-arg=<lib>`
- Later commits (2026-09-12 to 09-23):
  - added `rustup` targets `aarch64-unknown-linux-gnu`, `i686-unknown-linux-gnu` and `i686-pc-windows-gnu`;
  - added an i686 llvm-mingw toolchain (`CARGO_TARGET_I686_PC_WINDOWS_GNU_LINKER` / `_RUSTFLAGS="-L $LLVM_MINGW_STUB"`);
  - added a `+nightly i686-pc-windows-gnu`;
  - bumped `cargo-ndk` to 4.1.2.
- The latest master pipeline (`674682c8`, 2026-09-23) **succeeded**, so the published `:latest` image carries the fix.
- Caveats:
  - Whether RustyNES's buildbot jobs pull that `:latest` has not been confirmed from a job log [U].
  - Those `RUSTFLAGS` now *reach the linker*. Under the old `-Car=` token they never did, as `docs/agents/libretro.md` explains. So an Apple job's link line changes even on 1.96. Watch the first pipeline.
- The `rust-apple.yml` template still uses `cargo +nightly` for tvOS and sets no `RUSTFLAGS` [V]. RustyNES already overrides that.
- **RetroArch releases:** the last tagged release is still **v1.22.2 (2025-11-20)** [V, GitHub API], although `libretro.h` changes continue on master.

### Core options

The RustyNES core still declares options through legacy `RETRO_ENVIRONMENT_SET_VARIABLES` (v0) [V, `crates/rustynes-libretro/src/lib.rs`].

- `SET_CORE_OPTIONS_V2` (with `GET_CORE_OPTIONS_VERSION` as a fallback) adds categories, sublabels, per-value labels and translations. It has been in `libretro.h` since 2021, and the libretro docs page encourages it [V for the header contents; docs page not re-fetched].

| Date | API | Relevance |
|---|---|---|
| 2025-09-11 | `GET_TARGET_SAMPLE_RATE` (optional) | Could let BLEP synthesis output at the frontend's rate and skip a resample. |
| 2026-02-05 | ROM memory type | Memory descriptors; RA tooling. |
| 2026-06-29 | `GET_AUDIO_SAMPLE_BATCH_FLOAT` (float output negotiation) | The mixer is float internally. This avoids an i16 quantisation step. |

**Implication for RustyNES:**
- **Early in v3.1:** re-test the buildbot on 1.99, using a branch pipeline with `RUSTUP_TOOLCHAIN` removed. If all four Apple jobs link, retire the 1.96 split (`.gitlab-ci.yml`, the seven `rust-version = "1.96"` declarations, the `libretro-cross` 1.96 leg) and correct the three docs that describe the old image.
- **Later in v3.x:** add Core Options v2 and float-audio negotiation, both behind a capability check.

## 4. RetroAchievements

### Requirements and process [V, docs.retroachievements.org/general/hardcore-compliance-requirements.html, "last updated about 3 months ago"]

- RA now uses the term **"hardcore-compliant"** rather than "supported" or "partnership".
- **Eligibility:**
  - The emulator must be **publicly available for at least 6 months**. RustyNES is.
  - FOSS licence obligations must be met.
  - A **monetisation disclosure** is required. ADR 0035's no-monetisation decision makes this trivial.
  - A **privacy policy** is required, covering data retention, server locations and GDPR.
  - The emulator must disclose any earlier identification as another client.
- **Technical requirements:**
  - Triggers, Measured and Rich Presence must work, and leaderboards must work and cannot be disabled.
  - **Offline unlock queueing** with secure caching.
  - Save-state hit storage is recommended.
  - **Hardcore blocks:** cheats, rewind, slowdown and frame advance, *loading* save states, memory editors, debuggers, **scripting**, and **TAS input playback**.
  - Switching to hardcore mid-session needs a full reset.
- **User-Agent format:** `EmulatorName/v1.0.0 (OSName 10.0) core_name/v0.5.0`.
  - RustyNES sends `RustyNES/<ver> rcheevos/<ver>` (`RA_USER_AGENT`).
  - Check whether RA expects a `v` prefix and an OS segment, and whether `rcheevos/<ver>` is acceptable in the core slot [U].
- **How to apply** is not stated on that page [U]. The forum post "A Note on RA Process Updates and the Afterplay Emulator" (topic 31930) returned HTTP 403 to fetch.
- `docs/ra-integration-request.md` in the repo is **stale**. It says v1.8.8 and "MIT OR Apache-2.0", but the project is GPL-3.0-or-later.

## 5. App distribution

### Google Play [V unless marked]

- **Target API level:** API 36 is required for new apps and updates from **2026-08-31**, extendable to 2026-11-01. Apps below API 35 are hidden from new users on newer devices.
  - RustyNES's `targetSdk = 36` and `compileSdk = 37` already comply [V, `android/app/build.gradle.kts`].
  - API 37 has no announced deadline yet [S]. By the yearly pattern it will be **about 2027-08-31** [I].
- **16 KB page size:** required since **2025-11-01** for apps targeting 35+ with native code [S]. The repo already handles it (NDK r27+ note in `build.gradle.kts`).
- **New personal developer accounts** (registered after 2023-11-13) must run a closed test with **12 opted-in testers for 14 continuous days** before production access [S].
- **Developer verification** applies to sideloads too [V, developer.android.com/developer-verification]:

| Date | Milestone |
|---|---|
| Aug 2026 | APIs, limited-distribution accounts and the "advanced flow" available |
| 2026-09-30 | enforced in BR, ID, SG and TH (certified devices, Android 7+) |
| 2027+ | global |

  - Limited-distribution accounts: up to **20 devices**, no ID, no fee.
  - Full registration through the **Android Developer Console** needs government ID.
  - F-Droid published an open letter opposing the scheme (2026-02-24) [V, title only].
  - Press coverage frames it as a threat to emulator sideloading [S].
- **Android 17 (API 37)**, released 2026-06-16 [S]. Changes that apply when targeting 37 [V, behavior-changes-17]:
  - **`ACCESS_LOCAL_NETWORK` runtime permission** (in the `NEARBY_DEVICES` group) is mandatory for LAN discovery and connection. This affects RustyNES's direct-IP and LAN netplay.
  - On large screens the orientation and resizability opt-out is removed.
  - **Background audio hardening:** audio APIs fail *silently* outside a valid lifecycle. This also applies to all apps on Android 17.
  - Native libraries loaded with `System.load()` must be read-only.
  - `static final` fields cannot be modified through reflection or JNI.

### F-Droid / IzzyOnDroid

- F-Droid requires a 100% FLOSS toolchain, but "Rust toolchains are explicitly permitted as prebuilt binaries" [V, Inclusion Policy page, as summarised].
- It allows no proprietary deps (Play Services, Firebase). The repo's `foss` flavour exists for exactly this.
- It has anti-feature labels (for example `NonFreeNet` if a RetroAchievements or hosted-netplay server is used) [V].
- It has no emulator-specific rule [V].
- Developer-signed APKs need reproducible builds [S]. Practical need: commit `Cargo.lock` (done) and use `cargo build --locked` [S].
- **IzzyOnDroid** takes APKs from GitHub tagged releases [S]:
  - 30 MB per-APK limit, 3 versions kept;
  - reproducible-build verification for about 64% of its apps.
  - This is the lowest-friction "store" for a sideload-first app. Check the APK size against 30 MB [U].

### Apple [V for the guideline text]

- **Guideline 4.7** now reads: "retro game console **and PC** emulator apps can offer to download games".
- Apps offering such software must also meet 4.7.1 to 4.7.5:
  - an index of offered software with universal links (4.7.4);
  - an age-restriction mechanism (4.7.5);
  - a report and block mechanism (4.7.1).
  - These matter only if the app ever *offers* downloads. Loading user files does not trigger them.
- **SDK floor:** since **2026-04-28**, uploads to App Store Connect, **including TestFlight**, must be built with Xcode 26 and the iOS 26 SDK [S].
  - iOS 27 and Xcode 27 shipped 2026-09-14 [S].
  - By the yearly pattern, **Xcode 27 / iOS 27 SDK will be required about late April 2027** [I].
- **TestFlight:** 10,000 external and 100 internal testers; builds expire after **90 days**; the first external build needs beta review [S].
- **EU DMA:** AltStore PAL lets developers self-publish notarised apps for free through their own JSON "source" [S]. Apple's per-install Core Technology Fee was €0.50 [S]. Apple has since revised its EU terms (a "Core Technology Commission") [U, exact 2026 terms not verified].

**Implication for RustyNES:**
1. **Before 2027 (v3.x):** decide the Android identity question. Choose between full verification, the 20-device limited account, or relying on the advanced flow and IzzyOnDroid or F-Droid. F-Droid's own future is in doubt.
2. **Before about 2027-08 (v3.x MINOR):** add `ACCESS_LOCAL_NETWORK` handling and a foreground service for background audio, then target API 37.
3. **About April 2027:** rebuild iOS with Xcode 27.
4. **Every 90 days:** re-upload TestFlight builds, or testers lose the app.

## 8. Netplay hosting

- **Signalling:** RustyNES already ships its own `signaling_server` binary (`rustynes-netplay`, feature `signaling-server`, tokio-tungstenite) [V, repo]. The gap is *hosting*, not code.
  - **Cloudflare Workers + Durable Objects** (WebSocket Hibernation) work on the **free plan**, SQLite-backed objects only [V, CF pricing]:
    - free: 100k requests/day, 13,000 GB-s/day, 5 GB storage;
    - paid: $0.15/M requests and $12.50/M GB-s, with hibernation cutting duration charges sharply.
    - The cost is a rewrite of the room protocol in JS or Rust-to-wasm on Workers.
  - **Open-source alternative:** `matchbox_server` / `matchbox_signaling` (Rust; full-mesh signalling, GGRS-compatible sockets) [S, docs.rs].
- **TURN:** **Cloudflare Realtime TURN** [V, CF docs]:
  - $0.05/GB egress; 1,000 GB free per month, shared with the SFU;
  - free and unlimited STUN at `stun.cloudflare.com:3478`;
  - TURN over UDP 3478/443, TCP 3478/80 and TLS 5349/443;
  - per-allocation rate limits.
  - Rollback NES traffic is tiny. At about 60 packets/s of about 100 bytes, it is about 6 KB/s, or about 22 MB per player-hour [I]. **The free tier covers tens of thousands of relayed hours a month** [I].
  - Self-hosting coturn on a small VPS is the other option. Prices were not verified [U].
- **How others do it:**
  - RetroArch runs a public lobby list plus regional **MITM relay servers** that avoid port forwarding [S, retroarch.com/netplay.php].
  - Dolphin uses a "traversal server" for NAT hole-punching plus a lobby [U, from knowledge, not re-verified].

**Implication for RustyNES:**
- **v3.x:** decide whether to run a public lobby. The cheapest durable option is a Cloudflare Worker with Durable Objects for rooms, plus Cloudflare TURN with short-lived credentials minted by that Worker.
- That brings in a privacy policy (also needed for RA) and F-Droid's `NonFreeNet` anti-feature.

## 9. MiSTer

### Submission process [V, MiSTer-devel Wiki "Contributing a Core to MiSTer FPGA"]

- The licence must be GPLv3, MIT or compatible.
- The repo must follow the standard template (`sys/`, `rtl/`, `releases/`, `.qpf`, `.qsf`). The core **must not depend on custom edits to `sys/`** framework files.
- Releases are `releases/CoreName_YYYYMMDD.rbf`.
- Submit by emailing the repo link to **newcores@misterfpga.org**. Review "can take upwards of a month".
- On acceptance the repo transfers to MiSTer-devel and you stay maintainer. Search results give an older address (newcores.misterfpga@gmail.com) and a step to add the core to the "List of Cores" with a unique home folder [S].
- Alternatives to MiSTer-devel: JTCores, Coin-Op Collection, or a custom `downloader_<repo>.ini` database for `update_all`.
- Nothing says a second NES core is barred [U]. Expect reviewers to ask how it differs from the existing NES core.
- The RustyNES sibling repo is **private**, per CLAUDE.local. MiSTer-devel requires a public repo under a compatible licence. That is a prerequisite decision.

### SuperStation One

| 2026-01 | First batches (Founders and crystal-blue editions) reached buyers in early January. | [S, Time Extension, 2026-01-05] |
| 2026-07-29 | "Console Mode" UI released (it had slipped from June): RetroAchievements, artwork scraping, per-game core overrides. Comments mention Batch 4. | [S, Time Extension] |

- **Specs:** Intel Cyclone V SoC FPGA; **128 MB on-board SDRAM**; HDMI up to 1440p/1536p; VGA, composite and component; Wi-Fi, BT, Ethernet; NFC (Zaparoo); 2 PS1 SNAC ports; M.2 [S, CNX Software].

**Implication for RustyNES:**
- Hardware verification (ADR 0043's v3.x) can target units that are shipping now.
- Sequence: board session → hardware-verified MINOR or MAJOR → decide repo visibility → MiSTer-devel email (allow 1+ month).
- An `update_all` custom database is a faster interim channel that needs no review.

## 10. Other things a roadmap author would regret missing

- **Android developer verification (2027 global)**: see section 5. This is the biggest external risk to the current sideload model.
- **Android 17 local-network permission and silent background-audio failures**: see section 5. Both bite the existing netplay and audio paths.
- **AccuracyCoin moving under the "100%" claim**: see section 7. Any public "144/144" statement should carry the upstream commit it was measured against.
- **wgpu's 3-month breaking cadence** means about 4 forced graphics bumps between now and v4.0 [I].
- **`wasm32-wasip2`** is Tier 2 [S]. A `wasm32-wasip3` target is a 2026 goal [V, goal name]. Neither affects the browser build (`wasm32-unknown-unknown`).
  - A WASI build of the headless core could serve as a sandboxed CI oracle or a plugin target. It is optional, and not on the critical path.
- **i686 Windows host-tool demotion**: see section 1. 32-bit Windows is a std-only target now.
  - Keep 32-bit Windows artefacts only where a user base exists: the libretro buildbot builds it anyway.
- **Rust 2027 edition**: not imminent. See section 1.
- **RetroArch has not tagged a release since 1.22.2 (2025-11)**: see section 3. Any new-API adoption must degrade gracefully.
- **iOS SDK floor every April**: see section 5. Late April 2027 for Xcode 27 [I].
- **Firefox WebGPU on Linux and Android, and Chrome on most Linux GPUs, are still not default** [V]. Keep WebGL2.

**Implication for RustyNES:** add a recurring "ecosystem watch" item to every MINOR's plan. Cover:

- the wgpu/egui pair;
- the AccuracyCoin upstream diff;
- the rcheevos version;
- the libretro image commit log;
- the Android and iOS policy calendar.

Then pin three dated deadlines:

1. 2027 Android verification;
2. about April 2027, the Xcode 27 floor;
3. about August 2027, API 37.
