## What a MiSTer core actually is

SystemVerilog compiled by **Quartus 17.0.2** (a pinned, elderly version - not
"whatever Quartus you have") into a Cyclone V bitstream. The repository layout is
fixed:

| Path | Role |
|---|---|
| `rtl/` | the core's own HDL |
| `sys/` | the MiSTer framework - **used verbatim; modification is prohibited** |
| `releases/` | built `<Core>_YYYYMMDD.rbf` bitstreams |
| `<core>.qpf` / `.qsf` / `.sdc` / `.srf` | Quartus project, settings, timing constraints |
| `files.qip` | the source manifest Quartus reads |
| `<core>.sv` | the top-level glue between `sys/` and `rtl/` |

Consequences that matter to the plan: `sys/` being verbatim is what makes the
**licence-header audit** (risk 1) a prerequisite rather than a formality, and
`files.qip` being the manifest is what makes it safe to keep `tb/nes_top_cosim.sv`
in the tree - a file not listed there is simply not synthesised.

## Boards

| Board | FPGA | SDRAM | Note |
|---|---|---|---|
| Terasic DE10-Nano | Cyclone V SE 5CSEBA6, 41,910 ALMs, ~5,570 Kb M10K | **add-on board required** | the reference platform |
| Retro Remake SuperStation One | Cyclone V SoC | **128 MB integrated BGA** | runs MiSTer cores directly |

**The SDRAM requirement is not optional for NES.** The NES reads cartridge ROM
directly, and the DE10-Nano's onboard DDR3 is too slow for that access pattern, so
every NES core on MiSTer needs the add-on. The SuperStation One has it on the
motherboard, which is why the plan schedules hardware bring-up there first.

Retro Remake forks `Distribution_MiSTer` and `Downloader_MiSTer` and hosts cores
itself (`Atari7800_MiSTer` is the existing example). One `.rbf` is understood to
serve both boards - but no source found confirms the identical bitstream byte for
byte, so rung 6 verifies it rather than inheriting the claim.

## The incumbent

`NES_MiSTer`: GPL-3.0, ~150 mappers, FDS, savestates, 636 commits. It scores
**121/125 on AccuracyCoin**, and **real Famicom AV hardware also scores ~121/125** -
its four remaining failures are edge PPU behaviour where hardware agrees with it.

There is therefore **no published accuracy headroom**, and MiSTer's contribution
guidance is explicit that a core should "expand coverage, improve hardware
accuracy, or help preserve a system", with redundant cores discouraged. A second
NES core may be declined. That is understood and accepted; Retro Remake is the
planned fallback home rather than a contingency.

**Favourable, and load-bearing for this programme:** MiSTer's guide now says
*"Fully AI generated code should meet a minimum reasonable bar for readability and
include some evidence of quality and accuracy testing."* Per-cycle co-simulation
against a 141/141 oracle **is** that evidence, in a stronger form than any existing
core can currently show.

## The tension, and its resolution

The community's standard on-ramp is explicit:

> *"Rather than writing something from scratch, it's better to look at somebody
> else's work and try to fix a bug or two."*

The provenance firewall forbids exactly that - **for NES cores**. It does not
forbid it for other systems.

**Resolution: learn the framework by reading and fixing a simple non-NES core.**
An old arcade core is the community's own suggestion. This buys the `sys/`,
`hps_io`, OSD and video-timing knowledge that rung 6 needs, without ever opening
NES RTL. It is folded into rung 0 as a learning task with **no deliverable**,
rather than pretending the on-ramp does not exist.

## Why replay rather than lockstep

`Nes` exposes `run_frame()` and `step_instruction()` and nothing finer. Live
cycle-lockstep would mean new core API on the hot path, putting the determinism
contract and the ~3.9 ms/frame budget at risk.

It would also gain nothing, because **the determinism contract already makes
replay equivalent to lockstep**: same seed + ROM + input yields a bit-identical
framebuffer and audio, so a trace recorded now is exactly the trace a lockstep run
would have produced. Replay is additionally better in two ways - goldens are
re-diffable without re-simulating, and the two sides can run on different machines
at different times.

`scripts/mesen2_cpu_boot_trace.lua` already writes `cpu_boot_trace` from a foreign
emulator, so the FPGA testbench becomes the format's **third** writer, not its
first. A format with an existing foreign producer is a format worth reusing.

## The volume constraint nobody budgets for

A 4200-frame AccuracyCoin run is roughly **125 M CPU cycles**. Written as
per-cycle `irq_trace` CSV that is about **7.5 GB** - per side, per run.

Both sides therefore chain a 64-bit hash over the per-cycle tuple and compare
checkpoints every 4096 cycles: **244 KB** for a full run. On the first mismatch,
binary-search the window and re-run *only that window* with full capture and
waveforms.

This is a rung-0 design constraint. Bolting it on after the fact means rebuilding
both writers.

## Clocking, decided on day one

A single `clk_sys` = **21.477272 MHz** domain with a **mod-12 master phase
counter**: divide by 4 for the PPU dot, by 12 for the CPU cycle, and the low and
high halves give M2 phase directly.

That last property is why the decision belongs on day one rather than being
discovered later: it matches `irq_trace`'s two-samples-per-CPU-cycle model exactly,
so the trace format and the clock structure agree by construction.
