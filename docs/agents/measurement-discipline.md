# Measurement discipline — what a result does and does not prove

> **Split out of `AGENTS.md` (2026-09-20).** These notes were inline in that
> file's "Operating notes for Claude Code" section, which had grown to
> **115,606 bytes across 110 bullets** — loaded into every session whether or
> not the task touched any of it. The content is **verbatim**; only its
> location changed. `AGENTS.md` carries the index.
>
> **Read this file when the task touches measurement discipline.**
> Every bullet is a measured finding with its evidence attached; they are
> written to be re-checkable, not to be taken on trust.

- **A fix that touches ONE call site of a shared code path may not fix the bug — and will report that it did.** v2.3.6 hit this squarely. Review reported that a latency measurement destroyed the user's rewind history; the fix changed `measure_in_place`'s FINAL restore to `restore_quiet` and stopped. Every *trial* still went through `Probe::run_uncounted`'s loud `nes.restore(..)`, and a measurement runs up to **21 trials** against the live emulator, so the ring was still being cleared twenty-one times over behind a fix that closed the thread. Before declaring a fix complete, grep for every caller of the mechanism, not just the one the report named. The corollary is about tests: my test for that fix would have asserted "ring not empty", which **passes while a second defect remains** — the ring in fact GREW, polluted with replayed frames that never happened on the user's timeline. Assert the state comes back EXACTLY as it was; a weaker assertion is how an incomplete fix clears review.

- **Prose asserting an intent is how a defect survives releases.** Pixel Provenance shipped broken for four releases with a comment two lines above the offending code claiming the clear "leaves exactly the visible frame's writes — which is the timeline the user is looking at", plus four matching doc claims. Nobody checked because the text said it was fine. When correcting this class, KEEP the wrong text quoted alongside the measurement that disproves it — deleting it loses the evidence that the prose was the mechanism.

- **Re-run mutations after a STIMULUS change, not only after a code change.** v2.5.5 had one mutation — deleting the nametable toggle from `inc_x` — come back NOT CAUGHT **three times**, against a gate that was working correctly every time: horizontal arrangement made `$2000` and `$2400` alias the same kilobyte; a zero coarse-X scroll meant the only wrap happened at dot 256 and `copy_x` undid it at 257 before it reached a pixel; and the fill wrote one ascending 256-period ramp across two 1,024-byte nametables, so both came out **byte-identical**. Each fix looked like it had closed the hole, and only the next mutation run showed it had not. A NOT CAUGHT has now meant four different things in this project: the gate is blind, the stimulus is blind, the mutation was a no-op, or the mutant never built.
- **A fix that improves a symptom without curing it is evidence about the mechanism.** v2.5.5's frame was shifted right by exactly one pixel. Moving the shift window alone took the first wrong pixel from x=9 to x=17 — one tile further in — and that partial improvement is what proved the *reload* was out of phase too, rather than the shift being wrong twice. The resolution then **removed** a register instead of adding a knob: the reload is the pattern-high fetch's own dot, so it takes `chr_din` directly and `bg_hi_latch` no longer exists. When a change helps but does not close, read the residual before reaching for the next constant.
- **A mutation that comes back NOT CAUGHT may be indicting the STIMULUS, not the gate.** Two of v2.5.4's first eight mutations were no-ops because the ROM rendered from `$2000` with `PPUCTRL = 0`, holding `v[11]` and `ctrl[4]` at zero for its whole duration. The gate was working correctly; the ROM never set the bits. Before weakening or excusing a gate, check whether the stimulus REACHES the mutated path — same shape as v2.5.1's `BRK` passing 186/186 while the interrupt return address was wrong. Extending the ROM (a second rendering window at `$2800` with patterns at `$1000`) took the fetch count 3,099 → 6,247 and both mutations to CAUGHT.
- **SWEEP A KNOB AGAINST THE QUANTITY IT MOVES, NEVER ONLY AGAINST THE VERDICT (v2.6.18).** `SCROLL_GATE_LAG` was recorded as refuted after a depth sweep against the battery verdict — which cannot separate "the knob is inert" from "the knob worked and something else still fails". It reads `sweep_mask_history[depth - 1]`, so the derived two dots of deferral is depth **3**, while depth **2** (the cell the sweep treated as the derived one) is byte-identical to shipped. Sweeping it against the dot-256 increment itself separated those in one run and reopened an entry that had been closed as impossible.
- **DISTINGUISHING A FIX FROM A COMPENSATION IS A MEASUREMENT, NOT A JUDGEMENT (v2.6.7).** v2.5.7 is the cautionary case -- a phase was wrong and every window compensated for it -- so any one-cycle move deserves the question. The discriminator here was that the interrupt **SET** path was already correct: `01-basics` passes **655 of 655** checkpoints and those windows contain many set events. A global phase error does not localise to one edge of one signal. **Check whether the neighbouring paths on the same signal are already exact before accepting a one-cycle change**; if they are, the change is local, and if they are not, it is probably compensating for something upstream.
- **Every SAME-TIMELINE restore must hand-carry the state that lives outside the save state.** `Nes::restore_inner` clears the pixel- and audio-provenance stores — right for a real timeline change, wrong for a restore that puts back the state the user is still looking at. v2.3.6 wired `take_provenance`/`put_provenance` into `RunAhead::finish`, **the one call site the report named**; `rustynes-probe` had three more (`Probe::run_uncounted` per trial — a latency measurement runs up to 21 — `latency::measure_in_place`'s final restore, and the atlas panel's `TimelineGuard`), so the Latency Oracle and RAM Atlas silently emptied both provenance panels. Both stores are **cumulative**, so nothing rebuilt them. `crates/rustynes-test-harness/tests/snapshot_schema_audit.rs` enumerates the whole excluded set and is the place to look — but its reasons are **free text**, and a keyword pass over them mis-sorted 17 of 26, so the durability question is not machine-checkable. Assert a caller's state returns **byte-identical**, never merely "armed": a store emptied while left armed passes an `is_some()` check (caught in review on #405).
- **A test that reimplements its subject is testing itself, and it will agree forever.** v2.4.0 hit this in a test written *for a review finding*: it declared a local `fn strip(t) { t.trim_start_matches([' ', '*']) }` and asserted against that, so deleting the production stripping came back **NOT CAUGHT**. Only the mutation pass could see it — the test passed, read correctly, and covered nothing. The fix is the one this release needed three times over: **extract the decision into a named item both the code and the test call.** The other two were `atomic_write`'s injectable rename predicate (with it hard-wired, the exhaustion branch is unreachable on Unix and a mutation returning `Ok(())` for a save that never happened went uncaught) and `TimelineWatch` (`DebuggerOverlay::new` needs a window and a wgpu device, so nothing living only inside it is unit-testable). In all three the code **read** as testable beforehand.

- **AN ARITHMETIC COINCIDENCE READS EXACTLY LIKE A MECHANISM (2026-09-20).** The CHR fetch gate shows 21,941 diverging fetches against 4,389 `$2007` writes. 4,389 x 5 = 21,945, and that near-miss was written into a commit body, a PR description and a summary as "remarkably close", carrying an implied model — one write corrupts about five fetches until the next reload. Walking the stream for contiguous runs refuted all of it: **9,472 runs**, 88% of them exactly **length 2**, about **2.16 runs per write**, and **no concentration at dot 257**, so nothing was persisting until the reload. The real structure was sharper than the invented one — 99.7% of those pairs are the two pattern-table fetches of a single tile (dot gap 2, address gap 8, identical delta on both), which says the error lasts exactly one tile and then re-converges. **A product that lands near your total is not evidence of the factors.** Count the structure — runs, gaps, boundaries — before believing a multiplication.
- **A FLAT LINE AND AN INERT EXPERIMENT ARE THE SAME PICTURE (2026-09-20).** Delaying the CHR write transaction by 0,1,2,3,4,5 dots gave a bit-identical 32,861 every time, which is equally consistent with "phase does not matter" and "the patch never reached the hardware". The two are separated only by a **positive control**: the same patched path with one bit inverted in the captured address moved the result to 35,817. Without that, the refutation would have been indistinguishable from a broken edit. **Any experiment whose interesting outcome is "nothing changed" needs a control that makes something change**, on the same patched path, before the null is reportable.

- **A COMPONENT MEASURED THROUGH A DEFECT UPSTREAM OF IT READS AS NEGLIGIBLE, AND THE NUMBER IS HONEST (2026-09-20).** The CHR-during-rendering write address was quantified at **715 of 32,861 pixels — 2.2 percent** and parked on exactly that basis: "it would neither close the gate nor identify the cause", against an RTL change costing a Quartus re-sweep and a re-cut bitstream. The measurement was correctly taken and correctly reported. It was also worthless, because `v` itself was still one dot out, so the sweep measured this component *through* a defect upstream of it. Once `v` was fixed the same one-line change was worth the **entire remainder** — 2,404 of 2,404 pixels, closing an eight-release expected failure outright. **Re-measure every quantified-and-parked contribution after anything upstream of it moves.** A contribution is a property of the pair, never of the line, and a decision not to act that cites a percentage inherits every defect between the knob and the observable.
- **A COMPLETE SWEEP OVER THE WRONG SPACE TERMINATES WITH A CONFIDENT NEGATIVE (2026-09-20).** Eleven variants across five axes — composition, collision policy, write phase, write address, condition — all measured correctly, all recorded, and the shipped form was the best of them. The conclusion drawn was "the `v` divergence is not in this logic... whatever is left is structural", which closed the search and sent the next session away from the answer. Every variant swept **what the `$2007` arm computes**; none swept **what it computes it from**, and that was the axis: the arm read the raw register while the oracle resolves the access against `v` *after* that dot's rendering-pipeline load. A twelfth variant on any of the five axes could not have found it. What found it was instrumenting the quantity instead: a nametable fetch address **is** `{2'b10, v[11:0]}`, so the gate's own records already contained `v`, and the oracle's `--ppu-state-trace` gives its `v` per dot — two traces, one comparison, answer in the first diverging record. **When a sweep reports "not here", prefer instrumenting the disputed quantity over widening the sweep**; an exhausted axis list is evidence about the axes, not about the defect.
- **A PER-DOT TRACE FROM TWO MODELS IS NOT COMPARABLE UNTIL A REFERENCE EVENT SAYS SO (2026-09-20).** Comparing the oracle's `--ppu-state-trace` against the DUT's `PPUDATA_PROBE_CYC` showed the DUT's `v` one dot behind — which reads as a one-dot timing defect and is equally consistent with the two traces sampling at different points inside the dot. Neither tool documents its observation point. The discriminator was a **reference event with no modelling freedom**: the dot-256 `inc_x`+`inc_y` is fixed by the PPU specification, so wherever the two traces disagree about *it*, the disagreement is convention rather than behaviour. That alone was still not enough — it was the oracle's own fetch record at dot 258 reading `$244C` (i.e. `v` as of dot **256**) that showed fetch addresses lag `v` by ~2 dots on both sides through the ALE latch, which is why the traces agree at all. **Before reading a cross-model timing difference as a defect, find an event both models must place identically and calibrate on it.**
- **`[^.]*` AND `[^\n]*` ARE BOTH UNSAFE REGEX ANCHORS IN THIS CORPUS (v2.6.23).** Fixing the version-bump release anchors corrupted two files with two different failure shapes from the same underlying cause. `[^\n]*` matched `docs/STATUS.md`'s entire 32,134-character release-narrative line and replaced it wholesale, deleting thirteen releases of lineage — a diff stat reading "1 changed, 1 added". `[^.]*` (a character class excluding the literal byte `.`) stopped inside the NEXT version literal in a chain (`**v2.6.21**` has a period in it too), splicing new text mid-word and producing syntactically-broken prose that still reads as intact. Neither corruption was visible in the diff stat; agy caught the second in its first review round and it sat unfixed for three more (see the review-bots finding above). Before trusting a regex-based edit near a `vX.Y.Z` string or a line suspected of holding accumulated history: print the FULL matched span and read it, or check the line's length, before calling `.replace()`.

- **PER-SUITE COUNTS READ OFF A COMBINED RUN ARE MISLABELLED (2026-09-23, #545).** `cargo test -p rustynes-test-harness --test a --test b --test c --test d` prints one `test result:` line per suite, but **not in the order the `--test` flags were given**. Three commit messages and a PR body attributed the counts by position and got every label wrong: the report said anchor 14, prose 15, render 8, checklist 2, and the truth was anchor **15**, prose **8**, render **2**, checklist **14**. The "correction" posted in between was itself mislabelled the same way. Every suite passed each time; only the attribution was false, which is exactly the kind of error a reviewer cannot catch from outside. **Run each suite on its own when its count is going to be quoted**, or read the `Running tests/<name>.rs` line above each result instead of relying on order.

- **A FUZZ TARGET THAT NEVER TICKS CANNOT SEE A DEFERRED PANIC, AND ONE FED RAW BYTES NEVER REACHES A FIELD (v2.7.0).** `fuzz/fuzz_targets/save_state.rs` existed for a year and found nothing, while the core audit located save-state crashes by reading the code. Every one of them **restores cleanly and panics on the next tick**, and the target restored and stopped. It also fed raw bytes with no corpus (`corpus/` is gitignored), so almost no input got past the header and section framing. Three changes made it work, each for a measured reason: (1) **patch mode** -- `(offset u16, value)` triples over a REAL snapshot, so structure survives and every field is one patch away; (2) **run the machine after an accepted restore** -- but ~120 instructions, not a `run_frame`, which measured **~15 exec/s** against **~1,000**; (3) **make the base machine exercise the paths** -- a silent APU hides the channel panics because `Pulse::output` short-circuits on a zero length counter before it indexes the duty table, and rendering must be on for sprite evaluation to run. Against the unfixed tree it then found, in turn, a `debug_assert` fed by a restored field (6,848 runs), IMP-01 at `ppu.rs:5104` (29,326), and an OAM-DMA index overflow (287,867) -- **two of the three were not in the audit.** An audit locates what its reader thought to look for; a working fuzzer finds what nobody did. When a fuzzer reports nothing, first ask whether its inputs can reach the code and whether the harness executes the code that would fail.

- **A CEILING PROBE IS ONLY A CEILING IF THE WORKLOAD EXECUTES THE CODE IT DELETES — COUNT THE CALLS (v2.7.6, #555).** The core audit's §3.5b (the pulse sweep-mute check) was "measured zero" twice: in v2.7.5's combined probe and again alone in v2.7.6. Both bench ROMs are silent, `Pulse::output` short-circuits on `length.count == 0`, and a temporary counter in `muted()` read **0 calls per frame**. On `spritecans.nes` (59,561 calls a frame) the same probe measured a real 0.10-0.14% ceiling. This is IMP-07 again (the benches never drain audio). Before believing any zero from a deletion probe, count how often the deleted code runs on that workload; a CodeRabbit request to "qualify the conclusion" is what prompted the count.
