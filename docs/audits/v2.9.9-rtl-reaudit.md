### NR-13 — Low. The off-die bridge serves a read of an address whose write is still held in the pending slot, and keeps the old byte. DEMONSTRATED at module level; console reachability not established

- **Where.** `cart_sdram.sv:182-184` (`chr_issue`) and `:330-331` (the PRG issue condition). Both guard the read-after-write hazard against `wr_out_addr` only, which is the write already ON the bus. The held write (`wr_pending`, `wr_pend_addr`, `:231-233`, `:460-467`) is not compared.
- **Mechanism.**
  1. A write to address X arrives while another write is busy. It goes into the slot (`:464-466`).
  2. The invalidation at `:420-429` clears `*_held` for X (or poisons a read already out).
  3. A read of X issued after that, but before the slot drains, passes the hazard check, because `wr_out_addr` holds the OTHER write.
  4. The arbiter serves that read before the held write is strobed, and the old byte comes back with `*_held <= 1`.
  5. The stale copy is kept until the port's address changes.
- **Demonstration.** A scratch driver for the unchanged `tb/cart_sdram_tb.sv` does the following:
  1. Loads CHR offset `0x10 = 0x11`.
  2. Parks the CHR port at `0x200`.
  3. Writes `0x300`, then writes `0x10 = 0x99` while `wr_busy` (`load_wait` = 1, so the second write is held).
  4. Moves the CHR port to `0x10`.

  Result: `chr_dout = 11 (want 99)`, with no overrun. Moving away and back reads `99`. The control without the second write reads `11` as it should.
- **Reachability.** It needs two writes closer together than one write's service time, followed by a read of the second address before the slot drains.
  - CPU `$2007` CHR-RAM writes are at least one CPU cycle (48 SDRAM cycles) apart, against a write latency in the teens.
  - Loader writes arrive with the console in reset.
  - No console scenario was found that reaches it. Hence Low.
  - The slot exists precisely for writes faster than the bus, so the hazard sits on the path the slot was built for.
- **Fix.** Also hold off a read whose address equals `wr_pend_addr` while `wr_pending`. Equivalently, extend the existing compare to both slots.
- **Gate.** Add a `cart-sdram-gate` section with the stimulus above: red now, green after. Repeat it for PRG with a loader write.

### NR-14 — Low. NES 2.0 submappers are ignored, so boards this core does not implement are accepted as the base mapper. REASONED (code against the vendored wiki)

- **Where.** `ines_header.sv:79` sinks `b8[7:4]`, the NES 2.0 submapper, as unused. `supported()` at `:83-87` tests the 12-bit mapper number only.
- **Mechanism.** `nesdev_wiki/NES_2_0_submappers.xhtml` defines mapper 4 submappers. The core accepts every one as plain MMC3 and shows "Cartridge loaded":
  - 1, MMC6: "an alternative PRG-RAM enable and write protection scheme" (*StarTropics*, *StarTropics 2*).
  - 3, MC-ACC: 13 Acclaim boards.
  - 4, NEC MMC3: "Loading the latch with 0 disables IRQ".
  - 5, T9552: "a T9552 scrambling chip".

  The same applies to mapper 1 submapper 6 (2ME, EEPROM in place of CHR) and the bus-conflict submappers of 2 / 3 / 7. The oracle distinguishes the mapper 4 submappers since v2.9.6.
- **Failure scenario.** An NES 2.0 dump of a T9552 board runs with its PRG unscrambled and renders garbage behind "Cartridge loaded". This is the case the refusal exists for (NR-03).
  - An MMC6 image runs its PRG-RAM protection under MMC3 semantics.
  - An iNES 1.0 dump of the same game cannot be told apart, so the gap is limited to the headers that do say so.
- **Why the gate cannot see it.** `ines-header-gate`'s model (`tb/ines_header_main.cpp`) also ignores byte 8's high nibble, so model and RTL agree on the omission.
- **Fix.** For NES 2.0, accept only the submappers the RTL implements (0 for each, plus any that are deliberately treated as equivalent), refuse the rest with an OSD line, and add submapper cases to the model.

### NR-15 — Low. `cart_loaded` has no power-up value, and synthesis made it constant 1 in both bitstreams. DEMONSTRATED from the synthesis reports

- **Where.** `emu.sv:620` `logic cart_loaded;` has no initialiser. It is only ever set (`:759`, `if (rom_download) cart_loaded <= 1'b1;`) and never cleared. The project uses Quartus's default `Power-Up Don't Care : On` (`output_files/RustyNES.map.rpt:297`).
- **Evidence.** "Registers Removed During Synthesis": `emu:emu|cart_loaded ; Stuck at VCC due to stuck port data_in` (`output_files/RustyNES.map.rpt:1079`; off-die `output_files_offdie/RustyNES.map.rpt:1097`). With power-up left free, the tool chose 1, and a set-only register at 1 is a constant.
- **Consequence.**
  - The `~cart_loaded` term of `reset` (`emu.sv:786`) and the `cart_loaded` input of `osd_menumask` (`:308`) are absent from the bitstream.
  - Behaviour is unchanged ONLY because `mapper_ok` IS initialised (`:671`, `= 1'b0`) and gates both: a core started with no cartridge is held by `~mapper_ok`, and Reset is greyed by `!mapper_ok`.
  - The comment at `:624-626` ("Power-up values, not left to X ... `~cart_loaded` already did") describes a register the bitstream does not have.
  - `menumask-gate`'s `cart_loaded = 0` cases describe inputs the silicon cannot produce.
- **Fix.** `logic cart_loaded = 1'b0;`, as its neighbours have.
- **Gate.** A report check that fails when an `emu:emu|` register outside an allow-list appears as "Stuck at VCC" / "Stuck at GND" in "Registers Removed During Synthesis". Neither `quartus_clean.py` nor `check_warnings.py` reads that table. The legitimate entries today are `info[3..7]`, `prg_bytes[0..13]`, the APU table LSBs and the palette-RAM mirror slots.

### NR-16 — Low (process). The release script's warning checks never read the suppressed-messages files, and two `rtl/emu.sv` warnings live there. DEMONSTRATED

- **Where.** `scripts/release-rbf.sh:147` runs `tb/quartus_clean.py` on the fit, sta and `map.rpt`; `:180` runs `tb/check_warnings.py` on `map.rpt` and the fit. Neither is given `output_files/RustyNES.map.smsg`. The map report says that file holds the suppressed messages ("Analysis & Synthesis Suppressed Messages ... can be found in ... RustyNES.map.smsg").
- **Evidence.** On the 261003 reports, `quartus_clean.py output_files/RustyNES.map.rpt` passes ("scanned 3 Quartus message(s)"), and so does `check_warnings.py` ("3 warning(s) emitted, 3 pinned"). `quartus_clean.py output_files/RustyNES.map.smsg` fails with two owned warnings:
  - `Warning (10273) ... emu.sv(79): extended using "x" or "z"` (`ADC_BUS = 'Z`);
  - `Warning (10268) ... emu.sv(697): always construct contains both blocking and non-blocking assignments` (the `m = ...` local).

  Both are benign, and v2.9.0 recorded them by eye. What is missing is the check.
- **Mechanism.** `quartus_clean.py` exists because "`MESSAGE_DISABLE` ... could [make] a real warning about OUR code ... disappear". A message Quartus routes to `.smsg` disappears the same way. Its two current residents are owned, unpinned, and invisible to both release checks, so a new defect warning of the same routing would ship.
- **Fix.** Pass `map.smsg` (and `fit.smsg`) to both checks, and pin or fix the two current entries.
- **Gate.** The release script itself, red on today's `.smsg` until the two are pinned or fixed.

### NR-17 — Low (testbench). `sdram-arb-gate`'s CPU-deadline check fails only on IMPROVEMENT, and its own comments carry superseded numbers. DEMONSTRATED by reading

- **Where.** `tb/sdram_arb_main.cpp:265-274`. If `worst_prg <= PRG_BUDGET` it FAILS ("GOOD NEWS"); any larger value prints "ok ... short ... as expected". Nothing bounds the shortfall from above.

- **NR-05's backpressure against the real `hps_io` handshake.** `cart-sdram-gate` models `ioctl_wait` as checked before every byte with zero latency. In the framework, `ioctl_wait` is `io_wait`, which freezes `sys_top`'s `rack` / `io_ack` (`sys_top.v:256-262`). A byte already strobed is still delivered, but the HPS cannot start the next until the falling half of the handshake completes.
  - `wr_pending` is visible to `clk_sys` two console cycles after `ioctl_wr`.
  - The HPS's next strobe needs `io_ack` to reach it and its own `io_clk` change to return through `gp_outd` / `gp_outr` (two `clk_sys` registers).
  - The wait therefore always arrives first, and the gate's zero-latency model is conservative here, not optimistic.
  - Side effect: off the die, a CHR-RAM write that finds the bus busy raises `ioctl_wait`, which briefly holds EVERY HPS I/O acknowledge. It lasts at most one write's service time; harmless.
