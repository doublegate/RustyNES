| L-1.1 | Panics unwind across `extern "C"`; `.expect` on the run path; no `catch_unwind` (§1.1, Fix 9) | FIXED | Two halves; the unwind build costs ~0.1% of retired instructions per frame (`docs/performance.md` §v2.8.0). The shipped core aborted on panic (`[profile.release] panic = "abort"`, built `--release` on every path), so `catch_unwind` would have been dead code: the libretro builds now set `CARGO_PROFILE_RELEASE_PANIC=unwind` (crate `Makefile`, `.gitlab-ci.yml` `.core-defs`, the `libretro-cross` gate). A direct `cargo build --release` bypasses all three (and the crate is the workspace's only `default-members` entry), so `build.rs` warns when the override is absent and `on_load_game` logs `cfg!(panic = "abort")` to the frontend: verified by building both ways, the log string is in the aborting `.so` and absent from the unwinding one (Copilot, #556). Then `RustyNesLibretro::contained` wraps every emulation callback (run, serialize, unserialize, reset, load, the disk and cheat mutators) in `catch_unwind`; a caught panic POISONS the core (later calls inert) and keeps the console allocated, because the frontend holds pointers into its memory: the audit's Fix 9 (`self.nes = None`) would have been the use-after-free of L-1.3. The seven `.expect`s are `let-else` returns. Test `abi_tests::a_panic_inside_a_frame_is_contained_and_the_memory_stays_valid`. Mutations: without `catch_unwind` the test binary dies (`non-unwinding panic`, SIGABRT), exactly the frontend's fate; without poisoning, and with the audit's drop-on-panic, the test fails. The `panic!` sites inside `rust-libretro` itself are "core not initialized" guards (and two null-callback checks); they fire only if a frontend calls in before `retro_get_system_info` creates the instance. That RetroArch does not is inferred from the core running in it, not traced through RetroArch's source | v2.8.0 | |
| L-1.2 | `on_load_game` ignores `_game` and requires `GET_GAME_INFO_EXT` (§1.2, Fix 10) | FIXED | `lib.rs:855` took `_game` and `:899` refused a frontend without `GET_GAME_INFO_EXT`. The cause was the binding, not only the core: `rust-libretro-sys` 0.3.2's bindgen output reduced `retro_game_info` to `{ _address: u8 }` (libretro.h forward-declares it at line 2879), so `retro_load_game`'s `Some(*game)` carried one byte; already recorded in `docs/libretro/WALKTHROUGH.md:26` as why the core used `GET_GAME_INFO_EXT`. Fixed by vendoring `rust-libretro-sys` with the generated struct blocklisted and defined by hand (`vendor/rust-libretro-sys/VENDORED.md`; maintainer decision 2026-09-25), and a fallback in `on_load_game` (data, else read `path`; FDS by extension or magic). Red first: `abi_tests::a_frontend_without_game_info_ext_still_loads_the_game`. Mutations: removing the fallback turns it red; restoring the unpatched binding fails to compile (no fields `path`/`data`/`size`/`meta`) | v2.8.0 | |
| L-1.3 | Memory maps not deregistered on unload (§1.3, Fix 5) | FIXED | RetroArch keeps a core's memory maps until the core itself is torn down (`runloop.c` `uninit_libretro_symbols` -> `runloop_system_info_free`), not on content unload, so after `retro_unload_game` its descriptors point at freed WRAM/SRAM/CIRAM. An empty map clears them: the `SET_MEMORY_MAPS` handler frees the old descriptors before reading the new count (`runloop.c:3058-3079`). Red test `abi_tests::unloading_withdraws_the_memory_maps` (last map had 3 descriptors after unload); `on_unload_game` now sends an empty map before dropping the console, and removing that call turns the test red | v2.8.0 | |
| L-1.4 | `static mut` instance, no teardown, repeated-init panic in `rust-libretro` (§1.4) | PARTIAL | `static mut RETRO_INSTANCE` / `SYS_INFO` and the never-freed instance are `rust-libretro` design, unchanged. The data-race claim needs a frontend calling the core from several threads, which the libretro API does not permit | v2.8.0 | |
