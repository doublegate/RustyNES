## New findings

Severity follows the ledger's calibration: a crash or hang that untrusted
input can reach is High with an ordinary file and Medium with a corrupt or

Low. None of these is in an existing ledger.

### NC-09: a finite-but-huge APU filter value is accepted on restore, poisons the audio, and makes the machine's own snapshot unloadable (Medium, DEMONSTRATED)

- **Where:** `rustynes-apu/src/snapshot.rs:538-539` (`read_onepole`: `prev_in`
  and `prev_out` checked by `finite_f32` only) and :582 (`held_value`, the
  same). The filter runs `coeff * (prev_out + x - prev_in)`
  (`mixer.rs:129-137`). The rollback in `Nes::restore_inner` (`nes.rs:2440-2455`)
  restores a backup taken from the running machine and asserts it succeeds.
- **Mechanism:** a value such as `-2.05e38` or `f32::MAX` is finite, so
  restore accepts it. The next samples overflow to infinity and then NaN, and
  the IIR state stays non-finite. A snapshot of that machine then carries a
  non-finite `prev_out`, which the same validator rejects. Consequences:
  1. Host audio is NaN for the rest of the session.
  2. Every save state the user takes afterwards is refused on load
     ("APU snapshot resampler field `filter.prev_out` is out of range or not
     finite").
  3. The rollback precondition is false. When any later restore fails, the
     backup's own APU section is rejected part-way through the rollback,
     after BUS and PPU, so the APU and MAP sections stay from the REJECTED
     file. That is NC-03's half-applied machine again. In debug, test and fuzz
     builds the `debug_assert!` at `nes.rs:2450-2453` panics instead.
- **Evidence:**
  - `nesprobe` (overflow-checked build), 4 of 12 ROMs:
    `nes.rs:2450 :: rolling back to this core's own snapshot failed: Err(SectionInvalid { tag: "APU ", reason: "APU snapshot resam...`,
    at APU body offsets 144, 148 and 179 (the high bytes of `hp1.prev_in`,
    `hp1.prev_out` and `held_value`) = `0xFF` / `0x7F`. The ROMs were
    `db_vrc6a`, `M9_P128K_C64K`, `M10_P128K_C64K_S8K` and
    `mapper_holymapperel_118`.
  - `apupoison` (`plain` profile, release semantics, `db_vrc6a.nes`, frame 60,
    `hp1.prev_out` = `-2.047176e38`):

    ```text
    restore: Ok(())
    the machine's own snapshot, 2 frames later, restored on a fresh console: Err("save state section APU : APU snapshot resampler field `filter.prev_out` is out of range or not finite")
    audio after: 1450 samples, non-finite 1449
    restore_quiet(later state with a bad CPU version) on the poisoned machine: Err(... CPU snapshot unsupported version 99)
      BUS : equals pre-load true,  equals the rejected file false
      PPU : equals pre-load true,  equals the rejected file false
      APU : equals pre-load false, equals the rejected file false
      CPU : equals pre-load true,  equals the rejected file false
    ```

    `f32::MAX` gives the same. `1.0e38` does not overflow (it decays), so the
    bound has to be tighter than "finite".
- **Age:** pre-existing since IMP-02 (v2.7.0). The v2.9.0 probe ran 60
  instructions after a restore and never re-restored the machine's own
  snapshot, which is the step that shows it.
- **Proposed red test:** in `apu/snapshot.rs`, restore a snapshot whose
  `hp1.prev_out` is `f32::MAX`, run `clock()` for a frame, then assert that
  `Apu::restore(&apu.snapshot())` is `Ok` (red today). Whole-machine variant in
  `nes.rs`: the same blob through `Nes::restore`, two frames, then
  `restore_quiet(&snapshot())` must be `Ok`.
- **Proposed fix:** bound `prev_in`, `prev_out` and `held_value` to a
  magnitude the mixer can produce (its output is a few units at most; a bound
  such as `|v| <= 16.0` leaves wide margin) and reject anything larger as
  `InvalidResampler`. Separately, make the rollback robust: if the backup
  ever fails, fall back to a full rebuild rather than a half-applied machine.
- **Byte-identity:** unchanged for every genuine state.

### NC-10: the header-excluded identity lets a movie, a save state or a netplay peer cross between headers that build different machines (Low, DEMONSTRATED)

- **Where:** `nes.rs:3246-3251` (`rom_identity_sha256` hashes `bytes[16..]`);
  `hardware_options.rs:455-470` (`BoardDescription`: mapper, submapper,
  mirroring, console type, DualSystem, RAM sizes, battery, trainer);
  `movie.rs:923-958` (`seek_to_start` checks identity, region and
  `BoardDescription`); `config_digest` (`hardware_options.rs:582-594`).
- **Mechanism:** the module doc states the design: two images with the same
  PRG/CHR but different headers share an identity, so the movie checks the
  `BoardDescription` "and refuses on a mismatch". Two header facts change the
  machine and are in neither the identity nor the description:
  - **The PRG/CHR split.** The same body read as 2 x 16 KiB PRG + 4 x 8 KiB
    CHR or as 1 x 16 KiB PRG + 6 x 8 KiB CHR hashes the same.
  - **Raw flags-6 bit 0 under four-screen for mappers 218 and 30.** The
    constructor re-reads it (`rustynes-mappers/src/lib.rs:1161-1173`, :1210-1219),
    but `Cartridge::mirroring` is `FourScreen` either way.
- **Evidence (`identity` probe):**

  ```text
  == mapper 218, flags6 $A8 vs $A9
    rom_sha256 equal: true  image_sha256 equal: false
    BoardDescription equal: true  (None)
    config_digest equal: true
    movie recorded on A, seek_to_start on B: Ok("Ok")
    .rns from A restored into B: Ok("Ok")
    mapper: write PPU $0000=5A, read $1000 -> A 00, B 5A
  == mapper 3, PRG/CHR split 2x16K+4x8K vs 1x16K+6x8K
    rom_sha256 equal: true ... BoardDescription equal: true ... config_digest equal: true
    prg_rom_len 32768 vs 16384, chr_rom_len 32768 vs 49152
    movie recorded on A, seek_to_start on B: Ok("Ok")
    mapper: ... read $C003 -> A E7, B AC
  ```

  (The mapper-30 pair also matched on every key; the probe's single read did
  not show its difference, so that case rests on the constructor code.)
- **Reach:** a movie replays silently on a different machine, two netplay
  peers whose dumps differ this way connect (`SessionIdentity` = identity +
  `config_digest`) and then desync, and the two images share save slots. A
  `.rns` loading across ROMs is allowed by design (NL-01), so that part is
  not the defect; the movie and netplay checks exist precisely to prevent the
  first two. Realistic dumps rarely differ only this way, hence Low.
- **Proposed red test:** in `hardware_options.rs` tests, the two CNROM images
  above: assert `BoardDescription::capture` differs (red today), and in
  `movie.rs`, assert `seek_to_start` on B is `BoardMismatch`.
- **Proposed fix:** add the PRG-ROM and CHR-ROM lengths to `BoardDescription`
  (they also enter `config_digest`), and for the mappers that read raw header
  bits, either carry the resolved wiring on `Cartridge` (for example a
  resolved mirroring rather than `FourScreen`) or add the raw flags-6 low
  nibble to the description. Both are a movie-format change (format 3 is
  new, so the maintainer may prefer to land it before v3.0.0).
- **Byte-identity:** emulation unchanged; the movie/netplay format changes.

### NC-11: a movie's `extra_scanlines` is unbounded, and playback applies it (Low, DEMONSTRATED)

- **Where:** `hardware_options.rs:360` reads `extra_scanlines` as any `u16`;
  `apply_live` (:189ff) passes it to `Nes::set_extra_scanlines`, which does
  not clamp (`nes.rs:2942`, `ppu.rs:1745`). The desktop clamps its OWN setting
  to 80 (`rustynes-frontend/src/emu.rs:127-135`, `MAX_OVERCLOCK_SCANLINES`),
  but the movie path bypasses it. The CHANGELOG says recording "runs at stock
  timing, so a recorded movie stores no overclock", so any non-zero value
  comes from a hand-built or edited file.
- **Evidence (`movieprobe`, 30 `run_frame` calls under `MoviePlayer`):**

  ```text
  extra_scanlines 0:     29 frames completed,   863,632 CPU cycles
  extra_scanlines 1000:  29 frames completed, 4,156,670 CPU cycles
  extra_scanlines 65535:  0 frames completed, 4,350,085 CPU cycles
  ```

  At 65535 every call ends on the 150,000-cycle budget (`nes.rs:712`) without
  a frame: about five times the CPU cost of a frame, with no new picture and
  the input stream advancing one record per call.
- **Proposed red test:** `Movie::deserialize` of a movie whose options carry
  `extra_scanlines = 65535` returns `BadOptions` (red today).
- **Proposed fix:** reject values above the frontend's cap in `read_from`,
  or (since a recording never stores an overclock) require 0. Moving the 80
  cap into the core next to `set_extra_scanlines` would cover every host.
- **Byte-identity:** unchanged.

### NC-12: MMC1 restores `shift_count` unbounded (Low, DEMONSTRATED in debug builds)

- **Where:** `m001_mmc1.rs:579` (`self.shift_count = data[6]`) and :440
  (`self.shift_count += 1`).
- **Effect by build:** with overflow checks, a restored `0xFF` panics on the
  next serial write ("attempt to add with overflow"). In release a value of
  5-255 wraps silently, and the next commit happens only after up to 255
  serial writes, so banking runs wrong for about 50 register updates.
- **Evidence:** `mapprobe`, the only panic site across 13,740 boards and
  about 28.8M trials: `m001_mmc1.rs:440 :: attempt to add with overflow`
  (`1.0 p2 c1 ... byte 6 = 0xff`, all MMC1 shapes). Pre-existing; the
  v2.9.8 change to this function only removed the v1 reader.
- **Proposed fix and test:** reject `shift_count > 4` (and a `shift` with
  bits above 4 set) as `MapperError::Invalid`; test: byte 6 = 5 / `0xFF` is
  refused.
- **Byte-identity:** unchanged.

### NC-13: a movie's Game Genie list is not canonicalised, so playback re-applies it every frame (Low, DEMONSTRATED)

- **Where:** `hardware_options.rs:372-379` keeps the file's code order and
  duplicates. `capture` returns the live codes in address order with
  duplicates merged, and `apply_live` (:226-236) compares the two lists in
  order. Hosts call `apply_live` once per frame during playback and
  recording (`rustynes-frontend/src/movie_ui.rs:385, :403`,
  `rustynes-mobile/src/lib.rs:2935, :2950`).
- **Evidence (`movieprobe`):**
  - file order `["SXIOPO", "AAEAULPA"]`: live order
    `["AAEAULPA", "SXIOPO"]`, and `capture == movie options` is `false`.
  - a duplicated code: the live list is `["SXIOPO"]`, and again `false`.

  The comparison therefore never converges, so every frame clears and
  re-adds every code. No emulation difference was found; it is per-frame work
  and an options record that never equals what it produced.
- **Proposed fix:** sort by address and merge duplicates in `read_from` (or
  reject a non-canonical list, in keeping with "strict").

### NC-14: three snapshot decoders report a too-long body as "truncated" (Low, DEMONSTRATED)

- **Where:** `ppu/snapshot.rs:866-867` (`r.pos != data.len()` returns
  `Truncated(r.pos)`); `rustynes-cpu/src/snapshot.rs:148` (any length other
  than 40 is `Truncated`); the mapper `load_state`s (for example
  `m001_mmc1.rs:568-572`) report `MapperError::WrongLength` for a long blob.
  v2.9.8 fixed exactly this for the APU (`TrailingBytes`, `apu/snapshot.rs:748`)
  and BUS v2 says "unexpected trailing bytes".
- **Evidence (`sections` probe, one byte appended to each section):**
  `PPU : long Err(... PPU snapshot truncated at offset 248589)`,
  `CPU : long Err(... CPU snapshot truncated: expected 40 bytes, got 41)`,
  `MAP : long Err(... mapper save state truncated: expected 18475 b...)`.
  The rejection itself is correct (and `mapprobe` found no board accepting a
  long or short state). Only the reported reason is wrong.
- Also stale in the same file: the `ppu/snapshot.rs:624` comment still says
  "a valid v1..=8 snapshot", though only v11 loads since v2.9.8.

### NC-15: `Nes::run_frame`'s `# Panics` section is false (Low, docs, STRUCTURAL)

- **Where:** `nes.rs:703-707` says it "Panics if the CPU JAMs without
  producing a frame". The loop breaks instead (`nes.rs:755-757`:
  `if self.cpu.is_jammed() { break; }`).
- **Evidence:** reading, plus `nesprobe`: restored states with the CPU
  `jammed` byte set ran `run_frame` with no panic on every ROM.
- **Fix:** say that a JAM ends the frame early, as the 150,000-cycle budget
  does.

### NC-16: a `$4017` write now sets the IRQ inhibit at once but still clears it only at the timer reset (Low, SUSPECTED)

- **Where:** `rustynes-apu/src/frame_counter.rs:212-247`. Bit 6 set: v2.9.8
  sets `irq_inhibit` on the write cycle. Bit 6 clear: `irq_inhibit` stays set
  until the reset branch copies `pending_inhibit` 3-4 cycles later (:337).
- **Mechanism:** with the inhibit set, a `$4017 = $00` write 1-3 cycles before
  the four-step IRQ step (29828-29830) keeps the old sequence's IRQ masked.
  If the inhibit bit is one latch written immediately, as v2.9.8's own reading
  of the wiki implies for the set direction, the IRQ should be raised there.
  The code's comment notes that "no source settles" the inhibit-timing
  question.
- **Evidence:** reading only. No test ROM in the suite reaches the window,
  by the CHANGELOG's own account.
- **Suggested action:** record the asymmetry as a deliberate choice in
  `docs/apu-2a03.md`, or make both directions take effect on the write. Pin
  whichever is chosen with a test that writes `$00` 1-3 cycles before 29828
  with the inhibit previously set.

### NC-17: core files cite reference-emulator source by file, function or line with no `// Provenance:` header (process: for maintainer classification, STRUCTURAL)

This is not a claim that anything was derived. The provenance rules ask that
such mentions be surfaced and classified, never deleted, and that the
tooling's record match the code. A citation of a reference emulator's source
file, line or function is the kind of statement §1 records when it is a
derivation and §3 covers when it is an oracle comparison. These files have
no header and no §1 row, so `provenance_record_audit.rs` cannot see them:

- `rustynes-apu/src/frame_counter.rs` :105, :252 ("mirroring Mesen2's
  `ApuFrameCounter::GetIrqFlag` lazy algorithm", with the file and "lines
  214-227" at :253-254), :348, :494 and :523 ("Per Mesen2 `ApuFrameCounter.h`
  lines 110-115"). v2.9.8 edited this file (the `$4017` change).
- `rustynes-apu/src/apu.rs` :216 and :816 (TriCNES function names with
  "line 4154" / "line 4218"), :859 and :987.
- `rustynes-apu/src/snapshot.rs:492`; `rustynes-cpu/src/bus.rs` :65 and :111.
- `rustynes-core/src/vs_dualsystem.rs` :44 and :171.
- `rustynes-mappers/src/homebrew_boards.rs` :1124 and :1250 ("verified against
  Mesen2 `UnRom512::InitMapper`"), with an expression quoted at :1149 and :1444.
- `rustynes-mappers/src/m019_namco163.rs:69`.

(`rustynes-core/src/bk2_interop.rs:5` describes FCEUX's `.fm2` design, a file
format, and is listed only because the same grep caught it.) All of these
were present at the v2.9.0 tag. Classification (oracle comparison vs
derivation) is the maintainer's; this audit makes no finding on it.

## Checked and found clean (no finding)

- **Mapper state decoders (v2.9.8 strict layouts).** `mapprobe`, 13,740
  boards, about 28.8M single-byte trials: one panic site (NC-12). **No board
  accepts its state with one byte appended or removed**, which confirms the
  CHANGELOG's "short, long or older blobs are refused" for every buildable
  board. No board failed to reload its own state.
- **Cross-ROM MAP sections.** `xsize`, 67,131 big-to-small pairs and 804,852
  accepted loads: no panic. The header-excluded identity therefore does not
  turn cross-size `.rns` loads into crashes.
- **Whole-machine `.rns` (BUS v2, epoch 3).** `nesprobe`, about 213k trials
  over 12 ROMs. The only panic was NC-09, and no state was slow; four "slow"
  cases on the first run were host load, re-timed in isolation at 3.8 ms a
  frame. Per-section checks (`sections`): missing sections are refused, short
  and long ones are refused (NC-14 is about the message), and a duplicated
  section is accepted, with later copies applied over earlier ones. That is
  harmless, because every copy passes the same validation.
- **`FormatTooOld` / container epoch.** `parse_header` refuses
  `format_version < 3` (`save_state.rs:489`); pinned at `nes.rs:4437`.
- **`Movie::deserialize`.** 200,000 random mutations (1-4 bytes, 1 in 7
  truncated): 106,599 decoded, 0 panics; every 50th was also seeked.
- **`Movie::seek_to_start` rollback.** A movie with different options and a
  format-2 start state: `Err(StartStateTooOld)`; the core state was
  byte-identical and the options unchanged afterwards.
- **`serialize_header_preserving` and the dirty-tail clear.** 1,961,295 random
  parseable headers (iNES 1.0, NES 2.0, dirty tails): 0 round-trip
  mismatches, and 0 mismatches after a random single-field edit (mapper,
  submapper, PRG/CHR size, battery, trainer, mirroring, region, PRG-RAM),
  0 panics.
- **`Nes::power_cycle` + `adopt_settings_from`.** 5 ROMs x 4 configurations
  (default, `Filled(0xA5)`, `Seeded`, Famicom + OAM decay + Four Score):
  framebuffer and full core state equal to a fresh boot after 120 frames.
  Two transient differences were seen right after the cycle:
  - the battery RAM, kept by design;
  - the external open-bus latch with a non-zero RAM fill. `power_cycle`
    applies the fill before `cpu.reset`, which reads the vectors, while a
    fresh boot applies it after. The latch is overwritten by the first opcode
    fetch, so nothing observable differs, and netplay peers take the same
    path.

  `Ppu::adopt_settings_from` / `Apu::adopt_settings_from` cover every
  setter the two chips expose apart from the board-derived ones.
- **Mapper 191 non-power-of-two banking.** `mirror_bank` (`mmc3_boards.rs`)
  agrees with the `Non_power_of_two_ROM_size` doubling algorithm for every
  bank count 1-599 and every bank index (0 mismatches, independent model).
- **Mapper 226.** Register decode matches `INES_Mapper_226` (`[PMOP PPPP]`:
  bit 7 PRG bit 5, bit 6 mirroring, bit 5 mode; reset clears both registers).
- **Mapper 99 layouts.** The two accepted versions are the two current
  layouts (DualSystem and UniSystem-with-RAM), not a legacy reader.
- **`apply_header_overrides` / `ines1_as_nes2`.** Read in full. The
  promotion verifies the board with `same_board`; the dirty-tail clear runs
  before the promotion. The 12 vendored rows with a non-zero submapper (210 x
  11, 185 x 1) do not depend on the zeroed RAM-size bytes the submapper
  promotion writes, because both boards size their RAM themselves.
- **Determinism / unsafe.** No `HashMap`/`HashSet`, `std::time`, `Instant`,
  `SystemTime` or `rand` in the five crates or `rustynes-gamedb`; no
  `unsafe`.
- **Not covered:** FDS and NSF state decoders (not in `mapprobe`), UNIF
  boards, the fuzz targets, the commercial suites, multi-byte corruption.
