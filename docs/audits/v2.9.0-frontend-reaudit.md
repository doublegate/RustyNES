### NF-01 — High — Lua `__gc` finalizers run with no instruction budget (DEMONSTRATED)

- **Where:** `crates/rustynes-script/src/mlua_backend.rs:1210-1236` (`arm_hook` installs a
  count hook), `:1240-1243` (`disarm_hook`), base library kept at `:1270` (`setmetatable`
  is in the always-loaded base library).
- **Mechanism:** Lua 5.4 runs a `__gc` metamethod with debug hooks switched off
  (`GCTM` clears `L->allowhook` for the call; this is Lua's own behaviour, not
  RustyNES's), so the budget hook never fires inside a finalizer. A finalizer runs (a)
  during any GC step triggered by an allocation — i.e. inside `load` / `on_frame`, which
  the desktop runs **under the emulator lock** (`app.rs:5231-5253`) — and (b) at
  `lua_close`, i.e. when the engine is dropped: **Stop** (`app.rs:5770`), **Reload** /
  load (`app.rs:5786`), mobile `unload_script` (`rustynes-mobile/src/lib.rs:1364`) and
  `load_script` replacing an engine under the bridge lock (`:1359`).
- **Probe** (`scratchpad/v290/luaprobe`, budget set to 100,000):
  - `setmetatable({}, {__gc = function() while true do end end}) for i = 1, 20000 do local t = {} end`
    → `STILL RUNNING after 10.0s -> HANG` (control `while true do end` returns the budget
    error in 0.6 ms).
  - Same finalizer, `load` returns `Ok(())` in 0.3 ms, then `drop(engine)` →
    `STILL RUNNING after 10.0s -> HANG`.
- **Failure scenario:** a shared `.lua` script (or a buggy one) freezes the desktop app
  with the emulator lock held; pressing Stop to recover hangs the winit thread instead.
  On mobile the same hang sits under the bridge mutex, so the frame loop and UI stall
  (ANR on Android).
- **Red test:** in `rustynes-script/src/lib.rs`, run on a thread with a 10 s
  `recv_timeout`: `eng.load("setmetatable({}, {__gc=function() while true do end end}) for i=1,20000 do local t={} end")`
  must return (error or Ok) — and a second test that `drop(eng)` after registering such
  a finalizer returns.
- **Proposed fix:** remove `__gc` from what scripts can set: wrap `setmetatable` at VM
  creation (same pattern as `install_budget_guards`, original captured as an upvalue)
  to reject or strip a `__gc` key, and also block `rawset` on a metatable that carries
  it (metatables are plain tables, so strip at `setmetatable` time and refuse later
  `__gc` assignment via a proxy, or simply refuse any metatable containing `__gc`,
  since Lua only honours `__gc` present at `setmetatable` time). Keep `debug` removed.
  Belt and braces: drop the engine off the emulator lock and off the UI thread.

### NF-02 — High — C-level pattern matching escapes the instruction budget (DEMONSTRATED)

- **Where:** `mlua_backend.rs:1270` loads `StdLib::STRING`; `string.find` / `match` /
  `gmatch` / `gsub` run entirely in C.
- **Mechanism:** a count hook fires only between VM instructions. Lua patterns backtrack
  (`.-`, `*`), so `s:find('.-.-.-.-b')` on a 3,000-byte subject is roughly n^4 C steps
  with zero VM instructions. The 64 MiB memory limit does not help: no allocation.
- **Probe:** `local s = string.rep('a', 3000) return s:find('.-.-.-.-b')` with budget
  100,000 → `STILL RUNNING after 10.0s -> HANG`.
- **Failure scenario:** as NF-01 — the frame callback hangs the host under the emulator
  lock; no pcall needed, and SEC-03's guards cannot see it.
- **Red test:** the probe above with a 10 s thread timeout, expecting it to return.
- **Proposed fix:** replace `string.find/match/gmatch/gsub` (and the `string` metatable
  `__index` methods, which alias the same table) with wrappers that bound subject length
  × pattern complexity (e.g. refuse patterns with more than N `-`/`*`/`+` quantifiers
  against subjects over M bytes), or run matching through a Rust implementation with a
  step counter that shares the per-frame budget.

### NF-03 — Medium — Host-side copies out of Lua bypass the 64 MiB heap limit (DEMONSTRATED for two paths)

- **Where:** `emu.drawText` `mlua_backend.rs:443-459` (queue capped at 8,192 entries by
  `push_capped`, `:88-93`, but each `text` is unbounded); `userdata.set`
  `:954-959` (no cap on count or size, persists across frames); `comm.*` send paths
  (`WsSend`, `tcp`/socket send, `MmfWrite`) `:1016-1120` push unbounded payloads, and
  the host keeps `MmfWrite` data in an unbounded map for the life of the worker
  (`script_host.rs:328`, `:371-375`).
- **Mechanism:** SEC-02 capped the Lua heap and (in review) bounded the `emu.log` line
  length, but the same "copy a 60 MiB Lua string into host memory N times" pattern is
  open on every other host-bound string.
- **Probe** (`luaprobe --bin hostmem`, default Lua limit 64 MiB):
  - `emu.drawText(0,0,s)` ×128 with an 8 MiB `s` → `host holds 1024 MiB in 128 draw cmds`.
  - `userdata.set(tostring(i), s)` ×128 → `host holds 1024 MiB in 128 keys (persists across frames)`.
  Scaling either loop (budget permits ~250k calls per frame) exhausts host memory.
- **Failure scenario:** a script OOM-kills the desktop app (or the mobile process) in a
  single frame; with `userdata` the growth also persists and, with `script-sqlite`, is
  written to disk.
- **Red test:** mirror `the_host_log_is_bounded`: after the loops above,
  `drain_draws()` text bytes and `userdata_snapshot()` bytes must each be under a fixed
  cap (e.g. 4 KiB per text, 1 MiB per value, 16 MiB total).
- **Proposed fix:** one host-memory budget per engine (per-frame for queues, persistent
  for `userdata`/MMF), charged on every copy out of Lua, with per-item length caps
  matching `MAX_LOG_LINE_BYTES`.

### NF-04 — Medium — HD-pack `hires.txt` in a zip is decompressed without a size cap (DEMONSTRATED)

- **Where:** `crates/rustynes-hdpack/src/hdpack.rs:582-587` — `archive.by_name(&hires_name)`
  then `read_to_string` with no `take()`; contrast `read_zip_entry` (`:857-869`), which caps
  image entries at 64 MiB. The folder loader reads `hires.txt` unbounded too (`:548`).
- **Probe** (`hdprobe -- zip`): a **509 KiB** zip whose `hires.txt` inflates to 512 MiB
  → `VmHWM: 545668 kB` during `HdPack::load_from_zip_bytes`. Deflate's ~1000:1 ratio
  means a few MiB of zip reaches many GiB.
- **Failure scenario:** loading a downloaded HD pack OOM-kills the desktop app; on
  mobile `load_hdpack_from_zip_bytes` (`rustynes-mobile/src/lib.rs:1274`) does the same
  with a SAF-picked zip.
- **Red test:** build the 509 KiB zip in-test; assert `load_from_zip_bytes` returns
  `None` and (on Linux) that `VmHWM` growth stays under, say, 32 MiB.
- **Proposed fix:** `e.take(MAX_HIRES_BYTES + 1)` (e.g. 16 MiB) and refuse over-limit,
  for both loaders (use `File::take` for the folder path).

### NF-05 — Medium — HD-audio tracks are decoded without a duration or total cap, and a file is decoded once per declaration (DEMONSTRATED)

- **Where:** `hd_audio.rs:156-190` (`decode_ogg_to_mono` pushes every decoded sample),
  `:192-215` (`resample_linear` then materialises the 48 kHz copy), `:480-500`
  (`decode_tracks_from_folder` decodes per declaration, so N `<bgm>` lines naming one
  file decode it N times). Called on the winit thread at `app.rs:1981`.
- **Probe** (`hdprobe`): one **315 KiB** OGG (1 h of 8 kHz silence made with
  `ffmpeg -f lavfi -i anullsrc=r=8000 -t 3600 -c:a libvorbis -q:a -2`) declared four
  times → `4 tracks ... hold 2636 MiB of f32 PCM; VmHWM: 2815852 kB`.
- **Failure scenario:** a crafted (or merely long-soundtrack) HD pack exhausts memory,
  and even a benign one freezes the UI while decoding on the winit thread. CON-03 bounded
  the *rate ratio*, not the length.
- **Red test:** decode that OGG with `decode_tracks_from_folder` and assert total PCM
  bytes stay under a pack audio budget (e.g. 256 MiB), and that a file declared twice is
  decoded once.
- **Proposed fix:** charge decoded samples (source and resampled) to the pack budget
  that SEC-01 introduced, stop decoding at a per-track cap, and dedupe by file name
  (share an `Arc<[f32]>`).

### NF-06 — High — A two-number `<overscan>` rule panics the HD compositor on every frame (DEMONSTRATED)

- **Where:** `hdpack.rs:1131-1139` parses `<overscan>` as four unbounded `u32`s;
  `HdCompositor::new` `:1781-1785` computes `NES_W.saturating_sub(left + right).max(1)`
  and keeps `ov_left`/`ov_top` as given; `composite` `:1886-1896` then indexes
  `framebuffer[(y*256+x)*4 ..]` for `y in ov_top..ov_top+crop_h`.
- **Mechanism:** a margin above 239/255 leaves `crop_h`/`crop_w` clamped to 1 while the
  origin is out of the frame, so the first index is past the end. Separately
  `left + right` is an unchecked `u32` add.
- **Probe** (`hdprobe --bin overscan`, hires `<ver>100 / <scale>2 / <overscan>300,0,0,0 / <bgm>0,0,none.ogg`
  — the `<bgm>` line only satisfies `finish`'s "pack has content" check):
  release build → `panicked at hdpack.rs:1896:33: range start index 307200 out of range for slice of length 245760`.
  `<overscan>0,4294967295,0,1` in a debug build → `panicked at hdpack.rs:1782:43: attempt to add with overflow`
  (release wraps: `overflow-checks = false`, `Cargo.toml:290`).
- **Failure scenario:** desktop release is `panic = "abort"` (`Cargo.toml:289`), so the
  first composited frame after loading such a pack **kills the app** (composite call
  sites `app.rs:10047`, `:10447`). On mobile, `composite_hd_frame`
  (`rustynes-mobile/src/lib.rs:1305-1345`) is not a `contained_frame` method: the panic
  poisons the bridge mutex while `g` is held and reaches the host as a UniFFI exception —
  on iOS a non-throwing Swift binding (`try!`) crashes, per the MOB-03 note.
- **Red test:** in `hdpack.rs` tests, load the four-line hires above from zip bytes, build
  a compositor, call `composite` on a zeroed 256x240 frame; must not panic. Plus
  `<overscan>0,4294967295,0,1` must not panic in a debug test build.
- **Proposed fix:** clamp at parse time (`top+bottom < 240`, `left+right < 256`, each
  checked add), reject otherwise; in `composite`, iterate `ov_top..min(ov_top+crop_h, 240)`
  (and the same for x) as a second line. Consider routing `composite_hd_frame` through
  `contained_frame`.

### NF-07 — Medium — A BPS `TargetCopy` grows the output without bound before any size check (DEMONSTRATED)

- **Where:** `crates/rustynes-frontend/src/patch.rs:420-432` (`TargetCopy` loop pushes
  `length` bytes; the only check, `target_rel_offset >= out.len()`, can never fire once
  the cursor trails the growing output); the declared `target_size` cap (`:380-383`) is
  compared only after the stream (`:437`). Auto-applied to any same-stem `.bps` beside a
  ROM (`app.rs:287-305`, and the menu path `:1551`).
- **Probe** (`patchprobe`, compiles the repo's `patch.rs` unmodified via `#[path]`): a
  **27-byte** BPS patch (declared target 16 bytes; one `TargetRead` byte then a
  `TargetCopy` of 2^30 from offset 0; valid CRCs) →
  `Err(Malformed ... wrong target size) in 1.29s; VmHWM: 1049496 kB`. With a length of
  2^40 it would not stop until OOM.
- **Precondition:** the source-CRC check means the patch must be built for the user's
  exact ROM, which is how patches are distributed.
- **Failure scenario:** opening a ROM with a hostile `.bps` sitting next to it hangs,
  then OOM-kills, the app.
- **Red test:** the 27-byte patch above against a 16-byte ROM must return an error
  without allocating more than `target_size` (assert `out` never exceeds it, or bound
  peak via a counting allocator).
- **Proposed fix:** before every action, `out.len() + length <= target_size` or
  `Err(oor())`; this also makes the `with_capacity(target_size)` exact.

### NF-08 — Low — Stopping a script leaves its `comm.*` backlog running; reloading blocks the UI thread on it (REASONED, not demonstrated)

- **Where:** `script_host.rs:252-275` (unbounded `mpsc::channel`, serial worker, each
  HTTP call up to 20 s, `:219`), `:293-304` (`Drop` replaces the sender, then
  `join()`s). `ScriptAction::Stop` clears `self.script` but not `self.script_host`
  (`app.rs:5769-5777`); the next load replaces it (`app.rs:5831`), running that `Drop`.
- **Mechanism:** `std::sync::mpsc` delivers every buffered message before reporting
  disconnection, so the worker drains the whole backlog (up to 8,192 requests per frame
  can be queued, `MAX_QUEUED_CMDS`) before `join` returns. Meanwhile a *stopped* script's
  HTTP requests keep going out.
- **Failure scenario:** a script that queued a few hundred requests to a slow host is
  stopped; the requests continue; loading another script freezes the window for up to
  20 s × backlog.
- **Red test:** with `script-ipc`, a local listener that accepts and never answers;
  submit 10 `HttpGet`s; `drop(host)` must return within ~1 s.
- **Proposed fix:** a cancellation flag the worker checks between jobs (set in `Drop`
  before `join`), `join_or_detach` as in MOB-04, a bounded `sync_channel`, and clear
  `script_host` on Stop.

- `unsafe` in scope: every block in `rustynes-ios/src/{ffi,audio_ring,gfx_metal}.rs`,
  `rustynes-android/src/{lib,gfx}.rs` and the frontend (`emu_thread.rs`, `clock.rs`,
  `gfx_blit.rs`, `wayland_presentation.rs`, `wasm_cheevos.rs`) carries a `// SAFETY:`
  comment consistent with the code; the raw-count mismatch in `ffi.rs` (33 vs 19) is the
  `# Safety` doc headers, not missing comments.
- ROM zip extraction (`app.rs:204-233`) bounds declared and actual entry size; IPS output
  is bounded by its 24-bit offsets; UPS checks `out_size` before allocating.
- Desktop `EmuHandle::lock` ignores poison (`emu.rs:192-207`), but the desktop release
  profile aborts on panic, so poison is unreachable in shipped builds.
- Lua RefCell re-entrancy: callback lists are snapshotted before calls
  (`mlua_backend.rs:136-146`); no borrow is held across a Lua call on the paths read.
- Android `BatterySaver.read` checks `length()` then `readBytes()` without a bound; the
  file lives in app-private `filesDir`, so not attacker-writable — not a defect.
