### NL-01 — A failed `retro_unserialize` leaves a half-applied machine (Medium-High, DEMONSTRATED)

- **Where:** lib.rs:1648-1653. `on_unserialize` calls `nes.restore_quiet(slice)` for every
  unserialize.
- **Mechanism:** `Nes::restore_quiet` (nes.rs:2347) skips the rollback backup. `restore_inner`
  (nes.rs:2230-2244) takes a backup only for the loud `restore`. That skip was introduced in
  v2.7.4 (MOB-08), and the comment at nes.rs:2224-2229 justifies it with a premise: quiet
  restores "only ever restore snapshots this core just wrote, which cannot fail these checks".
  The premise is false for libretro. Every `retro_unserialize` uses the quiet path, and that
  includes:
  - a user's "Load State" from disk;
  - a state written by an older core version (every section version is checked with
    `!=`, bus.rs:2978-3016);
  - a netplay peer's state;
  - a truncated or corrupt file.

  `apply_snapshot` mutates the machine as it goes: BUS, then PPU, APU and MAP, then CPU, then
  the clock check. A rejection partway through therefore leaves the earlier sections from the
  blob and the later ones from the running game.
- **Dual cabinet:** `VsDualSystem::restore` (vs_dualsystem.rs:362-417) does call the loud
  `Nes::restore`, but it applies main and then sub. If the sub block is rejected, the main
  console keeps its restored state and the cabinet is split across two timelines.
- **Failure scenario:** after a core update, a user presses Load State on a state whose PPU
  section version differs. The BUS section, including WRAM, is loaded; the PPU section is
  refused; `retro_unserialize` returns false. RetroArch reports that the load failed, and the
  game then keeps running on the old game's PPU/APU/MAP/CPU with the new WRAM.
- **Demonstration (C ABI, built `.so`, `tests/cabi.rs`):**
  1. Load nestest, run 10 frames, serialize (S1).
  2. Run 50 more frames and serialize (S2).
  3. In S1, set the version byte of the `CPU ` section to 0xFF.
  4. Call `retro_unserialize(S1')`. It returns `false`.
  5. Serialize again (S3).

  Result: **S3 != S2**, and the first half of S3 (the bus/PPU sections) equals S1. For the
  synthetic dual cabinet (nestest with a NES 2.0 Vs. DualSystem header), corrupting the sub
  console's CPU version gives: returns `false`; the main half equals S1 (the early state); the
  sub half equals S2 (the reference).
- **Red test:** an `abi_tests` case that serializes, runs, corrupts the last `CPU ` section
  version, and asserts that `unserialize` is false **and** that a following serialize equals
  the pre-call serialize. Add a dual variant through `VsDualSystem::restore` with the sub
  block corrupted.
- **Fix:** make the libretro restore atomic.
  - Single console: before `restore_quiet`, snapshot into a pooled `restore_backup` buffer
    with `snapshot_core_into`, and restore that buffer on failure. The cost is one snapshot
    per unserialize, about 80 µs of the measured 159 µs pair (release build, i9). Measure it
    against run-ahead before adopting.
  - Alternatively, validate every section header and version before applying anything. This
    is cheaper, but it does not catch body-level rejections.
  - Dual: `VsDualSystem::restore` needs the same all-or-nothing rule across both consoles.
- **Also note:** `restore_inner` never checks the header's ROM hash tag (`let _ = header;
  // currently informational`, bus.rs:2969). A state from a different game with the same
  section shapes is accepted in full. This is core scope, so it is recorded here only.

### NL-02 — Cartridges without a battery get a `.srm`: `SAVE_RAM` ignores `has_battery()` (Medium, DEMONSTRATED)

- **Where:** lib.rs:1584-1591 (`get_memory_data`), 1608 (`get_memory_size`), and 956-968 (the
  memory map with `RETRO_MEMDESC_SAVE_RAM`).
- **Mechanism:** the core exposes `Nes::sram()` whenever it is non-empty. The core's own doc
  on `has_battery` (nes.rs:249-258) says NROM returns 8 KiB for every image and MMC1/MMC3
  allocate RAM by default. It adds that "a host that persists save RAM to disk … must gate
  on this, or a volatile cartridge acquires a save it never had and restores stale RAM
  across power cycles". The desktop frontend gates on it (battery_save.rs:173); the libretro
  core does not.

  RetroArch persists `RETRO_MEMORY_SAVE_RAM` to `.srm` and writes it back into the pointer
  after `retro_load_game`. That persist-and-reload behaviour is libretro's documented use of
  SAVE_RAM; the RetroArch side was not traced in source.
- **Measured over `tests/roms` (`tests/sram.rs`):**
  - **581 images** expose non-empty SAVE_RAM with no battery bit: 571 at 8 KiB, 8 at 64 KiB
    and 2 at 128 B.
  - Only 68 of the images that expose SAVE_RAM have a battery.
  - nestest (battery bit clear): `retro_get_memory_size(RETRO_MEMORY_SAVE_RAM)` = **8192**
    through the built `.so`.
  - FDS images do the same: `has_battery()` is false, and the 32 KiB adapter RAM
    (fds.rs:2123-2128) is exposed as SAVE_RAM.
- **Failure scenario:** any MMC3 game with volatile work RAM (for example the local
  *Mega Man 3* dump, which exposes 64 KiB SAVE_RAM without a battery) gets a `.srm` on
  close. Its WRAM is restored on the next boot, where hardware would power on without it.
  Games that check a RAM signature to tell a warm boot from a cold one behave differently.
  Every such game also leaves spurious save files, and cloud sync uploads them.
- **Documentation contradicted:** `docs/libretro/advanced_features.md:11` says "when
  non-empty (battery-backed carts only)".
- **Red test:** load nestest through the C ABI and assert that
  `retro_get_memory_size(RETRO_MEMORY_SAVE_RAM) == 0` and that no `SAVE_RAM` descriptor is
  registered. Do the same with the battery bit set, and assert 8192.
- **Fix:** gate both the legacy pointer and the `RETRO_MEMDESC_SAVE_RAM` descriptor on
  `nes.has_battery()`. RetroAchievements can still see volatile PRG-RAM if it is registered
  as a descriptor *without* the `SAVE_RAM` flag.

### NL-03 — FDS in-game saves (disk writes) are never persisted by the libretro core (Medium, STRUCTURAL; not run with a saving game)

- **Where:** the whole crate. Nothing calls `Nes::disk_is_dirty`, `disk_image_bytes` or
  `clear_disk_dirty` (nes.rs:1538-1556). A grep of `crates/rustynes-libretro/src` finds no
  disk-save path at all.
- **Mechanism:** an FDS game saves by writing to the disk image in the mapper. The desktop
  flushes the dirty disk to `fds_saves_dir` (emu.rs:1659-1685). The libretro core exposes
  only the 32 KiB RAM as SAVE_RAM (NL-02), and that RAM is not where FDS saves live. When
  content closes, the disk writes are lost.
- **Failure scenario:** a user saves in-game in *Zelda no Densetsu* (FDS), quits RetroArch,
  and the save is gone. Only save states survive.
- **Not demonstrated:** no disk-writing FDS title was driven here. The finding rests on the
  missing code path and on the desktop implementation showing what is needed.
- **Red test:** load an FDS image through the ABI, write disk bytes through the mapper (or
  with a scripted BIOS save), unload, reload, and assert the bytes survive through whatever
  persistence interface is chosen.
- **Fix:** expose the dirty disk through a persistence channel RetroArch writes. The two
  usual ways are the disk image, or an IPS-style diff, as SAVE_RAM when `disk_side_count() > 0`
  (which also replaces the 32 KiB RAM exposure). Either way it must be restored on load
  before the first `retro_run`. Consult `libretro.h` for the SAVE_RAM lifecycle.

### NL-04 — `.info` capability flags and description contradict the core (Low, DEMONSTRATED by reading)

- `rustynes_libretro.info` says `core_options = "false"`, but the core declares a core option
  through `SET_VARIABLES` (lib.rs:280-296, 420-431). The C-ABI run counted one
  `SET_VARIABLES` call.
- `docs/libretro/UPSTREAM_SYNC.md:89-96` records that this exact class of mismatch
  (`disk_control` false while disk control existed) shipped before, and that capability flags
  are asserted "by hand". `libretro_info_audit.rs` checks only the licence, the version and
  the extensions.
- The `description` still says "a strict, lockstep master-clock scheduler at PPU-dot
  resolution". That is the scheduler v2.0.0 retired, and it is the same claim L-3.5b removed
  from `architecture.md`.
- **Red test:** extend `libretro_info_audit` so that `core_options` must be `"true"` iff the
  crate source contains `set_core_options` or `SET_VARIABLES`, and so that a list of retired
  phrases is rejected in `description`.
- **Fix:** set `core_options = "true"` and rewrite the description. The upstream copy follows
  at v3.0.0, per the maintainer's sync rule.

### NL-05 — Core options are declared once per process, not once per `retro_set_environment` after a deinit (Low, DEMONSTRATED at the ABI; user impact SUSPECTED)

- **Where:** `rust-libretro` `retro_set_environment` calls `set_core_options` only when
  `initial`, which is the first environment ever set on the process-global instance (never
  reset, L-1.4). The core relies on that path (lib.rs:420).
- **Demonstration:** `retro_deinit`, then `retro_set_environment`, then `retro_init` produces
  **no** second `SET_VARIABLES` (the count stays 1). The log interface, pixel format,
  descriptors and controller info *are* re-sent, because they are in `on_set_environment`.
- **Failure scenario (inferred, not traced in RetroArch):** a frontend that keeps the library
  loaded across a deinit and re-init, and drops its option set at deinit, will not have
  `rustynes_four_score` for the second session. Examples are static builds and any host that
  does not `dlclose`. `GET_VARIABLE` then fails, and the Four Score stays off with no menu
  entry to change it.
- **Red test:** the ABI harness counts `SET_VARIABLES` across deinit, set_environment and
  init, and expects 2.
- **Fix:** declare the variables from `on_set_environment` as well (libretro.h allows a
  repeat call with the same number of options), or on every call where the callback changes.

### NL-06 — `SAVE_RAM` memory descriptor misdescribes the address space for SRAM larger than 8 KiB or of non-power-of-two size (Low, DEMONSTRATED structurally)

- **Where:** lib.rs:956-968 registers `{start: 0x6000, select: 0, disconnect: 0, len: sram_len}`.
- **Contract:** `libretro.h` (retro_memory_descriptor, line 2070-2075) says that with
  `select == 0` "each byte is assumed mapped exactly once. In this case, 'len' must be a
  power of two". Bank-switched memory needs both `len` and `select` non-zero (TODO at 2129-2132).
- **Measured (`tests/sram.rs`):**
  - 21 images expose more than 8 KiB of SRAM. *Mega Man 2/3-6* and *Metroid* have 64 KiB
    (MMC1/MMC3 default allocation). UNROM-512 and Holy Mapperel have 32 KiB.
  - 3 images expose **73,728 bytes** (*Legend of Zelda*, *Maniac Mansion*,
    *Kirby's Adventure*), which is not a power of two.

  As registered, a 64 KiB SRAM claims `$6000-$15FFF`, past the 16-bit bus. A 32 KiB SRAM
  claims `$6000-$DFFF`, over PRG-ROM, when the hardware has an 8 KiB window at
  `$6000-$7FFF`. The only exception is FDS, whose RAM really does span `$6000-$DFFF`.
- **Failure scenario:** a RetroAchievements or cheat-search read at `$8000-$DFFF` resolves to
  SRAM bytes instead of ROM. The effect on a non-power-of-two `len` depends on the frontend,
  which was not traced.
- **Red test:** a descriptor-shape test that registers every `tests/roms` image and asserts
  `len.is_power_of_two()` and `start + len <= 0x8000` for the CPU-space SAVE_RAM descriptor
  (FDS excepted).
- **Fix:** describe the 8 KiB window only (`len = 0x2000`, with `offset` at the current
  bank if the core can report it), or leave SRAM larger than 8 KiB out of the CPU address
  space. The whole buffer stays available through `RETRO_MEMORY_SAVE_RAM` for persistence.

### NL-07 — Disk labels are unreachable: only the v0 disk-control interface is registered (Low, DEMONSTRATED)

- **Where:** lib.rs:1392 calls `enable_disk_control_interface()`, which sends
  `SET_DISK_CONTROL_INTERFACE`. The v0 struct (`rust-libretro` contexts.rs:93-103) carries no
  `get_image_label`, `get_image_path` or `set_initial_image`.
- **Demonstration:** the ABI run counted `SET_DISK_CONTROL_INTERFACE` x1 and
  `SET_DISK_CONTROL_EXT_INTERFACE` x0, with the fake frontend reporting interface version 1.
  `on_get_image_label` and `on_get_image_path` (lib.rs:1719-1738) are therefore dead code.
- **Documentation contradicted:** `advanced_features.md:78` says the labels surface in
  RetroArch's Disk Control menu.
- **Fix:** call `enable_extended_disk_control_interface()`, falling back to v0. Doing that
  makes the L-1.5 label hazard reachable, so pair the change with a fix of the label copy.
  The label callback is in `rust-libretro`; the fix is either to vendor it or to use a
  label that is always short. Alternatively, correct the doc. **Red test:** the harness
  asserts the ext interface is registered when the frontend reports version 1 or higher.

### NL-08 — Vs. System games in the libretro core: no coin, service or DIP input, and no DB palette (Medium, DEMONSTRATED for the palette and the coin effect)

- **Where:** the load path is `Emu::from_rom` alone (lib.rs:833). The desktop's
  `apply_vs_db` (frontend app.rs:1388-1407) applies `set_vs_ppu_type` (from the SHA-keyed
  `vs_db`) and `set_vs_dip`, and binds `insert_coin` / `set_vs_service` to keys
  (app.rs:4943, 6590). The libretro crate calls none of `insert_coin`, `clear_coin`,
  `set_vs_service`, `set_vs_dip` or `set_vs_ppu_type` (grep).
- **Demonstration (`tests/vs.rs`, 7 local Vs. UniSystem dumps that are in `vs_db`):**
  - **Palette, 7 of 7:** applying the DB's PPU type (2C04-0001..0004) changes the framebuffer
    after 900 frames. The libretro core renders iNES-1.0 Vs. dumps with the parser's
    default 2C03 LUT. `vs_db.rs:5-10` calls that default the wrong colours.
  - **Coin, 6 of 7:** a coin at frame 120 changes the game's WRAM relative to the same run
    without one. A libretro user has no input that produces a coin.
  - **Limit of the evidence:** that the games are *unplayable* without a coin was **not**
    established. Start alone does change state in 6 of 7 runs, and the difference could be
    attract/credit logic. Only "the coin input matters and cannot be produced" is
    demonstrated.
- **Why it matters:** the `.info` description advertises "true RGB Vs. System arcade
  boards", and L-S1 closed with "nothing else a user must set was found".
- **Red test:** load a Vs. image whose header is edited to iNES 1.0 and whose SHA is in
  `vs_db` (or use a committed CC0 Vs. test ROM if one exists), and assert
  `nes.vs_ppu_type()` equals the DB's. Also drive a coin input descriptor through the ABI and
  assert that the `$4016` coin bit reads 1.
- **Fix:**
  - Apply `vs_db` (the PPU type, plus the DIP default) after `Emu::from_rom` for single and
    dual.
  - Map coin 1/2 and service to libretro joypad buttons on Vs. carts only. Select, L and R
    are the usual choice. Use a short hold of the kind `VS_COIN_HOLD_FRAMES` implements.
  - Optionally add a DIP core option.

### NL-09 — The dual-cabinet serialize path allocates and snapshots thumbnails on every call (Low / Info, MEASURED)

- **Where:** lib.rs:1628 `core.serialize_buffer = dual.snapshot()`, and
  `VsDualSystem::snapshot` (vs_dualsystem.rs:338-354), which uses the full `Nes::snapshot`
  **with the THM thumbnail** for both consoles.
- `VsDualSystem::restore` uses the loud `Nes::restore`, which takes a full backup snapshot of
  each console first.
- **Measured (release build, `tests/sram.rs`):**
  - a dual state is **645,529 B** against 261,300 B for a single console;
  - one serialize+unserialize pair costs **740 µs** against 159 µs, about 4.4% of an NTSC
    frame per run-ahead frame, spent entirely in the wrapper and container;
  - every call makes a fresh ~645 KB allocation.
- **Documentation contradicted:** `architecture.md` says the buffers are "sized once so the
  frame loop does not allocate".
- **Fix:** a `snapshot_core_into`-style path for the dual container (no THM, into the pooled
  buffer). Folding this into NL-01's atomicity fix would give the dual restore the pooled
  backup as well. Subject to the project's A/B adoption rule; this measurement is a single
  run and is not the evidence that rule requires.

### NL-10 — `retro_serialize` returns true when `size` is below `retro_serialize_size()` (Info)

- lib.rs:1632 succeeds whenever `size >= payload`. `libretro.h:3903-3904` says the function
  "should return false" if `size is lower than retro_serialize_size()`. It is harmless today:
  frontends pass the reported size. It could be tightened by returning false when
  `slice.len() < core.serialize_size`.
