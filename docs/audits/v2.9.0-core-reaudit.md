## How this was checked

- Every ledger row: the fix site and regression test located by grep and cited;
  tests run where cheap:
  - `cargo test -p rustynes-mappers`: all targets green (lib 769 passed;
    `battery_sram_exposed`, `documented_wram`, `hardwired_mirroring`,
    `prg_ram_window_open_bus` green).
  - `cargo test -p rustynes-apu -p rustynes-ppu -p rustynes-cpu`: all green.
  - `cargo test -p rustynes-ppu --lib snapshot`: 24/24, including
    `a_corrupt_sprite_count_is_rejected_not_indexed`,
    `an_out_of_range_raster_position_is_rejected`,
    `every_ppu_counter_and_index_is_bounded_on_restore` and
    `a_restored_extra_lines_countdown_is_clamped_to_the_live_knob`.
  - `cargo test -p rustynes-core --lib -- a_restored_ an_out_of_range a_sachen section_iter n163 namco`:
    12/12.
  - NOT run: the `--features test-roms` ROM suites (holy_mapperel for §5.4,
    AccuracyCoin), and the fuzz targets.
- New findings came from reading the code and from four throwaway probe
  programs. They sit OUTSIDE the repository, in
  `scratchpad/v290/probe/`, with path dependencies on the repo crates and their
  own target dir. They were built with `overflow-checks` and `debug-assertions`
  on, and also as a `plain` profile with both off, which gives release
  semantics.
  - `probe`: every constructible mapper (296 board configurations from iNES
    mapper 0-4095 x CHR-ROM/CHR-RAM, at four PRG/CHR sizes). Each gets a
    `save_state`. Then, one at a time, each byte in the first 256 and the last
    96 of that state is set to `FF`/`80`/`41`/`09`, the result goes to
    `load_state`, and an accepted state is exercised through reads, writes and
    hooks under `catch_unwind`. About 1.3M trials per size.
  - `nesprobe`: the same single-byte corruption at the whole-machine level:
    every non-framebuffer byte of a real `.rns`, `restore` or `restore_quiet`,
    then 60 instructions. Run for mappers 0, 1, 4, 5, 19, 24, 69, 85 and 111,
    about 250-450k trials each.
  - `fdsprobe`: FDS device state corruption.
  - `writes`: 6,000 random register writes, reads and hooks per board, for
    every mapper x submapper 0-15 x CHR-ROM/RAM x seven PRG/CHR sizes (13,376 +
    16,368 boards built). No save states are involved.
  - `partial`, `clockwrap`: two targeted demonstrations.
- Provenance firewall: no other emulator's source was opened. Only this repo's
  code and its vendored documentation were read.

## New findings

Severity follows the ledger's own calibration: a crash or hang that untrusted
input can reach is High when it needs no crafting beyond an ordinary file and
Medium when it needs a corrupt or crafted file. None of these findings is in
the existing ledger.

### NC-01: seven multicart mappers panic on an undersized or odd-sized PRG-ROM (Medium, DEMONSTRATED)

- **Where:** `rustynes-mappers/src/multicart_discrete.rs`:
  - :425 (`Multicart61`) and :582 (`Multicart62`), the 32 KiB path.
  - :1065 (`Multicart202`) and :1433 (`Multicart212`), `prg_32k_mode`.
  - :1929 (`Multicart58`), `prg32_mode`.
  - :3402 (`DiscreteMapper::prg_32k`, which serves mappers 46 and 57).
- **Mechanism:** each site computes the bank count as
  `(prg_rom.len() / PRG_BANK_32K).max(1)` (or `/16K` for 202/212), reduces the
  bank modulo that count, and then indexes `prg_rom[bank * 32K + off]` with
  `off` up to `0x7FFF`.
  - With a 16 KiB PRG-ROM, the count is clamped to 1 and bank 0 is used, so any
    `off >= 0x4000` is out of bounds.
  - For 202 and 212, an odd 16 KiB-bank count also fails: 48 KiB (count 3) and
    80 KiB (count 5) yield an even `lo16` of `count - 1`, and the second half
    of the 32 KiB window runs past the end.
  - The constructors do not reject these sizes.
- **Failure scenario:** someone loads an iNES file that declares mapper 46, 57,
  58, 61, 62, 202 or 212 with 1 x 16 KiB PRG (for 202/212, also 3 x or 5 x
  16 KiB). This is an undersized dump, a hack, or a header typo. The first
  write that selects 32 KiB mode, followed by a fetch from `$C000-$FFFF`,
  panics:
  - Native: the emulator thread dies.
  - wasm32: the tab aborts.
  - libretro: the panic is contained, but the core fails.
- **Evidence:** probe `writes`, with 6,000 random writes per board. Every other
  constructible board and size passed. Sample output:

  ```text
  multicart_discrete.rs:3402 :: index out of bounds: the len is 16384 but the index is 25301   (57.6, prg16=1)
  multicart_discrete.rs:425  :: index out of bounds: the len is 16384 but the index is 29124   (61.x, prg16=1, CHR-RAM)
  multicart_discrete.rs:1433 :: index out of bounds ...                                        (212, prg16=3 and 5)
  multicart_discrete.rs:1065 :: index out of bounds ...                                        (202, prg16=1 and 5)
  ```

- **Proposed red test:** a new `rustynes-mappers/tests/undersized_prg.rs`. For
  each of the seven mappers, at PRG sizes 16/48/80 KiB, it builds the board,
  writes every value 0-255 to every register address class, and after each
  write reads all of `$8000-$FFFF`. It must not panic.
- **Proposed fix:** index with `% prg_rom.len()`, as MMC3 already does
  (`m004_mmc3.rs:484`). This is also the hardware-faithful answer, because a
  16 KiB part in a 32 KiB window mirrors. The other option is to reject the
  size at construction, but that refuses files that work today until they hit
  32 KiB mode.
- **Byte-identity:** unchanged for every image that runs today. The change
  affects only accesses that currently panic.

### NC-02: GTROM (mapper 111) restores its bank registers unvalidated, so a corrupt save state panics after an accepted load (Medium, DEMONSTRATED)

- **Where:** `rustynes-mappers/src/homebrew_boards.rs:643-645` (`load_state`)
  assigns `prg_bank`, `chr_bank` and `nt_bank` raw from the blob. They are then
  used unmasked:
  - :570: `prg_rom[prg_bank * 32K + ..]`
  - :586: `chr_ram[chr_offset]`, where `chr_bank * 8K`
  - :587: `nt_ram[nt_offset]`, where `nt_bank * 4K`
- **Mechanism:** this is the IMP-01 class, a deferred out-of-bounds read,
  inside a mapper section. The v2.7.0 fuzz target cannot reach it because its
  base machine is NROM (`fuzz/fuzz_targets/save_state.rs:59`).
- **Failure scenario:** a user loads a corrupt or edited `.rns` (or a RetroArch
  `.state`) for a GTROM game.
  - `Nes::restore` returns `Ok(())`. The v2.7.4 rollback does not help, because
    the panic comes on the next tick, not during the restore.
  - The next CPU fetch from `$8000+` panics.
- **Evidence:** at the whole-machine level (`nesprobe 111`, through the LOUD
  `Nes::restore`):

  ```text
  homebrew_boards.rs:570 :: index out of bounds: the len is 32768 but the index is 8372319   (blob off 251011 = 0xff)
  ```

  At the mapper level (`probe`), the same panic also fires at :586 and :587
  for bytes 2 and 3.
- **Scope:** the mapper-level sweep corrupted each byte in the first 256 and
  the last 96 bytes of every constructible board's state (296 configurations,
  four sizes). Only mapper 111 produced an index panic. The whole-machine sweep
  of 8 other mappers (NROM, MMC1, MMC3, MMC5, N163, VRC6, FME-7, VRC7) found
  none. So the rest of the mapper surface looks robust to single-byte
  corruption. Multi-byte corruption was not tried.
- **Proposed red test:** in `homebrew_boards.rs` tests, save a GTROM state, set
  byte 1 to `0xFF`, and assert `load_state` returns `Err`. The alternative is
  to assert that `cpu_read(0x8000)` does not panic.
- **Proposed fix:** reject `prg_bank >= prg_rom.len() / 32K`, `chr_bank > 1`
  and `nt_bank > 1` as `MapperError::Invalid`. `update_register` can never
  produce those values (:543-549).
- **Byte-identity:** unchanged. Only corrupt blobs are affected.

### NC-03: a failed QUIET restore leaves a hybrid machine, and libretro routes untrusted user state files through it (Medium, DEMONSTRATED)

- **Where:** `rustynes-core/src/nes.rs:2225-2228`. The rollback backup is taken
  only when `clear_rewind` is set. The justifying comment says quiet restores
  "only ever restore snapshots this core just wrote, which cannot fail these
  checks". That is false for `rustynes-libretro/src/lib.rs:1649`
  (`on_unserialize` then `nes.restore_quiet(slice)`), which receives every
  RetroArch state load: a user's slot file, a file from another core build, or
  a corrupt one.
- **Mechanism:** `apply_snapshot` mutates in stages. The BUS, PPU, APU and MAP
  sections are applied first (`nes.rs:2311`), then the CPU section, then the
  clock check. An error in a later stage returns with the earlier stages
  applied. MOB-08 fixed this for loud restores only.
- **Failure scenario:** someone loads a state whose CPU section is
  version-mismatched or corrupt.
  - `retro_unserialize` returns `false`.
  - RetroArch keeps running a machine whose PPU, APU, mapper and RAM come from
    the file and whose CPU comes from the running game.
  - The F-05 clock check never ran, because the error came first.
- **Evidence:** `partial` probe. It takes a 3,000-frame snapshot, flips the CPU
  section's version byte, and applies it to a machine at frame 5:

  ```text
  restore_quiet: Err("save state section CPU  version 123 not supported (chip supports 4)")
    before: frame 5 bus cycle 119123
    next run_frame: cpu master clocks advanced 1800036, frame now 3000   (no frame completed)
    after : frame 3000 bus cycle 89462222            <- bus/PPU from the rejected file
  restore:       Err(same)
    after : frame 6  bus cycle 148907                <- loud path rolled back correctly
  ```

- **Proposed red test:** in `nes.rs` tests, a copy of MOB-08's test that calls
  `restore_quiet` with a CPU-version-corrupted blob and asserts `bus().cycle()`
  and `frame()` are unchanged. It is red on the current tree.
- **Proposed fix:** any one of these.
  1. Have libretro call the loud `restore`, or a new `restore_untrusted`, and
     keep `restore_quiet` for the core's own run-ahead and netplay blobs. The
     per-call backup costs one snapshot, and RetroArch's own run-ahead goes
     through this same callback, so measure it.
  2. Make `apply_snapshot` validate every section's header and version before
     mutating anything.
  3. At minimum, correct the comment.
- **Byte-identity:** unchanged. Only failure paths are affected.

### NC-04: F-05's clock-skew check accepts two clocks near `u64::MAX`, and the CPU clock then wraps and freezes the PPU for good (Low, DEMONSTRATED)

- **Where:** `bus.rs:824-837` checks only
  `master_clock.abs_diff(ppu_clock) <= 1024`. The CPU advances with
  `wrapping_add` (`rustynes-cpu/src/cpu.rs:446, 707, 751`). The PPU catch-up
  loop is `while self.ppu_clock + ppu_div <= target` (`bus.rs:4665`).
- **Mechanism:** a crafted state sets both clocks about 20,000 master clocks
  below 2^64. After the restore:
  1. `master_clock` wraps to a small value.
  2. `ppu_clock` stays near 2^64.
  3. The loop condition is false forever, so the PPU never ticks again.

  No genuine state can get there, since reaching 2^64 master clocks takes
  about 27,000 years of emulation.
- **Evidence:** `clockwrap` probe, the same with and without overflow checks:

  ```text
  restore -> Ok(()) mc 18446744073709531615 frame 3
  run_frame 0 (frame 3, mc 1780035, ...) -> returned
  run_frame 2 (frame 3, mc 5380131, ...) -> returned     <- frame counter frozen at 3
  ```

  This is the state F-05 set out to reject: "one far AHEAD meant the PPU never
  ticked again". It is not a hang, because `run_frame` returns on its CPU-cycle
  budget. The display freezes, and NMI never fires again.
- **Proposed red test:** in `nes.rs` tests, next to
  `a_restored_cpu_ppu_clock_skew_is_rejected`, shift both clocks by
  `u64::MAX - 20_000 - mc` and assert `restore` returns `Err`.
- **Proposed fix:** also reject `master_clock` above a plausibility ceiling.
  2^62 is still millennia of emulation.
- **Byte-identity:** unchanged.

### NC-05: a Vs. DualSystem restore is not atomic across its two consoles (Low, by reading; not run)

- **Where:** `rustynes-core/src/vs_dualsystem.rs:391-392`:
  `self.main.restore(main_block)?; self.sub.restore(sub_block)?;`.
- **Mechanism:** each `Nes::restore` rolls itself back on failure, but a valid
  main block followed by a bad sub block leaves main restored and sub running
  the old game. The cabinet is then a pair from two timelines, sharing a WRAM
  that is re-converged only on the success path (:403-412).
- **Reach:** libretro calls `dual.restore(slice)` for these four boards
  (`rustynes-libretro/src/lib.rs:1651`).
- **Proposed red test:** a `vs_dualsystem_synth` test that snapshots the pair,
  corrupts the CPU version byte inside the sub block, restores, and asserts
  that main's `frame()` is unchanged. Not written. The claim rests on the three
  lines cited.
- **Proposed fix:** snapshot `main` before restoring it, and restore that
  backup if the `sub` restore fails.
- **Byte-identity:** unchanged.

### NC-06: mapper 286 restores its DIP value unbounded, and the register decode overflows (Low, DEMONSTRATED in debug builds only)

- **Where:** `rustynes-mappers/src/bmc_simple.rs:486` does
  `self.dip = data[c + 3]` with no bound. Line :380 then evaluates
  `addr & (1u16 << (self.dip + 4))`.
- **Effect by build:**
  - In builds with overflow checks (dev, test, fuzz), a restored `dip >= 12`
    panics:
    - "attempt to shift left with overflow" (from `0x80` / `0x41`);
    - "attempt to add with overflow" (from `0xFF`).
  - In release, `dip + 4` wraps and the shift amount is masked to 4 bits, so
    there is no panic, only a wrong decode.
- **Evidence:** the probe at byte 48 of the state
  (`286/true byte 48 = 0x80`, `= 0xff`).
- **Proposed fix:** reject `dip` values the board cannot hold on restore.
- **Byte-identity:** unchanged.

### NC-07: the FDS audio `cycle_prescaler` is restored unbounded (Low, debug builds only, DEMONSTRATED)

- **Where:** `rustynes-mappers/src/fds.rs:1156` restores
  `cycle_prescaler = src[off]` raw. Line :1021 is `self.cycle_prescaler += 1`,
  so `0xFF` overflows.
- **Effect by build:**
  - With overflow checks: a panic (`fdsprobe`: "fds.rs:1021 :: attempt to add
    with overflow", state offset 41108 = `0xFF`).
  - In release: it wraps to 0, and one wave or modulation clock lands up to 16
    cycles late. That is audibly nil, but it is output from an out-of-range
    state.
- **Other FDS findings:** none from about 3k single-byte patches of the FDS
  state, covering the audio tail, registers and the disk tail. Reading the code
  also found no reachable panic in `load_disk_tail` (`fds.rs:2025-2090`). On
  wasm32, `saved_sides * FDS_SIDE_LEN` can wrap, but the length check and the
  cursor wrap identically in release, so the result is consistent. It only
  panics under overflow checks.
- **Proposed fix:** reject `cycle_prescaler >= 16`.
- **Byte-identity:** unchanged.

### NC-08: `docs/frontend.md` still describes the Zapper temporal-light model as default-off (Low, docs)

- **Where:** `docs/frontend.md:1373-1393` says "(opt-in)", "**default off**"
  and "It stays opt-in because there is no pass/fail light-gun test ROM".
- **Why it is wrong:** the model has been default-on since v2.3.6
  (`bus.rs:947-949`, `nes.rs:1631`). §4.7 fixed the rustdoc and missed this

- **Fix:** amend the passage to record the v2.3.6 promotion and its reason,
  "the frame model made a Duck Hunt hit impossible", as `nes.rs:1636-1638`
