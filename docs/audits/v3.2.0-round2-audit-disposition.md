# v3.2.0 Round 2 audit -- disposition

What was done with each of the 61 findings in
[`v3.2.0-round2-audit-report.md`](v3.2.0-round2-audit-report.md). That report
came with an unpushed AI-agent branch (`agy/perf_impr`, also `codex_sec`) that
had already applied most of them. The branch was not merged: its code was
imported as one commit (`bb66f0af`) on the v3.2.0 consolidation branch, and
every change in it was then read against the code it replaced. The commits
cited below are on that branch.

**Verdicts.** KEPT: the import's change is right as written (or needed only
documentation). FIXED: the change was right in intent and wrong in detail;
the cited commit corrects it, with a test that fails without the correction.
REVERTED: the change made things worse, and the pre-import code is back.
REJECTED: the finding's premise does not hold. CHANGED, UNVERIFIED: as in
the [README](README.md#verdicts) -- changed, but no gate on this machine can
build it. UNTRIAGED: the import never
applied it; the finding has not been checked against the code and must be
re-derived before anyone acts on it. DEFERRED: real, or plausibly real, and
left for a later release with a reason.

**Calibration.** The pattern of the earlier audits held for the sixth time:
the Rust findings were usually real, and the fixes often wrong in detail. Of
the 43 applied changes, the test suites caught two: the commercial-dump
oracle caught the MMC5 IRQ (MAP-R2-07) and the dump coverage sweep the FDS
audio rounding (MAP-R2-03); the full run (3,631 tests, with test ROMs and
commercial dumps) passed everything else. Every other defect below was found
by reading the change against the code it replaced, and each now has a test
that fails without the correction. The report's
self-certification ("clean-room", "certified", "100% bit-accurate") is
recorded at the top of the report as unverified; two of those claims were
tested and are false (CORE-R2-02, MAP-R2-07).

## Core

| ID | Verdict | What was done |
| --- | --- | --- |
| CORE-R2-01 | FIXED | Real, and confined to the `irq-timing-trace` diagnostic (the Lua and event-breakpoint taps already classify by the fetched vector): the unified dispatch enters `service_interrupt` with the IRQ vector for both kinds, so `vector == NMI_VECTOR` was never true and every NMI was traced as an IRQ. The report's fix, `kind` from the fetched vector, contradicts `ServiceEvent`'s documented split (`kind` the request, `vector` the fetch, so a hijacked IRQ or BRK is IRQ-kind at `$FFFA`) and the committed service goldens, which is the likeliest reading of the agy branch's "broke determinism". v3.3.0 passes whether an NMI was pending when the sequence began: the two NMI ROMs' service traces regain their NMI rows (5 and 7, as committed), and `irq_trace_fixture.rs` now checks the kinds against the Mesen2 traces beside it: a trace has an NMI-kind service event if and only if Mesen2 logged an `nmi_svc` for that ROM, and every NMI-kind event fetched `$FFFA`. It compares presence, not positions or counts (the two label hijacks differently and capture different windows); the old code fails it on both ROMs. That fixture needs `irq-timing-trace`, which standard CI does not enable. The diagnostic goldens themselves have drifted from the core since they were committed and are not re-blessed here. |
| CORE-R2-02 | FIXED | The "100% bit-accurate" shortcut read ROM where mappers 228 and 235 float the bus. Replaced by a per-board `may_unmap_prg_rom` flag, a debug-build contract check and a sweep over every mapper (`5a38c02b`). |
| CORE-R2-03 | REJECTED | Measured in v3.3.0 (`docs/performance.md`, "Round 2 CPU and bus candidates"): two plain and two aligned-build A/Bs. Aligned, nestest is about 1.2-2.1% faster in both runs, but palette changes sign (-0.78%, then +1.44%), and the second run's control reaches 4.3%: mixed-sign, so not adoptable. Not taken as dead-code removal either: `snapshot.rs` serialises the latches it stops updating, so save-state bytes would change though no frame does. |
| CORE-R2-04 | REJECTED | `Cpu::dispatch` is indeed not inlined (a separate symbol in a release binary, v3.3.0), so `*cycles = N` is a real store. But it is one store and one load per instruction, about 10,000 instructions a frame against a frame cost near 4 ms whose every cycle catches the PPU up and performs a bus access: an upper bound near 0.25%, below what `ab_check.sh` resolves, for a rewrite of all 256 match arms. Not worth an A/B. |
| CORE-R2-05 | REJECTED | Slower. Measured in v3.3.0 (same section): plain builds change sign between runs, and both aligned runs measure a consistent 0.8-3.6% slowdown on all four workloads, outside every control. |
| CORE-R2-06 | REJECTED | Its premise is that declaration order is layout. `SystemBus` has no `#[repr]`, and rustc reorders the fields of a `repr(Rust)` struct as it chooses, so moving declarations guarantees nothing about which fields share a cache line (v3.3.0). |
| CORE-R2-07 | FIXED | The `Nes` doc said "controller stub"; it now names the bus and what it holds (v3.3.0). |

## MiSTer RTL

| ID | Verdict | What was done |
| --- | --- | --- |
| RTL-R2-01 | REJECTED | Re-derived with a bit-exact model of `audio_dc_block.sv`'s recurrence over 3,000 adversarial sequences (full-scale toggles, random levels, square waves, long DC then a full step): `y_next` peaked at 2,147,418,112, a bare full-scale step from rest, 65,535 below `INT32_MAX`. The overflow needs `y` near `+SAT_HI` while `x_prev` is 0, and getting `x_prev` back to 0 after any rise pulls `y` down by the same amount; the filter's tracked level `x - y` never went below 0. The second DC-blocker overflow claim refuted, after the earlier RTL audit's. |
| RTL-R2-02 | DEFERRED | Real as a cost, not a defect. `ppu2c02`'s `vram [0:2047]` is absent from the synthesis RAM summary (where `wram`'s identical 2048 x 8 array is M10K), so the nametable is 16,384 register bits and their mux. It has three read sites (`nt_byte`, `at_bits`, `read_buffer`) and a write, more ports than an M10K block, and the proposed module adds a cycle of read latency to a cycle-accurate PPU. The fit closes with 44% of ALMs free; a ticket for a later release, with the whole ladder. |
| RTL-R2-03 | REJECTED | As a timing defect. The three `lpm_divide` instances exist, but in the console domain (46.6 ns); the "fails by 24 ns" is quoted from `cart.sv`'s account of the crossing that was then made from a register, and the v3.1.0 off-die compile met timing. A power-of-two bypass would only save area. |
| RTL-R2-04 | REJECTED | The palette split it audits was measured and ADOPTED in the sibling (`17b1dfa`): `quartus_map` on one tree, palette 2,390 -> 1,386 combinational ALUTs, design ALM estimate 30,397 -> 29,882, `make palette-gate` PASS and a channel-swap mutant caught (371 of 1,536). Its proposal, a channel counter reset at byte 0 in place of `% 3` / `/ 3`, was not taken: the divider is about 74 ALUTs, and the counter makes the write port depend on the download arriving in order from byte 0, which nothing checks. |
| RTL-R2-05 | REJECTED | `clk_sys` and `clk_sdram` are outputs of one PLL at exactly 4:1 (ADR 0039), in the same `set_clock_groups -exclusive` group of `sys/sys_top.sdc`, so the crossing is ANALYSED (`RustyNES.sdc` says why; v2.6.13's -24.769 ns on it was visible only because it is), and `chr_addr` is published from a register (`chr_flat_o`). A partially toggled address is what the setup check rules out. |
| RTL-R2-06 | REJECTED | As a defect. "26 cycles against 24" is the project's own stress-model figure from `sdram_arbiter.sv`'s table, which issues a CHR and a PRG request on the same cycle; the console never does (0 coincidences in 15 M SDRAM cycles) and its CPU path meets at 24 of 24. `make -C tb sdram-arb-gate` on the merged tree reprints the same numbers (26; 14 with CHR silent; PASS over 211,200 cycles). The handshake bypass would change a gated controller for a coincidence that does not occur. |
| RTL-R2-07 | REJECTED | The "banked" `oam_read` reads the same 256-entry array at the same index in the same cycle: the same Boolean function, so synthesis builds the same mux. Its "LEs" are not a Cyclone V unit. |

## v3.4.0 follow-up: the deferred netplay findings

The table above is the v3.2.0 record and stays as written. What v3.4.0
(`T-NETPLAY-ROLLBACK-WINDOW`, `T-NETPLAY-DATAGRAM-AUTH`) did with the
deferred netplay rows, each claim re-read against the code first. Spec:
[`docs/netplay-session.md`](../netplay-session.md).

| ID | v3.4.0 verdict | What was done |
| --- | --- | --- |
| NET-R2-01 | FIXED | Confirmed: on the v3.3.0 code a latent session whose predictions all held re-simulated 1,181 and 887 frames on its two peers in 300 ticks. The session now keeps a bounded window of per-frame entries; a confirmation promotes them and replays nothing, a misprediction replays from the mispredicted frame and re-predicts the rest. The report's patch was not used: it snapshotted only when no frame was speculative, which in a latent session is never. Gate: `held_predictions_confirm_without_a_replay` (zero frames re-simulated), `only_mispredictions_replay`. |
| NET-R2-02 | REJECTED in part | The claim that a replay overwrites the whole framebuffer before it is shown is false: a `run_frame` boundary can fall a few dots into scanline 0, and a slim restore plus one frame left 51, 15 and 6 stale bytes on nestest's frames 1 to 3. Built slim, the per-frame gate failed at frame 4 as a false desync. The window entries are full snapshots; what the finding wanted (no per-tick full-snapshot churn) comes from NET-R2-01's fix instead. |
| NET-R2-05 | FIXED | Measured before adopting: 209.7 us per frame byte-wise FNV-1a, 13.3 us for the four-lane word checksum (`framebuffer_digest`), on two runs. The report's word-wise FNV loop was not used: a bare XOR-and-multiply only carries bits upward, so two equal high-bit flips in two words cancel. It changes every exchanged digest, so it ships under protocol 9. |
| NET-R2-09 | FIXED | Confirmed: after 3,000 frames the v3.3.0 session held 3,002 history slots, 3,002 digests and 6,004 checksum slots. History, digests and checksums are now windows; `the_window_stays_bounded_over_a_long_session` bounds them by `RetainedWindow::bound`. |
| NET-R2-07 | FIXED (design) | The finding is real: on v3.3.0 one unauthenticated datagram ended a session. The report's fix (source filters) stays rejected for the reason above. Protocol 9 seals every native datagram with a per-session HMAC-SHA-256 key from handshake key shares (ADR 0046): forgeries and replays from any address are refused, a rebinding peer is kept and followed. Gates: `tests/datagram_auth.rs`. It does not stop an attacker who observes the handshake (recorded in the ADR). |
