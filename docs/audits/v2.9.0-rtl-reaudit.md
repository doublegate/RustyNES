### NR-02 — Medium. The DQ input hold check is placed one clock period early. The reported +12.8 ns hold margin is not physical. DEMONSTRATED by arithmetic from the reported slacks

- **Where.** `RustyNES.sdc:84-85`:
  ```
  set_multicycle_path -from [get_ports {SDRAM_DQ[*]}] -setup 2
  set_multicycle_path -from [get_ports {SDRAM_DQ[*]}] -hold  1
  ```
- **Mechanism.** `-setup 2` moves the setup latch to launch + 14.551 ns, which is the correct capture edge (M+CL, per the file's own comment). With the default hold, TimeQuest checks hold one period before the setup latch (+2.91 ns). That is the physically correct check: the next beat is launched by the next part edge, 11.641 ns later, with tOH 2.5 ns. `-hold 1` moves the hold check a further period back, to -8.731 ns. That describes an enable-style multicycle where the data is stable for two cycles. It does not describe this path: with burst length 1 the part releases the bus tOH after the next edge.
- **Proof from the reported numbers.** For a single-period data-valid window, setup slack + hold slack ≤ T + tOH − tAC = 11.641 + 2.5 − 6.0 = 8.14 ns, less any path skew.
  - Ledger R-4.6 records DQ setup +0.439 and hold +12.822 at seed 5 (seed 4: +0.453 / +12.821). Their sum is 13.26 ns, which is greater than 8.14 ns.
  - The worst setup is at least 0.439 in every corner, so no corner satisfies the bound. The hold being analysed cannot be the physical one.
  - The requirement is off by exactly one period. The real hold slack is therefore about 12.822 − 11.641 = **+1.18 ns** at zero board delay, assuming the same path and corner.
- **Why it matters.** It is positive today. But v2.9.2 will tune the SDRAM clock phase (`pll.v` `phase_shift2`) to recover setup lost to board trace delay, and any shift toward setup consumes this hold margin. TimeQuest will keep reporting ~12 ns while the real margin crosses zero. On hardware that is a corrupted read on some beats, and no simulation reproduces it.
- **Fix.** Delete the `-hold 1` line and keep `-setup 2`. Re-run the off-die compile, and record the new DQ hold slack in the ledger.
- **Gate.** `report_timing -hold -from [get_ports SDRAM_DQ[*]] -npaths 1` in `scripts/check_timing.py`. Fail if the DQ hold slack exceeds one clock period (11.641 ns), because such a figure cannot be physical.

### NR-03 — Medium. An NES 2.0 header is misread as a dirty iNES header. The mapper's high nibble is dropped and an unsupported board is accepted as a supported one. DEMONSTRATED by code reading against the vendored wiki

- **Where.** `emu.sv:636-640` (bytes 12-15 non-zero sets `header_dirty`) and `:676` (`m = header_dirty ? {4'd0, mapper_lo} : {mapper_hi, mapper_lo}`).
- **Mechanism.** `nesdev_wiki/INES.xhtml` ("Recommended detection procedure") says byte 7 AND $0C = $08 means NES 2.0, and applies the "bytes 12-15 all zero" test only when byte 7 AND $0C = $00. The loader never tests byte 7 bits 3:2. It treats every header with non-zero bytes 12-15 as a DiskDude-style dirty header.
  - NES 2.0 defines those bytes. `NES_2_0.xhtml` sets byte 15 to "Default Expansion Device", with `$01` meaning "Standard NES/Famicom controllers".
  - A correct NES 2.0 header is therefore routinely "dirty" here.
- **Failure scenario.** An NES 2.0 image of mapper 71 (Camerica; Micro Machines and the Codemasters titles in `docs/HARDWARE_TESTING.md` §5.3) with byte 15 = $01 decodes as mapper 7.
  - `mapper_supported(7)` is 1, so the image is accepted as AxROM. The console runs it and the OSD shows "Cartridge loaded".
  - This is exactly the "plausible-looking garbage" the refusal at `emu.sv:663-670` exists to prevent. With a clean iNES 1.0 header the same game is correctly refused.
  - Same shape for other mappers: 66→2 (UxROM), 65→1 (MMC1), 67→3, 68→4 (MMC3), 16/17→0/1, and so on.
  - NES 2.0 byte 8 (mapper bits 11:8) is never read either, so mapper 256+n aliases to n.
- **Fix.**
  - Capture byte 7 bits 3:2.
  - If they are `10`, NES 2.0: take the high nibble unconditionally, and require byte 8[3:0] == 0 for "supported".
  - Apply the bytes-12-15 rule only when they are `00`. For `01` (archaic), use the low nibble.
  - Move the decode into a small module, as `osd_menumask.sv` was, so a gate can reach it.
- **Gate.** A module gate sweeping header variants (iNES clean, DiskDude, NES 2.0 with byte 15 = $01, NES 2.0 with byte 8 ≠ 0) against a Python model of the wiki procedure.

### NR-04 — Medium. Images larger than the cartridge arrays are accepted and load aliased. MMC1's PRG A18 (SUROM/SXROM) is not implemented even off the die. DEMONSTRATED by code reading; the example title size is from general knowledge

- **Where.**
  - Acceptance depends only on the mapper number: `emu.sv:680`.
  - On the die the arrays are 256 KiB PRG and 128 KiB CHR (`emu.sv:891-892`). The loader and fetch addresses are silently truncated to the array: `cart.sv:827-828` (`prg[load_addr[$clog2(PRG_BYTES)-1:0]]`), `:743` (CHR). `:202` marks `load_addr[18]` unused on purpose.
  - MMC1 PRG banking uses only `mmc1_prg[3:0]` (`cart.sv:585-601`). No CHR-register bit 4 reaches PRG A18, although `cart.sv:875-876` and `docs/rung7-mappers.md:841` state that on SUROM/SXROM that bit IS PRG A18.
- **Failure scenario (on die).** A 512 KiB PRG / 256 KiB CHR MMC3 game loads. The upper halves overwrite the lower halves, and the core runs the result with "Cartridge loaded" on the OSD.
  - `docs/HARDWARE_TESTING.md` §5.3 lists *Kirby's Adventure* as an MMC3 IRQ-precision test title for the board session. It is commonly documented as a 512 KiB PRG + 256 KiB CHR cartridge; confirm from the header of the dump actually used.
  - The size limit itself is documented (`docs/submission-case.md:99-101`). The missing refusal, and the test list naming a title the shipped build cannot hold, are not.
- **Failure scenario (off die).** A 512 KiB SUROM image (MMC1) loads in full. The switchable window reaches only the first 256 KiB, while `prg_last` points into the upper 256 KiB. The game crashes when it banks.
- **Fix.**
  - Refuse (OSD info line) when `prg_16k_banks*16 > PRG_MAX_KB` or `chr_8k_banks*8 > CHR_MAX_KB`.
  - Either implement SUROM's PRG A18 (outer 256 KiB select from CHR bit 4 when PRG is 512 KiB) or refuse MMC1 images above 256 KiB PRG.
  - Remove or annotate Kirby's Adventure in the on-die hardware test list.
- **Gate.** A header-decode module gate (as in NR-03) with oversize cases. A `mkmapper.py` SUROM stimulus diffed against the oracle, which has SUROM since v2.7.2.

### NR-05 — Medium (off-die build only). The loader has no backpressure, and the bridge drops a write silently on one coincidence. MECHANISM DEMONSTRATED; hardware reachability SUSPECTED

- **Where.**
  - `emu.sv:415` `.ioctl_wait (1'b0)`. Its comment ("writes straight into on-chip cartridge memory with nothing that can back up") is true only on the die.
  - `cart_sdram.sv:398-419`.
- **Mechanism, part 1: the silent drop.**
  - Branch 1 (`wr_pending && !a_wr_busy`) issues the held write.
  - A `load_wr_now` / `chr_wr_now` pulse on the SAME cycle falls through both `else if` arms. It is neither issued, nor stored, nor flagged by `wr_overrun`. The byte is lost.
  - `load_wr_now` is a one-cycle edge (`:219-221`), so nothing retries it.
  - The invalidation at `:384-391` still runs, so the copy is marked stale and re-read from SDRAM, which holds the old byte.
- **Mechanism, part 2: overruns are nobody's problem.**
  - A byte arriving while one is pending sets `wr_overrun`.
  - `emu.sv:1061` sinks `arb_wr_overrun` and `arb_overrun` into `unused_sdram`, so on hardware no one ever sees them.
- **The harness knows the path cannot keep up.** `tb/cpu_main.cpp:684-693`: "One master clock per byte out-runs the bus: the bridge holds one write and reports an overrun for the next." The harness therefore paces the loader at 4 `clk_sys` per byte. `tb/cart_sdram_main.cpp:93-100` paces at 4 as well. The pending-slot drain coincidence is never exercised.
- **Trigger 1: bytes arriving faster than a write completes.** This includes a write that collides with a refresh (PRECHARGE ALL + tRP + tRFC + the write). The HPS byte interval is set by Main_MiSTer's io handshake (`sys_top.v:258-263`, `hps_io.sv:633,692`) and is not measured anywhere in this repo.
- **Trigger 2: a download before the controller is ready, which is more concrete.**
  - The arbiter grants nothing until `ready && sdram_usable` (`emu.sv:269`, `sdram_arbiter.sv:225-231`). That is 200 us plus init (17,214 SDRAM cycles in the gate) after PLL lock.
  - Bytes 1 and 2 are held (arbiter `wr_pend`, bridge `wr_pending`). Every later byte in that window overruns and is lost.
  - `emu.sv` does not hold the HPS off (NR-06). NR-07 makes this window recur on every framework RESET.
- **Fix.**
  - Drive `ioctl_wait = USE_SDRAM_CART && (!sdram_ready || arb_wr_busy || <bridge wr_pending>)`. It is combinational in `clk_sys` terms and legal because the domains are synchronous 4:1; expose `wr_pending` as a port.
  - Separately, fix the drop: when branch 1 fires and a new write arrives, move the new one into the slot.
- **Gate.** Add a `cart-sdram-gate` section that loads at one byte per `clk_sys`, with a refresh forced to coincide. It must be red on `main` (a lost byte, and no overrun on the drop cycle) and green after the fix. Add a second section that begins loading before `ready`.

### NR-06 — Low/Medium. The co-simulation gates the console reset on `sdram_ready` and claims `emu.sv` does the same. It does not. DEMONSTRATED

- **Where.** `tb/cpu6502_cosim.sv:438-444`: `wire console_rst_n = rst_n && o_sdram_ready;` with the comment "`emu.sv` gates its reset the same way and for the same reason". `emu.sv:759-760` gates only on `!sdram_usable`, which is the HPS's word about the board, not the controller's init. `cpu_main.cpp:662-674` also waits for `o_sdram_ready` before it streams the ROM.
- **Mechanism.** The off-die ladder verifies a start-up sequence (wait for ready, then load, then release) that the bitstream does not enforce.
- **Failure scenario.** Today the console cannot start before a download ends, and a download takes longer than 200 us, so the gap is latent. But the harness hides NR-05's trigger 2, and a comment asserting equivalence between gated and ungated RTL is the pattern this project audits for.
- **Fix.** Add `| (USE_SDRAM_CART && !sdram_ready)` to the `u_rst_nes` arst, and do NR-05's `ioctl_wait`. Or correct the comment.
- **Gate.** None possible while `emu.sv` is in no testbench. `check_reset_wiring.py` could assert the term is present.

### NR-07 — Low/Medium. The core PLL is held in reset by the framework's RESET, which stops `clk_sys` under `hps_io` and the HPS io handshake. SUSPECTED; needs the board

- **Where.** `emu.sv:178` `.rst (RESET)`. The Template core uses `.rst(0)` (`Template_MiSTer/Template.sv:116`).
  - `clk_sys` is `HPS_BUS[36]` (`sys/hps_io.sv:192`). `sys_top` generates the io acknowledge on it (`sys/sys_top.v:258-263`).
  - `CLK_VIDEO = clk_sys` (`emu.sv:984`).
- **Mechanism.** While RESET is high, `clk_sys`, `clk_sdram` and the SDRAM pin clock stop. `sysmem.sv:45` asserts RESET from `~init_reset_n | ~hps_h2f_reset_n | reset_core_req`.
  - Any HPS io transaction during that time gets no `io_ack`.
  - The video path loses its pixel clock.
  - On release, the SDRAM controller re-runs its 200 us init and the console's `pll_locked` term re-arms. That re-opens NR-05's pre-ready window.
  - `u_rst_save` also clears `save_ctl`, although the comment at `emu.sv:197` says only that the console reset must not clear it.
- **Failure scenario.** This depends on when Main_MiSTer asserts `reset_core_req` relative to its io traffic, which is not in this repo. If it resets and then talks (sends status, or streams a ROM), the transaction stalls or data is lost.
- **Fix.** Use `.rst(1'b0)` as in the Template. The emu.sv comment's concern (re-lock after loss of lock) can be met by leaving `locked` in the reset terms, which is already done.
- **Gate.** A hardware observation at v2.9.2: trigger a core reset from the HPS (and an MGL load) and confirm the OSD and ROM load still work. There is no simulation gate.

### NR-08 — Low (margin). PRG and CHR sit in the same SDRAM bank, so every CHR/PRG alternation is a same-bank row conflict. DEMONSTRATED by address arithmetic and the fit report

- **Where.** `emu.sv:238` (`CHR_REGION_BASE = 25'h400000`) and `:290` (`req_addr({1'b0, arb_req_addr_w})`); `sdram.sv:314-316` (bank = word bits 24:23, row = word bits 22:10).
  - PRG occupies byte 0-0x7FFFF and CHR byte 0x400000-0x43FFFF. Both are word bits 23:24 = 0, so bank 0, with PRG rows 0x000-0x0FF and CHR rows 0x800-0x87F.
  - The off-die fit report confirms the bank pins are constant: `SDRAM_BA[0..1]` and `SDRAM_A[12]` show "Output Register: no" (`output_files_offdie/RustyNES.fit.rpt:4716,4726-4727`), while `SDRAM_A[0..11]` are IOE-packed. The `13410` stuck-pin message that would name them is suppressed in `RustyNES.qsf:335`.
- **Mechanism.** The open-row policy (`sdram.sv:171-192`) keeps one row per bank. The console interleaves CHR fetches and PRG reads, so each switch pays PRECHARGE + tRP + ACTIVE + tRCD rather than a hit.
  - `sdram-arb-gate` reports 26 cycles worst PRG against 24, of which "14 is the access and 12 is contention".
- **Fix (suspected improvement).** Place CHR in bank 1: `CHR_REGION_BASE = 25'h1000000`, which is word bit 23. Both regions then keep a row open.
- **Gate.** Re-run `sdram-arb-gate` / `cart-sdram-gate` / `sdram-console-latency-gate`, and record whether the synthetic CPU worst case closes. Mind NR-09 when changing the base.

### NR-09 — Low. `CHR_REGION_BASE` is not actually shared with the bridge. DEMONSTRATED

- **Where.** `emu.sv:236-238` says the base is "shared by the bridge's own CHR port and the `$2007` one so they cannot disagree". But `u_cart_sdram` (`emu.sv:764`) passes no `#(.CHR_BASE(...))`. `cart_sdram.sv:83` has its own default `25'h400000`. The same is true in `tb/cpu6502_cosim.sv:449,476`.
- **Mechanism.** The two copies agree only because the defaults are equal.
- **Failure scenario.** Changing one, for example for NR-08, makes `$2007` reads come from a different region than fetches and CHR-RAM writes.
- **Fix.** Pass `.CHR_BASE(CHR_REGION_BASE)`, or derive `pd_addr` inside `cart_sdram`.

### NR-10 — Low. The off-die loader takes `load_data` from the unregistered `ioctl_dout` while its enable and address are registered. DEMONSTRATED; hazard latent

- **Where.** `emu.sv:778` `.load_data (ioctl_dout)`. `emu.sv:644-645` registers `cart_load_en` / `cart_load_data`, and `cart_load_addr` comes from the same edge. The co-simulation passes the registered `cart_load_data` (`cpu6502_cosim.sv:474`).
- **Mechanism.** `hps_io` updates `ioctl_dout` on the next data strobe (`hps_io.sv:692`). If that strobe lands on the edge where `cart_load_en` rises, the bridge writes byte N+1's data at byte N's address. The bitstream and the gated netlist also differ at this seam.

### NR-11 — Low. `emu.sv` has no width lint. DEMONSTRATED
