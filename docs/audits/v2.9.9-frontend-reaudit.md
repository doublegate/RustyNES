## New findings

Status legend: **DEMONSTRATED** = reproduced on this tree by a probe whose output is quoted;
**REASONED** = mechanism read from code, not reproduced; **SUSPECTED** = plausible, not
traced to the end; **STRUCTURAL** = a gap in coverage or reporting rather than a wrong
computation. Ids continue from v2.9.0's NF-10.

### NF-11 — Medium — Hotkeys and two other paths bypass the replay and netplay lockouts the menu enforces (REASONED)

- **Where:** `app.rs:6951-6952` (`SysAction::Reset` / `SysAction::PowerCycle`), `:6987`
  (`SysAction::DiskSwap`), all dispatched from the key handler (`app.rs:10154`, `:10180`)
  with no check; the menu greys the same items with
  `hw_interactive = rom && !rom_change_restricted && !replay_locked` (`ui_shell.rs:847`,
  items `:856`, `:867`; disk items `:998`, `:1012`). The Save-States manager's Load
  (`app.rs:11647-11660`) checks hardcore only, while the menu (`:5158`), the F4 hotkey
  (`:6930`) and the browser grid (`:11684`) also check `replay_interaction_locked`. A
  script's `LoadState` (`app.rs:6383-6388`) ignores the `writes_locked` it is given. F8
  branch (`handle_movie_branch`, `app.rs:3196-3207`) has no netplay check, where record
  (`:3070`), play (`:3122`) and import (`:3256`) refuse.
- **Mechanism:** a `.rnm` records input only (`FrameInput`, `rustynes-core/src/movie.rs:170-181`),
  so a Reset, Power Cycle, disk swap or state load during a recording is not in the movie
  and the recording no longer replays; during playback the replay runs on from a state it
  never recorded. `do_power_cycle` even re-applies a running movie's options
  (`app.rs:7178-7181`, `:7196-7199`), i.e. it handles the case it should refuse. During
  netplay the same keys change one peer only; the periodic checksum then reports a desync.
- **Failure scenario:** a player recording a TAS presses F3 out of habit; the saved movie
  plays back wrong with no warning (an attested recording would carry an attestation of a
  run the input stream cannot reproduce).
- **Red test:** an App-level test is not possible without a window; the testable seam is
  a function the four sites share. Pin: with `emu.movie` recording, the Save-States manager
  Load, `SysAction::PowerCycle`, `SysAction::Reset`, `SysAction::DiskSwap` and a script
  `LoadState` must each leave the `Nes` snapshot unchanged.
- **Proposed fix:** route all of them through one guard (`replay_interaction_locked() ||
  netplay active`, plus hardcore for loads), as the menu already computes.

### NF-12 — Medium — A movie keeps recording or playing across a ROM load and imposes the old game's options on the new one (DEMONSTRATED mechanism; REASONED reachability)

- **Where:** `load_rom_from_path` (`app.rs:1708-2147`) and `finish_start_nes`
  (`app.rs:9426` onward, the browser's every load via `install_nes_wasm` `:9295`) never
  stop `emu.movie`; `EmuCore::set_nes` (`emu.rs:788-792`) does not touch it. Open ROM is
  gated by netplay only (`ui_shell.rs:554`, `:585`), so it is reachable during a replay.
  Each frame `MovieUi::before_frame` (`movie_ui.rs:384-410`) calls `apply_live` with the
  held options, which include the mirroring override, the Game Genie codes, the Vs. DIP
  and PPU type and the console model (`rustynes-core/src/hardware_options.rs:81-114`,
  `:189-219`). `stop_playback` (`movie_ui.rs:329-337`) then restores the "player options"
  captured from the previous game. Its own doc assumes a ROM swap passes `None`, which
  nothing does.
- **Probe** (`movie_swap`; A = `flowing_palette.nes` with a mirroring override and code
  `SXIOPO`, B = `blargg/mmc3_test/4-scanline_timing.nes`, mapper 4, mapper-controlled
  mirroring):

  ```text
  B before: mapper_id=4 hardwired=false mirroring_override=None genie=0
  B after recording frames: mirroring_override=Some(Horizontal) genie=["SXIOPO"]
  recorded movie: frames=15 rom_sha256==A:true ==B:false
  B after playback stop: mirroring_override=Some(Horizontal) genie=["SXIOPO"]
  ```

- **Failure scenario:** game A's game-database mirroring correction is forced onto an MMC3
  game (the hazard ADR 0031 and `correct_console` guard against), A's Game Genie codes
  patch B's PRG reads, and both persist after the movie ends. A recording saves B's input
  under A's identity, so it never replays.
- **Red test:** the probe's assertions as a `movie_ui` unit test, plus an App seam test
  that a ROM install ends recording (saved or discarded with a message) and playback.
- **Proposed fix:** end the movie session on every ROM install (finish a recording through
  the save path, stop playback with `None`); or grey Open ROM under `replay_locked` as the
  hardware items are.

### NF-13 — Low — History-viewer clips that span a Reset, a rewind or a state load do not replay; an over-long window starts from the wrong anchor (DEMONSTRATED)

- **Where:** `history_viewer.rs:175-212` (`record_frame`), `:307-355` (`export_from`),
  `:360-381` (`evict_to_budget`). The history is cleared on ROM load and Power Cycle only
  (`app.rs:2044`, `:3751`, `:7203`); `do_reset` (`app.rs:5070-5089`), `handle_load_state`
  (`:2670-2703`) and the rewind path (`emu.rs:1427-1440`) leave it running. The module
  doc (`:13-15`) promises bit-identical replay.
- **Mechanism:** `seq` keeps counting across the discontinuity, so an exported clip pairs
  an anchor from before it with input from both sides. Separately, eviction keeps an
  anchor whose `seq` is older than the oldest retained input; an export starting there
  emits fewer frames than the state needs. The comment at `:365-367` calls this tolerated.
- **Probe** (`history_gap`, `history_evict`):

  ```text
  nestest control: clip frames=200 live-vs-replay differing bytes=0
  nestest reset: clip frames=200 live-vs-replay differing bytes=12531
  nestest rewind-30: clip frames=200 live-vs-replay differing bytes=12531
  inputs 70..=369, anchors [60, 120, 180, 240, 300, 360]
  export_from(70): 300 frames, differing bytes 12531
  export_from(130): 250 frames, differing bytes 0
  ```

  The eviction case is not reachable from the shipped menu, which offers only a 30 s clip
  against a 60 s log (`ui_shell.rs:1343`, `history_viewer.rs:46`).
- **Red test:** the probe as a unit test: reset at frame 120, export from 0, replay must
  match the live frame.
- **Proposed fix:** clear the history (or force an anchor and end exports there, as the
  v2.9.8 options-change anchor does) on Reset, rewind and state load; and in `export_from`
  refuse, or step forward to, an anchor older than the first retained input.

### NF-14 — Low — TAStudio's export records the frame-0 options, but a mid-session cheat or setting change reaches its re-emulation (DEMONSTRATED)

- **Where:** `tastudio/mod.rs:239-244` (`start_options`), `:396-410` (`to_movie`),
  `:705-741` (`seek`): nothing holds the options during re-emulation, unlike movie playback
  (`movie_ui.rs:384-410`). The Cheats panel and the live Settings apply paths
  (`app.rs:6551-6700`) stay usable while the editor is open.
- **Probe** (`tas_options`: nestest, 120 recorded frames, then code `UXPGKU` added, an
  input edited at frame 1, seek 0 then 120):

  ```text
  exported options carry 0 genie codes
  TAStudio frame 120 vs exported-movie replay: 255 differing bytes
  ```

- **Failure scenario:** a TASer adds a code to test a route; the greenzone shows the coded
  run, the exported `.rnm` / `.fm2` replays the uncoded one.
- **Red test:** the probe as a `tastudio` unit test.
- **Proposed fix:** hold `start_options` with `apply_live` before every re-emulated frame,
  as playback does (and say so in the Cheats/Settings UI), or refuse option changes while
  the editor is open.

### NF-15 — Low — A spectator whose ROM or configuration differs still runs the players' stream, silently (DEMONSTRATED)

- **Failure scenario:** v2.9.8's handshake refuses mismatched players with a message; a

- **Red test:** the probe: no frame may be produced before a matching `Sync`, and a

### NF-16 — Medium — The FDS writable disk is not sandboxed: a movie, TAStudio or netplay session's disk writes are saved over the player's `.fds.sav`, under the emulation lock (REASONED)

- **Where:** `per_frame_host_io` (`app.rs:2509-2513`) calls `flush_fds_save`
  (`app.rs:2548-2551`) after every produced frame; `EmuCore::flush_fds_save`
  (`emu.rs:1833-1864`) writes whenever the disk is dirty, with `write_atomic` (an `fsync`,
  `atomic_write.rs`) while the caller holds the emu lock. `start_sandboxed_session`
  (`emu.rs:1957-1964`) releases only the battery binding; `fds_disk_sha256` stays set.
  `power_on_for_movie` (`rustynes-core/src/movie.rs:1128-1141`) clears save data, which on
  FDS is not the disk (`clear_save_data`, default mapper impl).
- **Mechanism:** the battery fix of v2.9.0 ("a movie session's save RAM was written over
  the `.sav`") has no FDS counterpart. A movie replayed on a disk game writes the movie's
  saves to the disk image, and the per-frame flush persists them to the player's file.
  A disk game writing a file also dirties the disk on many consecutive frames, so a
  ~65 KiB-per-side copy plus an `fsync` runs every frame under the lock the emulation
  thread needs.
- **Failure scenario:** a player watches a TAS of an FDS game; their own disk save is
  replaced by the movie's progress.
- **Red test:** with a synthetic disk image (the BIOS can be a stub, as the mobile tests'
  `synthetic_fds_bios` is), start a sandboxed session, mark the disk dirty, run
  `flush_fds_save`: the `.fds.sav` must be unchanged.
- **Proposed fix:** unbind the FDS save in `start_sandboxed_session` exactly as the battery
  is; take the disk copy under the lock and write it after (the FE-01 `due_write` pattern),
  throttled.
- **Not here:** neither mobile host persists FDS disks at all (known; recorded in
  `docs/mobile-v2.9.3-run-sheet.md:129-132`).

### NF-17 — Medium — An FDS game's save identity is the modified disk, so its save states and cheats are lost after the first disk save (REASONED)

- **Where:** `Nes::from_disk_with_sample_rate` sets `rom_sha256 = sha256_of(disk_bytes)`
  (`rustynes-core/src/nes.rs:473-485`). The desktop boots the saved `.fds.sav` image when
  one exists (`app.rs:2480-2500`), keeping `fds_disk_sha256` as the pristine hash for the
  `.fds.sav` key only. Save-state slots key on `loaded_rom_sha256` (`emu.rs:807-812`),
  cheats on `nes.rom_sha256()` (`app.rs:2168`).
- **Mechanism:** each launch after a disk write hashes a different image, so the slot
  directory and cheat file of the previous session are not found. The v2.9.8 identity
  change ("FDS and NSF are unchanged") left this as it was.
- **Failure scenario:** save state in slot 1, the game saves to disk, quit, relaunch:
  slot 1 is empty and the cheat list is gone.
- **Red test:** load a disk, write to it, build the save-key the way `load_rom_from_path`
  does for the saved image; it must equal the pristine image's key.
- **Proposed fix:** key FDS identity on the pristine image (the value already kept in
  `fds_disk_sha256`), e.g. an `Nes` constructor that takes the identity separately.

### NF-18 — Low — The mobile bridge lets a movie, a state load, a Reset or a Power Cycle run inside a live netplay session, and netplay start inside a movie (REASONED)

- **Where:** `rustynes-mobile/src/lib.rs`: `reset` `:1401`, `power_cycle` `:1420`,

  recording during netplay runs `power_on_for_movie` on one peer; playback applies the

- **Red test:** with a loopback session in game, `movie_record_from_power_on` must return

- **Proposed fix:** a `refuse_during_session` helper beside `refuse_on_cabinet`, used by

### NF-19 — Low — The browser still reports "State saved" / "State loaded" whatever happened (STRUCTURAL)

- **Where:** `app.rs:5148-5152`, `:5168-5172`, `:5229-5233`, `:5249-5253`, `:11684-11690`

### NF-20 — Low — Movie export ends a recording before the file dialog, so cancelling it discards the recording; movie outcomes still go to stderr only (STRUCTURAL)

- **Where:** `handle_movie_export` (`app.rs:3405-3460`) takes `finish_recording()`

### NF-21 — Low — Both mobile hosts key saves by the whole file's SHA-256, not by the v2.9.8 identity (REASONED)

- **Where:** Android `prepareRom` keys `.sav`, the auto-resume state and the library on
  `sha256Hex(bytes)` of the bytes as read (`MainActivity.kt:758`, `:761-764`), which for a
  `.zip` is the archive; iOS uses `RomIdentity.sha256` of the file data
  (`RomIdentity.swift:15`; `AppModel.swift:346`, `:831`).
- **Mechanism:** v2.9.8 moved the identity to the bytes after the header
  (`rustynes-core/src/nes.rs:3246-3251`) so that header corrections and header-only dump
  differences stop splitting saves, and documents it as the key for states, `.sav` and
  cheats. On mobile the key still includes the header (and the zip container), so: two dumps
  differing only in the header do not share saves, a re-zipped ROM loses its saves, and a
  desktop slot cannot be matched by key.
- **Proposed fix:** a bridge accessor for `Nes::rom_sha256` (the bridge already has a
  private `rom_sha256`, `lib.rs:1176`) and a one-time key migration in both hosts; or
  record the difference in `docs/android.md` / `docs/ios.md` and the v3.0.0 notes.
