# v2.9.9 re-audit — libretro core

Scope: `crates/rustynes-libretro` (`lib.rs`, `abi_tests.rs`, `build.rs`, `Makefile`, the local
`rustynes_libretro.info`), `vendor/rust-libretro-sys`, `.gitlab-ci.yml`, `docs/libretro/`, and the
parts of `rust-libretro` 0.3.2 (the libretro binding library, not an emulator or core) that the
core's behaviour depends on. Tree: branch `release/v2.9.9-rc` @ `8b277044`, clean. No third-party
emulator or core source was opened. RetroArch source was not read either; frontend behaviour below
is taken from `libretro.h` or marked as inferred. RustyNES's own core crates were read where a
libretro behaviour depends on them.

The emphasis is on what v2.9.8 changed (`CHANGELOG.md` `[2.9.8]`): the game-database corrections in
the load path, the header-excluded ROM identity, `.rns` epoch 3, `Nes::power_cycle` keeping
settings, and the `platform=libnx` removal.

## What v2.9.8 changed, checked and found sound (not findings)

- **Game-database corrections** (`build_cartridge`, lib.rs:815-830). `correct_rom` runs on the
  frontend's own copy before the parse; `correct_console` runs on the single console or on both
  consoles of a cabinet; `apply_vs_database` runs after, on the corrected console. `rom_crc32`
  refuses anything but an iNES image with plausible sizes (`rustynes-gamedb` lib.rs:896-909), so
  UNIF, FDS and malformed images pass through uncorrected and cannot panic there. The user overlay
  is never configured in this core, as documented. A submapper promotion of an iNES 1.0 header
  zeroes bytes 9-15, which could in principle shrink a board's NES 2.0 PRG-RAM; the only rows that
  promote (mapper 210 x 11, mapper 185 x 1) build boards that allocate their RAM regardless
  (`m210_namco175.rs:112`), and the battery bit (byte 6) is untouched. The gradius-europe ABI
  test and the mirroring unit test pass.
- **Header-excluded identity.** RetroArch keys `.srm` by content name, not by
  `Nes::rom_sha256`, so the identity change does not move a libretro battery save. The
  FDS `.fds.sav` key is the disk hash, unchanged. The `.rns` header tag is the identity prefix and
  is still informational: a probe loaded nestest's state into `dpcmletterbox` (same NROM
  16 KiB / 8 KiB shape) and it was accepted. That is the documented core decision (`nes.rs`, the
  `restore` doc after NL-01), recorded here only because v2.9.8 removed one of its two stated
  reasons. States from a different board shape were refused (mapper 3 and mapper 1 probes).
- **`.rns` epoch 3.** `parse_header` refuses `format_version < MIN_FORMAT_VERSION`
  (`save_state.rs:488-493`) before anything is applied, and the rollback backup covers any later
  rejection. Demonstrated through the ABI (above, NL-01 row). What the user is told is NL-11.
- **`retro_reset` versus `power_cycle`.** The libretro core never calls `power_cycle`; Reset is
  `Nes::reset` (lib.rs:2378-2391), which keeps the bus-held settings (Vs. PPU type and DIP, the
  database's mirroring override, Four Score) by construction. For a cabinet the core resets both
  consoles without a cabinet-level method (`VsDualSystem` has `power_cycle` but no `reset`).
  Measured with `coreprobe` on the ten local Vs. dumps the database or header makes cabinets: after
  600 frames, `main.reset(); sub.reset();`, then 1,200 frames, the two framebuffers equal a fresh
  boot's on 1,153-1,200 of 1,200 frames, and both screens keep animating where the fresh boot does.
  No hang. The desktop has no dual reset to compare with (`app.rs` `do_reset` touches `nes` only).
- **Four Score / four ports.** Descriptors and controller info cover four ports; ports 3-4 offer
  no light gun; `.take(2)` guards `set_zapper`. Four Score does not change the state size.
- **`retro_get_memory_*`.** Null / 0 with no game; battery-gated `SAVE_RAM`; WRAM and CIRAM sizes
  are the fixed buffers. No length from the frontend is used to index anything.
- **Frontend-supplied lengths.** `retro_serialize` checks `size` against the reported size;
  `retro_unserialize` hands the exact slice to the parser, which bounds every read
  (truncated / empty probes above); `GET_GAME_INFO_EXT` data and `retro_game_info` data are taken
  at the frontend's stated size, as libretro.h permits; the label buffer is bounded by `len`.
- **Threading.** No asynchronous callback is registered (no audio callback, no frame-time
  callback); the only call the frontend may make outside the main sequence is
  `get_image_label`, which reads but does not mutate. `rustynes_gamedb`'s table is a `OnceLock`
  and its overlay an `RwLock`.
- **Vendored patch.** No UB found: the hand-written struct is `#[repr(C)]` with the header's
  types in the header's order, and nothing else differs from crates.io.
- **`.info` against the code.** Capability flags, extensions, licence and version are audited;
  the description's "unsafe-free `#![no_std]` emulation core" holds (`#![no_std]` and
  `#![forbid(unsafe_code)]` in all five chip and core crates); "191 mapper families" matches
  `docs/STATUS.md` but is not audited (see the upstream section).

## New findings

Severity scale as in the v2.9.0 report: High (data loss or corrupted emulation reachable in normal
use), Medium (a user-visible functional defect), Low (a contract or documentation defect with
limited effect), Info.

### NL-11 — A refused `retro_unserialize` tells the user nothing: the reason is discarded (Low, DEMONSTRATED)

- **Where:** lib.rs:2594-2599. `nes.restore_quiet(slice).is_ok()` and `dual.restore(slice).is_ok()`
  drop the `SnapshotError`; `on_serialize`'s failures (2557-2581) are likewise silent.
- **Mechanism:** v2.9.8 made every state from v2.9.7 and earlier fail (`FormatTooOld`), and the
  CHANGELOG promises they "are refused with a clear error ... [that says] to re-record". The
  desktop surfaces that error; the libretro core returns a bare `false`, and the frontend can show
  only its own generic failure (RetroArch's wording not traced in its source).
- **Demonstration (probe `probe_old_format_state`):** a nestest state with its format field set
  to 2 returns `false` and leaves the machine unchanged (good), and the frontend's log interface
  received **no message** (`log=[]`), although the harness's log interface was registered and is
  shown working by `messages_reach_the_frontends_log_interface`.
- **Red test:** an `abi_tests` case that rewrites the format field to 2, calls `unserialize`, and
  asserts a logged line naming the format (and the re-record advice).
- **Fix:** log the `SnapshotError` at `RETRO_LOG_WARN` from `on_unserialize`, phrased for a
  user (an older RustyNES state, a different game's state, or a damaged file). Optionally
  `RETRO_ENVIRONMENT_SET_MESSAGE` for the first refusal of a session. Netplay and run-ahead
  never hand the core a foreign state, so the message does not fire on the hot path.

### NL-12 — A save/load round trip changes the console's later audio and serialized state, so the "deterministic" save state is not (Medium, DEMONSTRATED; netplay consequence REASONED)

- **Where:** core scope, surfaced through this core. `rustynes-apu/src/snapshot.rs:17-20` and
  `574-575`: the blip resampler's pending host-rate samples are "intentionally NOT preserved"
  across a restore. The libretro `.info` advertises `savestate_features = "deterministic"`, and
  `docs/libretro/advanced_features.md` ("Deterministic Serialization for GGPO & TAS") describes
  rollback netplay as riding on it.
- **Demonstration 1, the serialized state (C ABI, probes `probe_run_ahead_round_trip` and
  `probe_where_run_ahead_differs`):** run nestest for 20 frames straight, and again with a
  RetroArch-style serialize, one extra frame, unserialize after every frame. The final states
  differ, in the `APU` section only: 24 bytes at body offsets 141-174, the output filter's
  `prev_in` / `prev_out` values (non-zero straight, zero after the round trips). Loading each final
  state into a fresh core and running 120 more frames: the framebuffers are identical, the `APU`
  sections still differ. The same holds for the Vs. probe cartridge with and without a coin.
- **Demonstration 2, the audio (`coreprobe` `audio2`/`audio3`, core API, `db_apu.nes` and the
  local *Donkey Kong*):** a single snapshot-and-restore in place at frame 100 makes frame 100
  deliver **717 samples instead of 734**, starting from `0.0`, and the stream never becomes
  bit-identical again (differs through frame 599 of 600). A restore before every played frame
  (the shape of a rollback whose re-simulated frame is then presented) delivers 429,360 samples
  over 600 frames instead of 439,526 (**-2.3%**), with a maximum per-sample difference of 0.48
  full scale (signal peak 0.39). Control: two straight runs are byte-identical in audio and state.
- **What it does NOT affect, measured:** classic single-instance run-ahead, where the presented
  frame follows a serialize and not an unserialize, plays the full 439,526 samples and matches the
  straight run to within float rounding (max difference below 5e-5). Video is never affected.
- **Consequences:**
  - A user's Load State drops about 17 samples and steps the output by the lost integrator level
    (a click), every time.
  - RetroArch netplay compares CRCs of serialized states between peers periodically and resyncs
    on a mismatch (inferred from RetroArch's documented netplay settings; not traced in its
    source). A peer that has rolled back carries different filter bytes from one that has not,
    with identical emulation, so the check can report a desync that is not one.
  - The project's own contract ("same seed + ROM + input sequence ⇒ bit-identical framebuffer
    and audio") does not hold for audio once a restore is interleaved.
- **Red test:** `abi_tests`: load, run 10 frames, serialize S, unserialize S, run 10 frames,
  serialize; a second load runs 20 frames straight and serializes; assert the two states are
  equal. It fails today at the `APU` section.
- **Fix (core, not this crate):** serialize the blip's pending samples (or the integrator state
  they encode), so a restore resumes the exact stream, with a new APU section version. That is a
  save-state format change, so it belongs with the next epoch decision; until then the `.info`
  `savestate_features` claim and `advanced_features.md` should say that audio is not bit-exact
  across a restore.

### NL-13 — The Vs. coin pulse counts `retro_run` calls, not emulated frames: run-ahead shortens it and makes the state depend on the run-ahead setting (Low, DEMONSTRATED)

- **Where:** `VsPanel::step` (lib.rs:725-744) decrements `coin_frames` once per `retro_run`, and
  the latch it drives (`vs_coin`) is excluded from the snapshot as host input
  (`snapshot_schema_audit.rs:520-522`). `VsPanel` itself is wrapper state, not serialized.
  Run-ahead, preemptive frames, rewind and netplay rollback all call `retro_run` more than once
  per presented frame, with `retro_unserialize` in between.
- **Demonstration (probe `probe_vs_coin_under_run_ahead`, C ABI, the harness's Vs. probe
  cartridge, L held for two real frames):** the coin bit as the game read it after each real frame:

  | run-ahead | frames the coin is seen |
  | --- | --- |
  | 0 | `.....111............` (3 frames, 50 ms) |
  | 1 | `.....11.............` (2 frames) |
  | 2 | `.....1..............` (1 frame, 17 ms) |

  The final serialized state differs between run-ahead 0 and 1 and between 0 and 2.
- **Why it matters:** the core documents the real coin switch as closed for 40-70 ms
  (`Nes::insert_coin`, quoted at lib.rs:674-678); at run-ahead 2 the pulse is 17 ms, which a game
  that debounces the switch over more than one poll can miss (not demonstrated with a commercial
  game). Under netplay the pulse's frame span depends on each peer's rollback count, so peers can
  see the coin in different frames.
- **Red test:** the probe above, asserting the same three-frame pattern at run-ahead 0, 1 and 2.
- **Fix:** count the pulse in emulated frames, not calls: derive it from the console's own frame
  counter (record the frame the coin went in, clear when the console's frame number reaches it plus
  three), or keep `coin_frames` and `coin_down` in the console's serialized state. Either makes a
  restore rewind the pulse along with the frame.

  flushes the data") ties the `.srm` write to `retro_deinit`; libretro.h does not define when a
  frontend writes save RAM, and RetroArch's timing was not traced. State it as inferred, or drop

- **Fix:** correct the comments and the two docs; extend the retired-phrase list in

### NL-15 — Flash boards allocate their whole PRG flash on every restore (Info, REASONED)

- **Where:** `homebrew_boards.rs:827` (GTROM, mapper 111) and `:1522` (flash UNROM 512, mapper 30):
  `load_state` builds a fresh `vec![0u8; flash.len()]` (up to 512 KiB) and copies it in. Every
  `retro_unserialize` reaches it, and run-ahead and rollback call that every frame; the NC-03
  backup snapshot taken first also encodes the flash's sector diff.
- **Not measured.** Under `docs/agents/perf-and-panels.md`'s adoption rule this is a candidate,
  not a claim; it is core scope and only reaches libretro through restore frequency.
- **Fix candidate:** decode the sector diff straight into the live buffer after validating it, or
  into a buffer pooled on the mapper.

### Observations, not filed

- `tick_fds_flush` writes and `fsync`s the disk image (about 65 KB per side) and the directory on
  the emulation thread, once per in-game save (lib.rs:1428-1445, 1766-1804). On slow storage that
  is a one-off frame hitch; the trade-off (a save that survives a crash) is documented.
- `a_vs_dump_in_the_database_renders_with_its_palette` (abi_tests.rs:1663-1708) builds its oracle

- Desktop-only options with no libretro equivalent (Famicom console model, die revisions, OAM
