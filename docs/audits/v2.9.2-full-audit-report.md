# RustyNES and RustyNES_MiSTer Comprehensive Code & Security Audit Report

## 1. Executive Summary & Health Scorecards

### 1.1 Scope of the Audit

This comprehensive audit evaluates the entire software emulation ecosystem of **RustyNES** and the hardware FPGA implementation of **RustyNES_MiSTer**. The audit encompasses both production repositories in their entirety:

1. **Software Emulation Engine (`RustyNES`)**:
   - **Foundational Core Crates**: `crates/rustynes-core` (master clock coordinator, `LockstepBus`, console abstraction, save states), `crates/rustynes-cpu` (Ricoh 2A03/2A07 CPU core and instruction decoder), `crates/rustynes-ppu` (Ricoh 2C02 PPU, 2-cycle ALE pipeline, sprite evaluation FSM), `crates/rustynes-apu` (audio synthesis channels and band-limited BLEP decimation filter), and `crates/rustynes-mappers` (174 cartridge mapper families, expansion audio, and FDS disk subsystem).
   - **Applications & Frontends**: `crates/rustynes-frontend` (desktop desktop shell using `winit`, `wgpu`, and `egui`), `crates/rustynes-mobile` (UniFFI cross-platform bridge), `crates/rustynes-android` and `android/` (JNI/NDK native layer and Jetpack Compose mobile app), `crates/rustynes-ios` and `ios/` (Metal/SwiftUI application shell), and `crates/rustynes-netplay` (deterministic rollback netplay engine and WebRTC/WebSocket signaling relay).
   - **Libretro Ecosystem**: `crates/rustynes-libretro` (RetroArch C-ABI integration, dynamic audio rate synchronization, deterministic save-state serialization, and multi-system arcade composition), `Makefile`, and upstream synchronization assets.

2. **Hardware RTL & Platform Core (`RustyNES_MiSTer`)**:
   - **SystemVerilog Core RTL**: `rtl/` directory, including `sdram_arbiter.sv` (4-port high-speed memory arbiter), `sdram.sv` (Alliance AS4C32M16SB SDRAM controller), `cpu6502.sv` (cycle-accurate SystemVerilog 6502 implementation), `nes_top.sv` (system bus and DMA interconnect), `controller.sv` (shift register input deserialization), and memory banking controllers.
   - **Platform Integration & Framework**: `rtl/emu.sv` (MiSTer framework top-level wrapper), `rtl/reset_sync.sv` (metastability-hardened asynchronous-assert/synchronous-deassert reset tree), `rtl/video_timing.sv`, and audio/video mixing shims interfacing with the MiSTer Linux HPS system (`sys/`).
   - **Synthesis, Constraints & Tooling**: Intel Quartus Prime 17.0.2 Lite synthesis configuration (`RustyNES.qsf`), TimeQuest Static Timing Analysis constraints (`RustyNES.sdc`), build automation scripts (`Makefile`, `clean.bat`, `scripts/build-offdie.sh`, `scripts/release-rbf.sh`), and Verilator co-simulation testbenches (`tb/`).

The audit was conducted under an unconditional clean-room protocol strictly enforcing the **`GEMINI.md` Provenance & License Firewall** and **ADR 0037** (SystemVerilog HDL Reference Firewall):

- **Absolute Black-Box Reference Firewall**: At no point during this investigation was any source code, header file, constant definition, variable naming convention, or comment structure from third-party reference emulators (including Mesen2, puNES, FCEUX, Nestopia, higan, ares, TriCNES, or tetanes) or third-party reference FPGA cores (such as `NES_MiSTer` or `fpganes`) opened, read, quoted, or transcribed.

- **Integrity & Verification Rigor**: In accordance with the project integrity mandate, no test results or outputs were simulated or fabricated. All identified issues were verified through direct AST static analysis, borrow-checker tracing, non-blocking hardware assignment sequencing, and TimeQuest timing report verification.

## 2. RustyNES Core Emulation Engine Audit

### 2.1 Security & Memory Safety Analysis

#### 2.1.1 Unsafe Code Isolation & Memory Safety Baseline

The five core emulation crates (`rustynes-core`, `rustynes-cpu`, `rustynes-ppu`, `rustynes-apu`, and `rustynes-mappers`) enforce an absolute prohibition on unsafe code. Every crate root explicitly declares `#![forbid(unsafe_code)]`. An exhaustive workspace-wide symbol scan confirmed zero occurrences of the `unsafe` keyword in these crates.

Memory safety is maintained through standard library primitives:

- Fixed-capacity array buffers and slices are used for CPU RAM (2 KiB), PPU VRAM/CIRAM (2 KiB), OAM (256 bytes), and secondary OAM (32 bytes).
- All indexing operations on ROM, RAM, and mapper banking windows utilize bounded masks (e.g., `addr & 0x07FF`, `(addr & 0x1FFF) as usize`), guaranteeing panic-free memory addressing during execution.
- However, state deserialization routines parsing untrusted external binary payloads (`.rns` save states) expose specific arithmetic and bounds vulnerabilities.

#### 2.1.2 FDS Save-State Deserialization Integer Overflow & Bounds Violation

- **Target File**: `crates/rustynes-mappers/src/fds.rs:2045-2070`
- **Severity**: High
- **Vulnerability Description**:
  The Famicom Disk System (FDS) mapper implementation deserializes save states through `FdsMapper::load_state`. At line 2045, the number of saved disk sides is parsed directly from an untrusted 4-byte slice in the payload:

  ```rust
  let saved_sides = u32::from_le_bytes(data[off..off + 4].try_into().unwrap()) as usize;
  off += 4;
  let v4_extra = if version >= 4 { FDS_V4_TAIL_LEN } else { 0 };
  let expected =
      base + FdsAudio::TAIL_LEN + 4 + saved_sides * FDS_SIDE_LEN + 4 + 4 + 1 + v4_extra;
  ```

  `FDS_SIDE_LEN` is defined as 65,500 bytes. When parsing a maliciously crafted or corrupted save-state file where `saved_sides` is set to an arbitrary value (such as `0xFFFF_FFFF`), the multiplication `saved_sides * FDS_SIDE_LEN` triggers an integer overflow panic in debug builds and wraps in release builds.

  On 32-bit platforms (such as `armv7` mobile targets or 32-bit embedded hosts), this unchecked arithmetic overflows `usize::MAX`, leading to an incorrect `expected` calculation. Furthermore, at line 2069:

  ```rust
  off += (saved_sides - restore) * FDS_SIDE_LEN;
  ```

  If `saved_sides` is extremely large, this unchecked addition causes pointer or slice offset overflow, panicking the host process and terminating the emulator.

- **Remediation**:
  Physical FDS disks possess at most 2 sides per disk, and multi-disk games never exceed 16 sides in total. Imposing an explicit upper bound `const MAX_SAVED_SIDES: usize = 16;` and utilizing checked arithmetic (`checked_mul`, `checked_add`) completely eliminates the panic surface and prevents memory exhaustion.

### 2.2 Emulation Correctness & State Preservation

#### 2.2.1 VRC Mapper Save-State PRG-RAM Omission & State Loss

- **Target Files**:
  - `crates/rustynes-mappers/src/m085_vrc7.rs:595-763`
  - `crates/rustynes-mappers/src/m024_vrc6.rs:610-698`
  - `crates/rustynes-mappers/src/m021_vrc4.rs:401-445`
  - `crates/rustynes-mappers/src/m022_vrc2.rs:311-346`
- **Severity**: High
- **Defect Description**:
  The Konami VRC ASIC mappers (VRC2, VRC4, VRC6, and VRC7) allocate and manage an 8 KiB PRG-RAM buffer (`Box<[u8]>`) mapped to CPU addresses `$6000-$7FFF`. These memory regions hold live game state, battery-backed save files, and temporary working RAM in titles such as *Lagrange Point* (VRC7), *Madara* (VRC6), *Akumajou Densetsu* (VRC6), *Ganbare Goemon Gaiden* (VRC4), and *Esper Dream II* (VRC2).

  While the standard cartridge mappers (MMC1, MMC3, MMC5, Namco 163, Sunsoft FME-7) serialize their `prg_ram` within their respective `save_state` and `load_state` implementations, all four VRC mappers completely omit `self.prg_ram` from serialization.

  When a user creates a save state, engages rewind, or synchronizes state during netplay or TAS recording, the live WRAM/SRAM contents are discarded. Restoring the save state leaves PRG-RAM containing whatever arbitrary data existed prior to the load. In battery-backed RPGs, this manifests as immediate inventory corruption, quest state reset, or system crashes upon state restore.

- **Remediation**:
  Increment the mapper snapshot version (e.g., from v2 to v3 for VRC7; from v1 to v2 for VRC2/4/6) and serialize `self.prg_ram`. In `load_state`, maintain backwards compatibility by checking `if version >= 3`, adjusting `core_expected` to conditionally include `self.prg_ram.len()`, ensuring that any subsequent audio extension tail (e.g., VRC7 OPLL synthesizer snapshot or VRC6 audio registers) is sliced from the correct stream offset (`&data[core_expected..]`) without offset misalignment or state corruption.

- **Context7 Research & Technical Grounding**:
  According to binary serialization and buffer validation principles documented in Context7, deserialization of versioned composite payloads must validate base slice length invariants before extracting secondary offsets. In structures containing variable-length or optional feature tails (such as the VRC7 1,312-byte OPLL synthesizer state), inserting fields without dynamically recalibrating base offsets corrupts downstream payload parsing, leading to runtime deserialization failures or synthesizer state degradation.

#### 2.2.2 Ricoh 2A03 Internal Data Bus Open-Bus Desynchronization

- **Target File**: `crates/rustynes-core/src/bus.rs:4050-4056`
- **Severity**: Medium
- **Defect Description**:
  On the physical NES, the 2A03 CPU data bus is dynamic; when an address is read that is not driven by any device (CPU RAM, PPU, APU, or Cartridge), the capacitance of the physical bus lines retains the last driven voltage level for a brief decay window (~several frames). This value is known as "open bus".

  In `crates/rustynes-core/src/bus.rs`, `LockstepBus::raw_cpu_read` models this behavior. However, for unmapped cartridge reads, the code executes:

  ```rust
  0x4020..=0xFFFF => {
      if self.mapper.cpu_read_unmapped(addr) {
          // Unmapped read: bus stays at the floating-latch
          // value (per nesdev "Open bus behavior"). Don't
          // overwrite `open_bus` — return early.
          self.last_read_addr = addr;
          return self.open_bus;
      }
      let raw = self.mapper.cpu_read(addr);
      ...
  }
  self.last_read_addr = addr;
  self.open_bus = v;
  if !self.in_dmc_dma {
      self.internal_data_bus = v;
  }
  v
  ```

  Notice that returning early at line 4055 bypasses lines 4088-4091 (`self.internal_data_bus = v;`).

  On the Ricoh 2A03, when the CPU reads an unmapped bus location, the CPU's internal data input latches capture the floating voltage present on the pins. By bypassing `self.internal_data_bus = v`, the emulator allows `self.internal_data_bus` to retain a stale value from an earlier cycle. When software subsequently reads the APU Status Register at `$4015`, bit 5 is documented by NESdev to return the open-bus value of the internal data bus (`internal_data_bus & 0x20`). Failing to update `internal_data_bus` during unmapped reads leads to bus divergence and test ROM failures in strict open-bus validation suites.

- **Remediation**:
  Allow unmapped reads to set `v = self.open_bus;` and fall through to the common internal bus update path, ensuring that `self.internal_data_bus` captures the open bus value without corrupting external floating state.

### 2.3 Performance & Scheduling Bottlenecks

#### 2.3.1 Hot-Path Overhead from Deprecated Pre-v2.0.0 NMI Edge Detector

- **Target File**: `crates/rustynes-core/src/bus.rs:3239, 3262, 3436-3442, 4530-4534, 4723`
- **Severity**: Medium
- **Performance Impact**: 4.1% to 4.7% execution penalty on palette-intensive frames.
- **Analysis**:
  During the pre-v2.0.0 development cycle, PPU NMI edge detection was tracked via `sample_nmi_edge()`, which updated `self.nmi_edge_latch` and `self.last_nmi_level`. In the single-clock cycle-accurate engine shipped in v2.0.0 (ADR 0002 / ADR 0029), interrupt handling was refactored: the CPU samples `bus.nmi_level()` directly at the phase boundary in `Cpu::handle_interrupts`.

  However, `sample_nmi_edge()` remains active on the hot path, executing at lines 3239, 3262, and 4723 for every single PPU dot. The edge latch it mutates (`self.nmi_edge_latch`) is only read by `Bus::poll_nmi`, which is deprecated with zero callers in the production emulation loop. As formally measured in ADR 0042, executing this dead edge sampling 3 times per CPU cycle costs 4.1% to 4.7% of core throughput.

- **Remediation**:
  Remove `sample_nmi_edge()` calls from `tick_one_cpu_cycle` and `run_ppu_to`, delete `self.nmi_edge_latch` and `self.last_nmi_level` from `LockstepBus`, and eliminate the legacy snapshot fields per ADR 0042.

#### 2.3.2 Audio Buffer Allocation Overhead & Zero-Allocation Streaming

- **Target File**: `crates/rustynes-apu/src/blip.rs:315-349`
- **Severity**: Low
- **Performance Impact**: 60 heap allocations per second during audio processing.
- **Analysis**:
  `BlipBuf::drain_all` returns a `Vec<f32>` by value. To avoid holding a lock across consumers, it invokes `core::mem::replace(&mut self.samples, Vec::with_capacity(...))` on every frame. When consumed by mobile or libretro frontends (`NesController::drain_audio`), this results in continuous heap allocation and deallocation cycles (60 times per second), increasing memory allocator lock contention and nursery garbage collection pressure.

- **Remediation**:
  Introduce a zero-allocation drain API `BlipBuf::drain_into(&mut self, out: &mut Vec<f32>) -> usize` that drains existing samples into a caller-supplied pre-allocated buffer via `out.extend(self.samples.drain(..))`.

## 3. RustyNES Frontends, Mobile & Web Audit

### 3.1 Desktop Frontend & Presentation Layer (`rustynes-frontend`)

#### 3.1.1 Gamepad Disconnect State Retention & Port Exhaustion Leak

- **Target Files**:
  - `crates/rustynes-frontend/src/input.rs:608-626, 942-954`
  - `crates/rustynes-frontend/src/app.rs:2340-2351`
- **Severity**: High
- **Defect Description**:
  In `rustynes-frontend`, physical gamepads are managed by the `gilrs` crate and tracked inside `InputState` via `PadAssignment`:

  ```rust
  #[derive(Debug, Clone, Default)]
  struct PadAssignment {
      ids: [Option<gilrs::GamepadId>; MAX_PADS],
  }

  impl PadAssignment {
      fn player_for(&mut self, id: gilrs::GamepadId) -> Option<usize> {
          if let Some(i) = self.ids.iter().position(|&slot| slot == Some(id)) {
              return Some(i);
          }
          let free = self.ids.iter().position(Option::is_none)?;
          self.ids[free] = Some(id);
          Some(free)
      }
  }
  ```

  When a gamepad event occurs, `InputState::handle_gamepad_event` assigns or looks up the player index associated with the gamepad ID. However, when a controller disconnects, two compounding failures occur:

  1. **Held Button Latching**: If a controller is disconnected while a button (such as A, B, or D-Pad) is held down, `gilrs::EventType::Disconnected` is received. `handle_gamepad_event` falls through to `_ => {}`. The held button states in `self.gamepad_buttons[player]` and axis states in `self.gamepad_axis[player]` are never cleared. The virtual NES controller sees that button pressed down permanently.
  2. **Port Slot Exhaustion Leak**: `PadAssignment` has no `release()` method. When `gilrs` detects a disconnect and subsequent reconnect (or a different controller is plugged in), it assigns a new distinct `GamepadId`. `player_for()` scans `self.ids` for a free slot (`Option::is_none`). Because disconnected IDs are never cleared, after exactly four connect/disconnect cycles, all four slots in `self.ids` are permanently occupied by dead IDs. At that point, `player_for()` returns `None`, and the emulator ceases responding to any physical gamepad inputs until the process is restarted.

- **Remediation**:
  Add a `release(&mut self, id: gilrs::GamepadId) -> Option<usize>` method to `PadAssignment` that sets the matching slot to `None`. In `handle_gamepad_event`, handle `gilrs::EventType::Disconnected` by clearing `gamepad_buttons[player]`, zeroing `gamepad_axis[player]`, and calling `self.pad_assignment.release(id)`.

- **Context7 Research & Gamepad Lifecycle Management (`/websites/rs_gilrs_gilrs`)**:
  Consulting the `gilrs` documentation in Context7 (`/websites/rs_gilrs_gilrs`) reveals the event queue architecture under `Gilrs::next_event()`. Disconnect events (`EventType::Disconnected`) signal that a physical gamepad connection has terminated. When a device disconnects and later reconnects (or when a player switches controller ports), `gilrs` does not guarantee reuse of the prior `GamepadId`; instead, a newly generated distinct `GamepadId` is allocated. If the host application does not explicitly release the slot mapping upon receiving `EventType::Disconnected`, the fixed controller array (`[Option<GamepadId>; MAX_PADS]`) suffers from slot leak exhaustion. Furthermore, because axis and button release events are not synthesized post-disconnect, unreleased button state remains permanently latched.

#### 3.1.2 Desktop SOCD Cleaning Gap

- **Target File**: `crates/rustynes-frontend/src/input.rs:874-879`
- **Severity**: Medium
- **Defect Description**:
  On an original Nintendo Entertainment System controller, the mechanical cross-rocker under the plastic directional pad pivots around a central ball bearing, making it physically impossible to depress `Up` and `Down` or `Left` and `Right` simultaneously. However, on desktop keyboards, hitboxes, or arcade stick configurations, players can easily actuate opposing cardinal keys simultaneously.

  In `InputState::player`:

  ```rust
  pub fn player(&self, player: usize) -> Buttons {
      if player >= MAX_PADS {
          return Buttons::empty();
      }
      self.keyboard_buttons[player] | self.gamepad_buttons[player] | self.gamepad_axis[player]
  }
  ```

  The raw bitmasks are combined via bitwise OR without validation. When a player presses opposing directions, the NES hardware register receives both bits set (`UP | DOWN` or `LEFT | RIGHT`). In games such as *The Legend of Zelda*, *Mega Man*, *Super Mario Bros.*, and *Castlevania*, the original 6502 engine routines do not validate opposing inputs, resulting in screen boundary clipping, integer underflow displacement, and catastrophic memory corruption glitches.

- **Remediation**:
  Apply standard SOCD (Simultaneous Opposing Cardinal Directions) Neutral Cleaning before returning `Buttons`. If both `UP` and `DOWN` are asserted, clear both; if both `LEFT` and `RIGHT` are asserted, clear both.

#### 3.1.3 Host Audio Synchronization & Texture Presentation Architecture

- **Subsystems**: `crates/rustynes-frontend/src/audio.rs`, `crates/rustynes-frontend/src/gfx.rs`
- **Context7 Research & Technical Grounding (`/rustaudio/cpal`, `/websites/rs_wgpu`)**:
  - **CPAL Audio Stream Buffer Negotiation**: According to CPAL documentation retrieved via Context7 (`/rustaudio/cpal`), `cpal::BufferSize::Default` defers stream buffer sizing to host audio subsystem defaults (such as PipeWire quantum sizes or ALSA hardware periods) rather than applying fixed internal buffers. On modern Linux desktop systems with PipeWire, host quantum shifts under system load can cause buffer underruns if the emulator's ring buffer cannot dynamically absorb latency variation. To maintain jitter-free 44.1/48 kHz audio playback, the frontend's ring buffer must maintain a bounded minimum watermark, or configure `cpal::BufferSize::Fixed` with an explicit fallback to `BufferSize::Default` upon `BuildStreamError::StreamConfigNotSupported`.
  - **wgpu Texture Streaming Pipeline**: Consulting the `wgpu` API specification via Context7 (`/websites/rs_wgpu`) confirms that high-frequency 60 FPS texture updates (such as writing the $256 \times 240$ NES framebuffer) via `wgpu::Queue::write_texture` with a properly aligned `TexelCopyBufferLayout` (`bytes_per_row: Some(NES_W * 4)`) achieve direct host-to-device memory staging without intermediate command encoder overhead. Maintaining pre-allocated linear staging buffers across frames ensures zero-allocation texture presentation.

### 3.2 Android Host & JNI/NDK Bridge (`rustynes-android`, `android/`)

#### 3.2.1 VirtualController Touchpad Simultaneous Opposing Cardinal Directions

- **Target File**: `android/app/src/main/java/com/doublegate/rustynes/VirtualController.kt:120-128, 186-194`
- **Severity**: Medium
- **Defect Description**:
  The Android mobile application implements an on-screen multi-touch directional pad in `VirtualController.kt`. When tracking multi-touch pointer events across the touch area, the active touches are iterated over:

  ```kotlin
  for (pos in active.values) m = m or hitTest(pos.x, pos.y, w, h)
  ...
  if (dy < -dz) m = m or NesBit.UP
  if (dy > dz) m = m or NesBit.DOWN
  if (dx < -dz) m = m or NesBit.LEFT
  if (dx > dz) m = m or NesBit.RIGHT
  ```

  If a user rests two fingers or slides their thumb across the boundary of the virtual D-pad, touches in opposing sectors activate simultaneously, bitwise-ORing `UP | DOWN` or `LEFT | RIGHT` into `m`. This raw mask is transmitted directly to the native core via JNI, exposing Android users to the same collision bugs present on desktop.

- **Remediation**:
  In `VirtualController.kt`, implement neutral SOCD cleaning prior to invoking `onButtonsChanged(m)`. If both `NesBit.UP` and `NesBit.DOWN` are set, mask them out with `m and (NesBit.UP or NesBit.DOWN).inv()`; apply identical neutral cancellation for `LEFT` and `RIGHT`.

#### 3.2.2 JNI Bisqwit NTSC Per-Frame Heap Thrashing & Zero-Copy Optimization

- **Target Files**:
  - `crates/rustynes-android/src/gfx.rs:77, 412, 484`
  - `crates/rustynes-android/src/lib.rs:284-309`
- **Severity**: Medium
- **Performance Impact**: 7.37 MB/s of continuous garbage collection allocations in the Java Virtual Machine.
- **Analysis**:
  When Bisqwit NTSC composite video filtering is active, the Android frontend delivers indexed palette frames to the native graphics layer via `NativeRenderer_nativeSetIndexFrame`:

  ```rust
  pub extern "C" fn Java_com_doublegate_rustynes_NativeRenderer_nativeSetIndexFrame(
      mut env: EnvUnowned,
      _this: JObject,
      handle: jlong,
      idx: JByteArray,
      phase: jint,
  ) {
      guarded("nativeSetIndexFrame", (), || {
          ...
          let bytes = env
              .with_env(|env| -> jni::errors::Result<Vec<u8>> {
                  env.convert_byte_array(&idx)
              })
              .resolve::<LogErrorAndDefault>();
          ...
          gfx.set_index_frame(&bytes, phase.max(0) as u8);
      })
  }
  ```

  `env.convert_byte_array(&idx)` allocates a new 122,880-byte `Vec<u8>` on the Rust heap on every frame ($256 \times 240 \times 2 = 120\,\text{KiB}$). At 60 FPS, this generates over 7.37 MB of allocations per second, triggering Android ART nursery GC pauses and frame rate stuttering.

  In contrast, the primary video rendering function `nativeRender` uses a pre-allocated native buffer and accesses Java arrays using `env.get_byte_array_region`, which copies directly into existing memory without allocating heap vectors.

- **Remediation**:
  Refactor `AndroidGfx` and `nativeSetIndexFrame` to adopt the zero-copy buffer pattern: pre-allocate `index_buf` on `AndroidGfx` (`crates/rustynes-android/src/gfx.rs`), expose helper methods `index_buf_mut()` and `commit_index_frame(phase)`, and copy into it directly via `idx.get_region(env, 0, buf_i8)` without allocating a temporary `Vec<u8>` on every frame.

- **Context7 Research & Mobile Texture Staging (`/websites/rs_wgpu`)**:
  Consulting the `wgpu` specification in Context7 (`/websites/rs_wgpu`) regarding mobile graphics constraints emphasizes that per-frame CPU-side heap allocations on JNI boundaries cause heap fragmentation and ART garbage collector pressure. Reusing a persistent staging buffer on `AndroidGfx` and streaming bytes to `wgpu::Queue::write_texture` with fixed byte layouts (`bytes_per_row: Some(NES_W * 2)`) preserves predictable 16.6 ms frame timing on Android mobile devices.

### 3.3 iOS Host & Metal/SwiftUI Presentation (`rustynes-ios`, `ios/`)

#### 3.3.1 MultiTouchControlPad SOCD Filtering Gap

- **Target Files**:
  - `ios/RustyNES/MultiTouchControlPad.swift:410-426`
  - `ios/RustyNES/ControlPadLayout.swift:151-170`
- **Severity**: Medium
- **Defect Description**:
  Similar to the Android touch implementation, the iOS on-screen touch controller in `MultiTouchControlPad.swift` iterates over all touches in the control view:

  ```swift
  for touch in event?.allTouches ?? [] where touch.view === self {
      ...
      mask.formUnion(ControlPadLayout.hitTest(touch.location(in: self), in: bounds.size))
  }
  ```

  Multi-touch gestures that bridge opposing quadrant boundaries generate simultaneous opposing direction bits. No SOCD filtering is performed before sending the button mask across the Swift-to-Rust UniFFI bridge.

- **Remediation**:
  In `ControlPadLayout.swift`, apply neutral cancellation to the computed `mask`: if `mask.contains(.up)` and `mask.contains(.down)`, clear both using `mask.set(.up, pressed: false)` and `mask.set(.down, pressed: false)`; if `mask.contains(.left)` and `mask.contains(.right)`, clear both using `mask.set(.left, pressed: false)` and `mask.set(.right, pressed: false)`.

#### 3.3.2 Wall-Clock vs. Emulated-Frame Turbo Pacing Desynchronization

- **Target File**: `ios/RustyNES/GameControllerManager.swift:166, 343-360`
- **Severity**: Low
- **Defect Description**:
  On desktop (`crates/rustynes-frontend/src/emu.rs:358-365`), turbo autofire is paced deterministically according to the emulated frame counter (`frame / period % 2 == 0`). This ensures that turbo buttons oscillate at exactly the desired rate (e.g. 30 Hz at 1x speed, 60 Hz at 2x fast-forward) in lockstep with the NES CPU.

  In iOS `GameControllerManager.swift`, turbo pacing is implemented via a decoupled `Foundation.Timer` running on the iOS `RunLoop` at a fixed 30 Hz wall-clock interval:

  ```swift
  let timer = Timer(timeInterval: 1.0 / 30.0, repeats: true) { [weak self] _ in
      guard let self else { return }
      self.turboPhase.toggle()
      for m in self.managed where m.turbo.bits != 0 { self.emit(m) }
  }
  RunLoop.main.add(timer, forMode: .common)
  ```

  When the user pauses the emulator, fast-forwards at 3x or 4x speed, or experiences thermal throttling below 60 FPS, the wall-clock turbo continues pulsing independently. When unpausing or running at variable speeds, button presses oscillate asynchronously, causing missed inputs and non-deterministic behavior during gameplay.

- **Remediation**:
  Remove the wall-clock `Timer` in `GameControllerManager.swift` and advance `turboPhase` synchronously on each emulated frame tick.

### 3.4 Cross-Platform Netplay & Signaling Subsystem (`rustynes-netplay`)

#### 3.4.1 Unbounded Frame Lookahead Remote Denial-of-Service / OOM

- **Target File**: `crates/rustynes-netplay/src/session.rs:427-447, 580-591, 613-618`
- **Severity**: Critical
- **Vulnerability Description**:
  In `crates/rustynes-netplay/src/session.rs`, peer-to-peer rollback netplay sessions process incoming UDP network packets via `RollbackSession::advance`.
  When processing `NetMessage::Input` or `NetMessage::Checksum`, the code extracts the remote `frame` number and unconditionally executes:

  ```rust
  fn ensure_frame(&mut self, frame: u32) {
      let need = frame as usize + 1;
      if self.history.len() < need {
          self.history.resize(need, InputSlot::default());
      }
      if self.snapshots.len() < need {
          self.snapshots.resize(need, None);
      }
      if self.local_checksums.len() < need {
          self.local_checksums.resize(need, None);
      }
      if self.confirmed_hashes.len() < need {
          self.confirmed_hashes.resize(need, None);
      }
      if self.remote_checksums.len() < need {
          self.remote_checksums.resize(need, None);
      }
      if self.confirmed_entering.len() < need {
          self.confirmed_entering.resize(need, None);
      }
  }
  ```

  There is zero validation of the incoming `frame` index. A remote attacker connected to a netplay session can send a single UDP packet with `frame = 0x7FFF_FFFF`.

  `ensure_frame` immediately attempts to resize six internal vectors to $2,147,483,648$ elements each. Allocating gigabytes of memory triggers an unrecoverable out-of-memory (OOM) abort across the entire operating system, terminating the victim's emulator process instantly.

  Notably, `crates/rustynes-netplay/src/spectator.rs:315-318` already contains an explicit defense against this exact vector:

  ```rust
  let horizon = self.last_confirmed_frame.map_or(0, |c| c + 1);
  if frame > horizon.saturating_add(MAX_SPECTATOR_FRAME_LOOKAHEAD) {
      continue;
  }
  ```

  However, `session.rs` was left unprotected.

- **Remediation**:
  Define `pub const MAX_SESSION_FRAME_LOOKAHEAD: u32 = 1024;`. In `session.rs`, calculate `max_allowed = self.current_frame.saturating_add(MAX_SESSION_FRAME_LOOKAHEAD)`. If an incoming packet's `frame` exceeds `max_allowed`, drop the packet immediately without calling `ensure_frame`.

#### 3.4.2 Signaling Relay Ghost Client Leak & Room Persistence

- **Target File**: `crates/rustynes-netplay/src/signaling.rs:629-642, 697-733`
- **Severity**: Medium
- **Defect Description**:
  The netplay signaling relay (`Relay`) tracks active matchmaking rooms and client mappings:

  ```rust
  // crates/rustynes-netplay/src/signaling.rs:730-731
  room.slots.push(client);
  self.client_room.insert(client, room_code.to_string());
  ```

  When a client disconnects, `disconnect()` looks up `self.client_room.remove(&client)`, finds the room, removes the client from `room.slots`, and deletes the room if `room.slots.is_empty()`.

The client remains registered in `slots` of "Room A" as a ghost client. When the client eventually disconnects, only "Room B" is looked up and cleaned up. ### 3.5 Mobile Bridge Panic Containment (`rustynes-mobile`)

#### 3.5.1 UniFFI HD Pack Compositing Uncaught Panic & Mutex Poisoning

- **Target File**: `crates/rustynes-mobile/src/lib.rs:1345-1382`
- **Severity**: High
- **Defect Description**:
  In `crates/rustynes-mobile/src/lib.rs`, `NesController` exposes emulation APIs to Kotlin and Swift via UniFFI. All major emulation functions (such as `step_frame` and `contained_frame`) wrap their logic inside `catch_ffi_panic` to ensure that panics do not unwind into foreign C/Swift/Java runtimes.

  However, `composite_hd_frame` executes without panic containment:

  ```rust
  pub fn composite_hd_frame(&self) -> Vec<u8> {
      let mut g = self.lock();
      ...
      let out = comp
          .composite(&framebuffer, &hd_tiles, &watched, |addr| {
              chr.get((addr & 0x1FFF) as usize).copied().unwrap_or(0)
          })
          .to_vec();
      drop(g);
      out
  }
  ```

  If an out-of-bounds tile index or memory allocation error triggers a panic inside `comp.composite()`, the unwinding panic poisons the `self.lock()` mutex while the lock is held. - **Remediation**:

- **Context7 Research & Foreign Function Interface Panic Safety (`/mozilla/uniffi-rs`)**:
  UniFFI architectural documentation in Context7 (`/mozilla/uniffi-rs`) specifies that foreign-to-Rust function calls must never allow Rust panics to unwind across the FFI boundary. UniFFI relies on `std::panic::catch_unwind` on all exported entry points. If a panic unwinds uncontained across an FFI boundary without `catch_unwind`, it violates C-ABI calling conventions, corrupts stack frames, and causes an immediate process crash or aborts foreign runtimes (throwing an uncaught `InternalException` in Kotlin or terminating with `SIGABRT` in Swift). Wrapping internal operations in `catch_ffi_panic` ensures that any unexpected composite failure is gracefully caught, leaving mutex locks unpoisoned.

## 4. RustyNES Libretro Core & Toolchain Audit

### 4.1 C-ABI Safety & Panic Containment Boundary

#### 4.1.1 Uncontained Panic Abort Vulnerability in `disk_image_label`

- **Target File**: `crates/rustynes-libretro/src/lib.rs:1773-1799`
- **Severity**: High
- **Vulnerability Description**:
  In `rustynes-libretro`, RetroArch C-ABI callbacks must adhere to strict FFI panic boundaries. Almost all callbacks (`on_run`, `on_reset`, `on_serialize`, `on_unserialize`) wrap their execution in `contained(|| { ... })` using `std::panic::catch_unwind`.

  However, in `disk_image_label`:

  ```rust
  unsafe extern "C" fn disk_image_label(
      index: std::os::raw::c_uint,
      label: *mut std::os::raw::c_char,
      len: usize,
  ) -> bool {
      if label.is_null() || len == 0 {
          return false;
      }
      let sides = unsafe { rust_libretro::retro_get_num_images_callback() };
      if index >= sides {
          return false;
      }
      let text = side_label(index);
      let n = text.len().min(len - 1);
      unsafe {
          std::ptr::copy_nonoverlapping(text.as_ptr(), label.cast::<u8>(), n);
          *label.add(n) = 0;
      }
      true
  }
  ```

  `disk_image_label` is exported as an `unsafe extern "C"` function registered with RetroArch via `register_disk_control`. It contains no `catch_unwind` guard. If `side_label(index)` (which performs dynamic formatting via `format!("Side {}")`) or any memory operation triggers a panic, the panic unwinds directly to the `extern "C"` boundary.

  Under the Rust Language Reference, an unwinding panic that crosses a non-unwinding C-ABI boundary results in an immediate hard process abort (`std::process::abort()`). This causes RetroArch to terminate violently without flushing SRAM, writing save states, or cleanly shutting down audio/video devices.

- **Remediation**:
  Wrap the entire callback body in `std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| { ... })).unwrap_or(false)`.

#### 4.1.2 Release Profile Panic Strategy Alignment

- **Target Files**:
  - `Cargo.toml:289`
  - `crates/rustynes-libretro/build.rs:20-38`
  - `crates/rustynes-libretro/Makefile:21`
- **Severity**: Medium
- **Defect Description**:
  The workspace `Cargo.toml` sets `panic = "abort"` under `[profile.release]` to optimize binary size and execution speed for desktop targets. In `rustynes-libretro`, however, panic containment relies entirely on `std::panic::catch_unwind`, which requires `panic = "unwind"`.

While the project `Makefile` sets this environment variable, developers or CI pipelines running standard `cargo build --release -p rustynes-libretro` compile the library with `panic = "abort"`. Under `panic = "abort"`, all `catch_unwind` blocks in the core are rendered completely inert, turning any internal error into an immediate frontend crash.

- **Remediation**:

#### 4.1.3 Upstream `rust-libretro` Crate C-ABI Hazards

- **Target Files**:
  - `vendor/rust-libretro-sys`
  - `rust-libretro-0.3.2/src/lib.rs:33, 334, 543-565`
- **Severity**: Medium
- **Analysis**:

  1. **Const-to-Mutable Pointer Casting in `retro_unserialize`**: Line 543 receives `data: *const c_void` from the frontend, casts it to `data as *mut u8`, and constructs `std::slice::from_raw_parts_mut(data as *mut u8, size)`. ### 4.2 Global State, Memory Mapping & Lifecycle Hygiene

#### 4.2.1 Memory Map Use-After-Free Vulnerability on Direct `retro_deinit`

- **Target File**: `crates/rustynes-libretro/src/lib.rs:2294-2314, 2327-2348`
- **Severity**: High
- **Vulnerability Description**:
  `rustynes-libretro` registers physical memory maps with RetroArch via `RETRO_ENVIRONMENT_SET_MEMORY_MAPS` so that RetroAchievements (`rcheevos`) and cheat engines can directly inspect WRAM, SRAM, and CIRAM.

  In `on_unload_game` (lines 2336-2346), memory maps are safely withdrawn before dropping `self.nes`:

  ```rust
  if std::mem::take(&mut self.memory_maps_registered) {
      let empty = retro_memory_map {
          descriptors: std::ptr::null(),
          num_descriptors: 0,
      };
      rust_libretro::environment::set_memory_maps(cb, empty);
  }
  ```

  However, in `on_deinit` (lines 2294-2300):

  ```rust
  fn on_deinit(&mut self, _ctx: &mut DeinitContext) {
      self.persist_fds_disk();
      self.fds_save_path = None;
      self.nes = None;
      self.dual = None;
      ...
  ```

  If a frontend skips calling `retro_unload_game` and directly invokes `retro_deinit` (which the libretro API specification permits during abrupt shutdowns or core swaps), `self.nes = None` executes without withdrawing the memory map descriptors.

  The console memory (WRAM, SRAM, VRAM) is deallocated. However, the frontend and background RetroAchievements worker threads retain the registered raw memory pointers. Subsequent memory reads or writes by the frontend access deallocated heap pages, resulting in a severe Use-After-Free (UAF) memory corruption vulnerability. Furthermore, `self.memory_maps_registered` is not reset in `on_deinit`, leaving state desynchronized across init cycles.

- **Remediation**:
  In `on_deinit`, check `if std::mem::take(&mut self.memory_maps_registered)` and send an empty `retro_memory_map` to RetroArch before setting `self.nes = None`. Additionally, reset `vs_descriptors` via `self.describe_inputs(cb, None)`.

- **Context7 Research & Libretro Core Lifecycle (`/websites/libretropy_readthedocs_io_en`)**:
  Per the libretro API specification and bindings documented in Context7 (`/websites/libretropy_readthedocs_io_en`), the frontend environment callback `RETRO_ENVIRONMENT_SET_MEMORY_MAPS` registers physical memory descriptors (`retro_memory_descriptor`) directly with the host frontend. The libretro lifecycle specification explicitly permits frontends to terminate cores via `retro_deinit()` directly without first invoking `retro_unload_game()`. If memory descriptors are registered during execution, the core MUST deregister them by passing an empty `retro_memory_map` (with `descriptors: null` and `num_descriptors: 0`) prior to freeing the underlying console buffers. Failing to clear memory descriptors on direct deinitialization leaves the host process and RetroAchievements worker threads holding dangling pointers, resulting in Use-After-Free memory corruption.

### 4.3 Rollback Serialization & Netplay Optimization

#### 4.3.1 Pre-Allocation Headroom Deficit in `load_game`

- **Target File**: `crates/rustynes-libretro/src/lib.rs:1119-1144`
- **Severity**: Medium
- **Performance Impact**: Heap allocation and reallocation during the first frame of run-ahead or rollback netplay.
- **Analysis**:
  In `RustyNesLibretro::load_game`:

  ```rust
  let mut tmp = Vec::new();
  nes.snapshot_core_into(&mut tmp);
  self.serialize_size = tmp.len() + rustynes_core::SAVE_STATE_DEVICE_HEADROOM;
  ```

  And for dual-system arcade games:

  ```rust
  let mut sizing = Vec::new();
  dual.snapshot_into(&mut sizing);
  self.serialize_size = sizing.len();
  ```

  The code allocates a temporary `tmp` / `sizing` vector, serializes into it to measure the size, and immediately drops it. `self.serialize_buffer` is left at capacity 0 (`Vec::new()`).

  Consequently, on the very first frame where RetroArch invokes `on_serialize` (which occurs immediately upon entering rollback netplay or enabling 1-frame/2-frame Run-Ahead latency reduction), `self.serialize_buffer` must allocate ~260 KB (or ~645 KB for dual-system) on the heap during active gameplay. This violates the project's zero-allocation hot-path guarantee.

- **Remediation**:
  Perform the initial sizing snapshot directly into `self.serialize_buffer`, record its length, and call `self.serialize_buffer.reserve(rustynes_core::SAVE_STATE_DEVICE_HEADROOM)`. This pre-warms the buffer to its maximum capacity during ROM load, guaranteeing zero heap allocations during gameplay.

### 4.4 Video/Audio Pipeline Optimization & Toolchain

#### 4.4.1 Branchless Joypad Bitmask Decoding

- **Target File**: `crates/rustynes-libretro/src/lib.rs:637-664`
- **Severity**: Low
- **Performance Impact**: Up to 32 conditional branch instructions executed per frame.
- **Analysis**:
  In `nes_buttons(jp: JoypadState)`:

  ```rust
  let mut bt = rustynes_core::Buttons::empty();
  if jp.contains(JoypadState::A) { bt |= rustynes_core::Buttons::A; }
  if jp.contains(JoypadState::B) { bt |= rustynes_core::Buttons::B; }
  if jp.contains(JoypadState::SELECT) { bt |= rustynes_core::Buttons::SELECT; }
  if jp.contains(JoypadState::START) { bt |= rustynes_core::Buttons::START; }
  if jp.contains(JoypadState::UP) { bt |= rustynes_core::Buttons::UP; }
  if jp.contains(JoypadState::DOWN) { bt |= rustynes_core::Buttons::DOWN; }
  if jp.contains(JoypadState::LEFT) { bt |= rustynes_core::Buttons::LEFT; }
  if jp.contains(JoypadState::RIGHT) { bt |= rustynes_core::Buttons::RIGHT; }
  bt
  ```

  Comparing `rust_libretro::types::JoypadState` (bits: B=0, SELECT=2, START=3, UP=4, DOWN=5, LEFT=6, RIGHT=7, A=8) with `rustynes_core::Buttons` (bits: A=0, B=1, SELECT=2, START=3, UP=4, DOWN=5, LEFT=6, RIGHT=7):

  - Bits 2 through 7 (`0xFC`: SELECT, START, UP, DOWN, LEFT, RIGHT) are bit-identical in both representations.
  - Button `A` is bit 8 in `JoypadState` and bit 0 in `Buttons`: `(raw >> 8) & 1`.
  - Button `B` is bit 0 in `JoypadState` and bit 1 in `Buttons`: `(raw & 1) << 1`.

  Evaluating 8 branches per controller across 4 ports burns CPU pipeline bandwidth on predictable branches that can be replaced with 3 bitwise operations.

- **Remediation**:
  Replace `nes_buttons` with branchless bit arithmetic:

  ```rust
  let raw = jp.bits();
  let common = (raw & 0xFC) as u8;
  let a = ((raw >> 8) & 0x01) as u8;
  let b = ((raw & 0x01) << 1) as u8;
  rustynes_core::Buttons::from_bits_truncate(common | a | b)
  ```

#### 4.4.2 Elimination of Redundant 491.5 KB Zero-Fill in Vs. Dual-System Composition

## 5. RustyNES_MiSTer Hardware RTL Core Audit

### 5.1 SDRAM Controller & Bus Arbitration Correctness

#### 5.1.1 Lost-Write Race Condition in Non-Blocking Arbiter

- **Target File**: `rtl/sdram_arbiter.sv:358-363, 374-378`
- **Severity**: Critical
- **Defect Description**:
  The 4-port SDRAM arbiter (`sdram_arbiter.sv`) arbitrates access between CHR fetches, PRG fetches, PPU pattern table dumpers, and CPU/cartridge writes. Writes are buffered in holding registers:

  ```systemverilog
  // rtl/sdram_arbiter.sv:358-363
  if (wr_stb) begin
      if (wr_pend) overrun <= 1'b1;
      wr_pend      <= 1'b1;
      wr_hold      <= wr_addr;
      wr_data_hold <= wr_data;
  end

  // rtl/sdram_arbiter.sv:366-378
  if (granting) begin
      ...
      if (grant_chr)      begin serving <= SRC_CHR; chr_pend <= 1'b0; end
      else if (grant_prg) begin serving <= SRC_PRG; prg_pend <= 1'b0; end
      else if (grant_pd)  begin serving <= SRC_PD;  pd_pend  <= 1'b0; end
      else                begin serving <= SRC_WR;  wr_pend  <= 1'b0; end
  end
  ```

  In SystemVerilog IEEE 1800-2017 non-blocking assignment (`<=`) semantics, procedural assignments within the same `always_ff` block execute sequentially, and the final assignment to a register in that clock cycle determines the value latched on the next rising clock edge.

  Consider the cycle $T$ where a previously pending write is granted by the arbiter (`grant_wr` asserts, triggering line 377). If an external master (such as the ROM loader or a back-to-back CHR-RAM write from the CPU) simultaneously asserts `wr_stb` on cycle $T$:

  1. Lines 358–363 execute first: `wr_hold` and `wr_data_hold` capture the *new* write's address and data, and assign `wr_pend <= 1'b1;`.
  2. Later in the same block, lines 366–378 execute: because the *old* write is being granted, line 377 evaluates and executes `wr_pend <= 1'b0;`.
  3. Because line 377 executes last, `wr_pend` is latched as `0` on the next clock edge!

  The arbiter issues the old write that was granted. However, the newly arrived write captured in `wr_hold` has had its pending flag silently cleared (`wr_pend == 0`). When the current write finishes and the bus returns to idle, the arbiter believes no writes are pending. The write captured in `wr_hold` is never issued to the SDRAM. This leads to silent cartridge RAM or CHR-RAM data loss during heavy memory traffic.

  Notice that for CHR, PRG, and PD, lines 349, 352, and 356 guard the pending flag: `if (!grant_chr) chr_pend <= 1'b1;`. For writes, this guard was omitted.

- **Remediation**:
  In line 377, guard the pending flag clear: `else begin serving <= SRC_WR; if (!wr_stb) wr_pend <= 1'b0; end`.

#### 5.1.2 Missing Bank Address Pin Drive in `S_ACTIVE`

- **Target File**: `rtl/sdram.sv:677-688`
- **Severity**: High
- **Defect Description**:
  The Alliance AS4C32M16SB synchronous DRAM chip requires that the bank address lines `BA[1:0]` remain valid and stable during both the row activation command (`C_ACTIVE`) and the subsequent column read/write commands (`C_READ` / `C_WRITE`).

  In `rtl/sdram.sv`, the controller handles row hits in `S_IDLE` by driving both `sdram_ba <= a_bank;` and `sdram_a <= a_col;` (Line 664).
  However, when servicing a row miss, the controller transitions through `S_ACTIVE` after waiting for $t_{RCD}$:

  ```systemverilog
  S_ACTIVE: if (wait_ctr == '0) begin
      cmd         <= pending_we ? C_WRITE : C_READ;
      sdram_a     <= '0;
      sdram_a[COL_BITS-1:0] <= a_col;
      sdram_a[10] <= 1'b0;          // NO auto-precharge: row stays open
      sdram_dqm   <= pending_we ? pending_dqm : 2'b00;
      if (pending_we) begin
          sdram_dq_out <= pending_din;
          sdram_dq_oe  <= 1'b1;
      end
      state <= S_RW;
  end
  ```

  `sdram_ba` is omitted from `S_ACTIVE`! The code relies entirely on register retention from the `S_PRE` state (lines 647–659) across several clock cycles.

  In modern FPGA synthesis flows (Quartus Prime / Synopsys), registers that are unassigned in specific FSM state transitions are subject to register retiming, replication, and physical placement fanout replication. Under high clock frequencies (85.9 MHz SDRAM clock), relying on retention rather than explicit assignment creates glitch hazards and setup/hold timing skew across the two bank select pins (`SDRAM_BA[0]` and `SDRAM_BA[1]`), potentially addressing the wrong memory bank during column access.

- **Remediation**:
  Explicitly drive `sdram_ba <= a_bank;` inside `S_ACTIVE` alongside `sdram_a`.

#### 5.1.3 SDRAM Auto-Refresh Starvation & Debt Accumulation Failure

- **Target File**: `rtl/sdram.sv:472-486, 633-638`
- **Severity**: High
- **Defect Description**:
  The JEDEC SDRAM standard requires 8,192 auto-refresh cycles every 64 ms (an average refresh interval $t_{REFI} = 7.8125\,\mu\text{s}$). Under sustained memory traffic, refreshes may be temporarily postponed, but JEDEC permits a maximum of 8 delayed refreshes which must be performed immediately once the bus becomes idle.

  In `rtl/sdram.sv`:

  ```systemverilog
  // rtl/sdram.sv:472-477
  if (refi_ctr >= REFI_BITS'(CK_REFI)) begin
      refi_ctr        <= '0;
      refresh_pending <= 1'b1;
  end else begin
      refi_ctr <= refi_ctr + 1'b1;
  end

  // rtl/sdram.sv:633-638
  end else if (refresh_pending) begin
      cmd             <= C_REFRESH;
      refresh_pending <= 1'b0;
      wait_ctr        <= WAIT_BITS'(CKW_RFC);
      state           <= S_REFRESH;
  end
  ```

  `refresh_pending` is implemented as a 1-bit boolean flag.

  If the memory bus experiences sustained burst traffic (e.g. rapid back-to-back CHR/PRG DMA transfers during active scanline rendering) that delays refresh execution for $\ge 2 \times t_{REFI}$, `refi_ctr` expires a second time. Because `refresh_pending` is already `1'b1`, the counter rolls over, but the skipped refresh interval is completely lost.

  When the memory bus finally idles and executes line 633, `refresh_pending` is cleared to `0`. Exactly *one* refresh command is issued, leaving the SDRAM in an uncompensated refresh deficit. Over extended gaming sessions under high ambient temperatures, capacitive charge decay on unrefreshed rows causes random single-bit data corruption in PRG-ROM or WRAM.

- **Remediation**:
  Replace the 1-bit `refresh_pending` flag with a 4-bit saturating debt counter `logic [3:0] refresh_debt;`. Increment `refresh_debt` whenever `refi_ctr >= CK_REFI`, decrement it on each executed `C_REFRESH`, and assert `refresh_pending = (refresh_debt != 4'd0);`.

### 5.2 CPU, DMA, and Hardware Parity

#### 5.2.1 CPU Interrupt Edge Detector Freeze During OAM/DMC DMA

- **Target Files**:
  - `rtl/nes_top.sv:928-934`
  - `rtl/cpu6502.sv:1632-1637`
- **Severity**: Medium
- **Defect Description**:
  On the Ricoh 2A03 / NMOS 6502, Direct Memory Access (DMA) steals CPU bus cycles by asserting the RDY line. Halting execution prevents the instruction pointer from advancing, but the internal phase clocks and interrupt edge-detection latches remain continuously active.

  In the SystemVerilog implementation:

  ```systemverilog
  // rtl/nes_top.sv:928-934
  logic cpu_run_ce;
  assign cpu_run_ce = ce && !dma_stall_w;

  cpu6502 u_cpu (
      .clk  (clk),
      .rst_n(rst_n),
      .ce   (cpu_run_ce),
      ...
  );

  // rtl/cpu6502.sv:1632-1635
  end else if (ce) begin
      // The /NMI edge, sampled every CPU cycle regardless of state.
      nmi_n_q <= nmi_n;
      if (nmi_n_q && !nmi_n) nmi_pending <= 1'b1;
  ```

  `nes_top.sv` implements DMA cycle-stealing by completely gating off `u_cpu.ce` (`cpu_run_ce = ce && !dma_stall_w`).

  During an OAM DMA transfer, the CPU clock enable is disabled for 513 to 514 consecutive CPU cycles. Throughout this entire duration, line 1632 in `cpu6502.sv` does not execute! The edge-detection register `nmi_n_q` remains frozen.

  If the PPU asserts `/NMI` during DMA and subsequently deasserts it (or if a mapper IRQ line pulses low and returns high during DMA), `cpu6502` never observes the negative transition edge. When DMA completes and `cpu_run_ce` is restored, `nmi_n_q` and `nmi_n` are both observed at their post-DMA levels, and `nmi_pending` is never latched. This causes dropped VBlank interrupts in timing-critical games that initiate DMA near scanline 241.

- **Remediation**:
  In `cpu6502.sv`, decouple interrupt edge sampling from execution stall gating by introducing a dedicated un-stalled clock enable `ce_raw` (driven by the raw 1.79 MHz CPU phase tick from `nes_top.sv`). Evaluate interrupt edge detection concurrently with instruction decoding inside `always_ff` (using independent `if (ce_raw)` and `if (ce)` branches, rather than priority-chained `else if`), guaranteeing zero instruction starvation and zero lost interrupt transitions during DMA.

#### 5.2.2 64 MB Physical Address Truncation in Bus Arbiter

- **Target Files**:
  - `rtl/sdram_arbiter.sv:131, 185`
  - `rtl/emu.sv:258, 318, 347`
- **Severity**: Medium
- **Defect Description**:
  The physical Alliance AS4C32M16SB SDRAM chip populated on MiSTer SDRAM daughterboards contains 64 MB of storage ($32\,\text{M words} \times 16\,\text{bits}$), requiring 25 word address bits (`[24:0]`) or 26 byte address bits (`[25:0]`).

  In `sdram_arbiter.sv`:

  ```systemverilog
  parameter int ADDR_BITS = 25
  ...
  output logic [ADDR_BITS-2:0]   req_addr,   // WORD address
  ```

  And in `emu.sv`:

  ```systemverilog
  logic [23:0] arb_req_addr_w;   // WORD address: ADDR_BITS-1 bits
  ...
  sdram_arbiter #(.ADDR_BITS (25)) sdram_arb (
  ...
  .req_addr (probe_active ? probe_req_addr : {1'b0, arb_req_addr_w}),
  ```

  The arbiter is parameterized to 25 byte bits (32 MB), emitting a 24-bit word address (`arb_req_addr_w [23:0]`). In `emu.sv`, bit `[24]` of the SDRAM controller's word address input is padded with `{1'b0, arb_req_addr_w}`.

  Because the upper bank address bit is permanently tied to zero, only SDRAM banks 0 and 1 (32 MB) can ever be addressed. Any future multi-ROM image, homebrew expansion, or mapper configuration allocating assets in SDRAM banks 2 and 3 silently wraps into banks 0 and 1, corrupting memory.

- **Remediation**:
  Expand `ADDR_BITS` to 26 in `sdram_arbiter.sv` and `emu.sv`, widen `arb_req_addr_w` to `[24:0]`, and pass `arb_req_addr_w` directly to `.req_addr` without zero-padding.

#### 5.2.3 Truncated CHR Offset Arithmetic Wrap-Around

- **Target File**: `rtl/emu.sv:744`
- **Severity**: Low
- **Defect Description**:
  In `rtl/emu.sv`, during HPS ROM loading across the `ioctl` bus:

  ```systemverilog
  cart_load_addr <= (ioctl_addr[18:0] - 19'd16) - prg_bytes[18:0];
  ```

  `ioctl_addr` is a 27-bit word address, and `prg_bytes` is a 22-bit byte count. Truncating both signals to 19 bits before subtraction causes arithmetic underflow and modulo $2^{19}$ (512 KiB) wrap-around whenever PRG-ROM exceeds 512 KiB. This corrupts CHR data placement for large 1 MiB or 2 MiB MMC5 and homebrew ROMs.

- **Remediation**:
  Perform the subtraction at full 27-bit width before assigning to the cartridge load address: `cart_load_addr <= 19'(((ioctl_addr - 27'd16) - {5'd0, prg_bytes}));`.

## 6. RustyNES_MiSTer Platform Integration, Framework & Synthesis Audit

### 6.1 Top-Level Integration & Framework Interfacing (`rtl/emu.sv`)

#### 6.1.1 Controller D-Pad Bit Mapping Comment Inversion

- **Target File**: `rtl/emu.sv:788-796`
- **Severity**: Low (Documentation / Code Consistency)
- **Defect Description**:
  In `rtl/emu.sv`:

  ```systemverilog
  // The `J1` order in CONF_STR is A, B, Select, Start followed by the
  // framework's fixed d-pad bits, and the NES shifts out A, B, Select, Start,
  // Up, Down, Left, Right. `joystick_N` carries the d-pad in [3:0] as
  // Up, Down, Left, Right and the named buttons from [4], so the two are the
  // same eight bits in a different order.
  wire [7:0] pad1 = {joystick_0[0], joystick_0[1], joystick_0[2], joystick_0[3],
                     joystick_0[7], joystick_0[6], joystick_0[5], joystick_0[4]};
  wire [7:0] pad2 = {joystick_1[0], joystick_1[1], joystick_1[2], joystick_1[3],
                     joystick_1[7], joystick_1[6], joystick_1[5], joystick_1[4]};
  ```

  The comment explicitly asserts: *"`joystick_N` carries the d-pad in [3:0] as Up, Down, Left, Right"*.

  However, in `sys/hps_io.sv` and the official MiSTer framework specification (`MkDocs/docs/developer/hps_io.md:34-40`), the hardware bit assignments for `joystick_x[3:0]` are defined as:

  - `joystick_x[0]`: Right
  - `joystick_x[1]`: Left
  - `joystick_x[2]`: Down
  - `joystick_x[3]`: Up

  Because the Verilog concatenation places `joystick_0[0]` at bit 7 (`pad1[7]`), `joystick_0[1]` at bit 6 (`pad1[6]`), `joystick_0[2]` at bit 5 (`pad1[5]`), and `joystick_0[3]` at bit 4 (`pad1[4]`), and the NES controller shift register (`rtl/controller.sv:77-112`) shifts right with `sr[0]` outputting A, B, Select, Start, Up, Down, Left, Right, the synthesized hardware wiring happens to function correctly. However, the comment in `emu.sv` inverts the actual MiSTer framework bit order. This creates significant confusion during gamepad maintenance, turbo button mapping, or controller diagnostic audits.

- **Remediation**:
  Update the comment in `emu.sv:788-796` to accurately document the MiSTer `hps_io` bit ordering (`[0]=Right, [1]=Left, [2]=Down, [3]=Up`) and its corresponding mapping into the NES serial shift stream.

#### 6.1.2 Aspect Ratio Fallback Selection Clamping

- **Target File**: `rtl/emu.sv:1129-1131`
- **Severity**: Medium
- **Defect Description**:
  In `rtl/emu.sv`:

  ```systemverilog
  assign VIDEO_ARX = (ar == 2'd0) ? 13'd4 : {11'd0, ar - 2'd1};
  assign VIDEO_ARY = (ar == 2'd0) ? 13'd3 : 13'd0;
  ```

  Line 136 defines the OSD aspect ratio options in `CONF_STR`: `"O[2:1],Aspect ratio,Original,Full Screen;"`.
  The status bits `status[2:1]` (`ar`) are expected to be `2'b00` (Original, 4:3) or `2'b01` (Full Screen, 0:0).

  However, if `status[2:1]` evaluates to `2'd2` or `2'd3` (which occurs if an inherited MiSTer global config file, an external script, or an OSD override injects non-standard status values), `VIDEO_ARX` evaluates to `13'd1` or `13'd2`, while `VIDEO_ARY` is `13'd0`.

  In the vendored framework file `sys/sys_top.v:912-927`, when `ARY == 0`, if `ARX == 1` or `ARX == 2`, the framework interprets this as an instruction to apply custom aspect ratio multipliers (`arc1x`/`arc1y` or `arc2x`/`arc2y`) generated by the `video_freak` module. Because `video_freak` is omitted from RustyNES, `arc1` and `arc2` are unassigned/zero, causing distorted image geometry and broken video scaling on HDMI displays.

- **Remediation**:
  Harden the aspect ratio selection by clamping any non-zero value of `ar` directly to `13'd0`:
  `assign VIDEO_ARX = (ar == 2'd0) ? 13'd4 : 13'd0; assign VIDEO_ARY = (ar == 2'd0) ? 13'd3 : 13'd0;`.

#### 6.1.3 Missing SDRAM Hardware Failure OSD Diagnostic

- **Target File**: `rtl/emu.sv:162-170, 762-774, 839`
- **Severity**: Low
- **Defect Description**:
  In the off-die build (`USE_SDRAM_CART=1`), the NES core depends on an external SDRAM daughterboard. If the SDRAM module is not installed, poorly seated, or fails the hardware memory probe (`sdram_probe`), line 839 holds the core in perpetual reset:

  ```systemverilog
  wire offdie_no_sdram = USE_SDRAM_CART && (!sdram_ok || !sdram_ready);
  reset_sync u_rst_nes (.clk (clk_sys), .arst (reset | offdie_no_sdram), .rst_n_out (nes_rst_n));
  ```

  In `CONF_STR`, the OSD information strings list errors for unsupported mappers, ROM size limits, and trainers, but contain zero diagnostic text for SDRAM absence. Furthermore, `info_req` is pulsed exclusively on the falling edge of `rom_download`.

  When an off-die bitstream boots on a MiSTer system without a functioning SDRAM module, the screen remains black, and the user receives no feedback explaining why the core is unresponsive.

- **Remediation**:
  Add an SDRAM failure message to `CONF_STR` (`"SDRAM module required but not detected;"`) and pulse `info_req` when `probe_done && !probe_pass` occurs in off-die mode.

### 6.2 Clock Distribution & Reset Synchronization

#### 6.2.1 Wide Asynchronous Reset OR-Tree Glitch Hazard

- **Target Files**:
  - `rtl/emu.sv:778-779, 839-840`
  - `rtl/reset_sync.sv:1-50`
- **Severity**: Medium
- **Defect Description**:
  In `rtl/emu.sv`:

  ```systemverilog
  wire reset = RESET | status[0] | buttons[1] | rom_download
               | ~pll_locked | ~cart_loaded | ~mapper_ok;
  wire offdie_no_sdram = USE_SDRAM_CART && (!sdram_ok || !sdram_ready);
  reset_sync u_rst_nes (.clk (clk_sys), .arst (reset | offdie_no_sdram), .rst_n_out (nes_rst_n));
  ```

  The asynchronous clear port (`arst`) of `reset_sync` is driven directly by a wide combinational OR-tree combining signals across three distinct clock domains:

  - `status[0]` and `buttons[1]` (clocked by `clk_sys`, 21.477 MHz).
  - `RESET` from `sysmem` (clocked by `clk_100m`, 100 MHz).
  - `sdram_ready` from `sdram.sv` (clocked by `clk_sdram`, 85.9 MHz).
  - `sdram_ok` generated combinationally in `sdram_presence.sv:86`.

  In FPGA logic fabric (Cyclone V ALMs), asynchronous clear inputs on flip-flops bypass clock synchronization. Any static timing hazard or combinational race glitch across this multi-domain OR-tree instantly fires the asynchronous clear of `meta` and `sync` inside `u_rst_nes`, forcing a spurious reset into `nes_top`.

- **Remediation**:
  Register the asynchronous reset terms into a clean synchronous flop within `clk_sys` before driving `reset_sync`, filtering out combinational glitches while preserving safe synchronous release.

#### 6.2.2 PLL Lock Qualification & Settling Time

- **Target File**: `rtl/emu.sv:202-218`
- **Severity**: Low
- **Analysis**:
  The Altera PLL (`rtl/pll.v`) locks the 50 MHz input reference clock to generate `clk_sys` (21.477 MHz), `clk_sdram` (85.909 MHz), and phase-shifted `clk_sdram_ps`.
  `pll_locked` is fed directly into `~pll_locked` across all reset synchronizers without a lock-settling debounce counter. While Cyclone V PLL lock signals are generally stable once asserted, standard high-reliability FPGA design practices recommend qualifying lock with a small counter (e.g. 256 cycles) to ensure clock jitter has stabilized before releasing logic.

   - WebGPU API specification and safe Rust abstractions.
   - Texture streaming throughput via `wgpu::Queue::write_texture` with `TexelCopyBufferLayout` alignment.
   - Pre-allocated native staging buffer reuse patterns for high-performance mobile (Android/iOS) pipelines.

2. **`cpal` Audio Architecture (`/rustaudio/cpal`)**:
   - Cross-Platform Audio Library stream management and callback pacing.
   - `cpal::BufferSize::Default` host quantum negotiation (ALSA / PipeWire) vs. `cpal::BufferSize::Fixed` latency control.
   - Dynamic ring-buffer starvation prevention and audio/video frame drift mitigation.

3. **`gilrs` Input Subsystem (`/websites/rs_gilrs_gilrs`)**:
   - Gamepad event dispatching and event queue lifecycle via `Gilrs::next_event()`.
   - Dynamic `GamepadId` generation and disconnect handling (`EventType::Disconnected`).
   - Slot leak prevention and held-input state purging during controller hotplug cycles.

4. **`uniffi` Foreign Function Interface (`/mozilla/uniffi-rs`)**:
   - Multi-language binding generation for Kotlin, Swift, and C.
   - FFI panic isolation contracts via `std::panic::catch_unwind`.
   - Prevention of foreign runtime termination (`InternalException` in Kotlin, `SIGABRT` in Swift) and mutex poisoning.

5. **`libretro` API Specification (`/websites/libretropy_readthedocs_io_en`)**:
   - Libretro C-ABI lifecycle constraints across `retro_init`, `retro_load_game`, `retro_unload_game`, and `retro_deinit`.
   - Memory descriptor registration and deregistration protocols via `RETRO_ENVIRONMENT_SET_MEMORY_MAPS`.
   - Prevention of Use-After-Free vulnerabilities across host frontends and RetroAchievements threads.

6. **Hardware & Industry Engineering Standards**:
   - *Ricoh 2A03 / 2A07 CPU & 2C02 PPU Technical Reference Manuals* (NESdev Wiki open-bus, interrupt polling, and OAM DMA timing).
   - *Alliance Memory AS4C32M16SB 512Mb (32M x 16) Synchronous DRAM Datasheet* (Rev 1.0, timing parameters, command truth tables).
   - *JEDEC Standard No. 21-C*: Synchronous DRAM Configurations and Auto-Refresh Requirements ($t_{REFI}$, $t_{RFC}$).
   - *Altera / Intel Cyclone V Device Handbook* (Volume 1: Transceiver and Core Fabric Architecture, Volume 2: Power and Grounding).
   - *Altera Quartus Prime Standard / Lite Edition Handbook*: TimeQuest Timing Analyzer Principles, SDC Constraints, and Recovery/Removal Slack.
